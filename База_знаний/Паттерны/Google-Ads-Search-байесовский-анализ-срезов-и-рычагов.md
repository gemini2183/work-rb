# Google Ads Search — байесовский анализ срезов и рычагов

Написано по запросу пользователя 2026-09-28 (ProfiMet, `Search | Poliweglan | Pl`):
существующий [[Google-Ads-аудит-кампании-алгоритм-и-ошибки-смешения-данных|алгоритм
аудита]] отвечает на вопрос "что вообще происходит в кампании" (структура трафика по
типу/сети, инвентарь, search terms, IS), но не отвечает на два следующих вопроса,
которые нужны пользователю:

1. **Каким полным набором рычагов вообще можно управлять** в Search-кампании — не
   только "что посмотреть", а "что можно включить/выключить/подкрутить/исключить/
   перенести".
2. **Какие конкретные срезы внутри каждого рычага статистически тянут
   эффективность вверх/вниз** — причём выявляется это анализом данных конкретной
   кампании, а не выбирается заранее по шаблону ("для Search обычно смотрят вот
   это"). Список рычагов ниже — это пространство поиска, не прогноз результата.
3. **Решение по срезу зависит не только от статистики самого среза, но и от того,
   как идёт KPI всего проекта за месяц** — при выполняющемся плане статистически
   слабый, но всё ещё конверсионный срез можно осознанно не трогать и продолжить
   наблюдение; при плане под угрозой тот же срез уже стоит действия на меньшей
   уверенности (см. Часть 3.0). Байесовский вывод не заменяет эту рамку, а
   комбинируется с ней.

Задача документа — дать: (а) исчерпывающий чек-лист рычагов Search-кампании, (б)
единый статистический метод, которым по каждому рычагу оценивается, значим ли
разброс между срезами и какой срез плохой/хороший, устойчивый и к большим, и к
маленьким выборкам, (в) как из статистического вывода получить конкретное действие,
(г) как вести цикл "действие → лог → повторная проверка → разбор результата".

## Часть 1 — Каталог рычагов Search-кампании (пространство поиска)

Полный список того, чем можно управлять в ручной Search-кампании Google Ads (не
Performance Max/Shopping — там своя механика, см.
[[../Инструменты/Search-Term-View-ограничения-Shopping-Performance-Max|ограничения]]).
Для каждого — какой ресурс Google Ads API/GAQL его несёт (для будущей автоматизации
сбора) и какое действие соответствует "срез плохой"/"срез хороший".

### 1.1 Семантика (ключевые слова)
- **Что:** ключевые фразы, их match type (BROAD/PHRASE/EXACT), статус
  (ENABLED/PAUSED), группа объявлений, в которой лежат.
- **Ресурс:** `keyword_view`, `ad_group_criterion`.
- **Действия:** пауза ключа, смена match type (обычно сужение BROAD→PHRASE/EXACT
  при плохом качестве трафика), перенос в отдельную группу/кампанию (другая ставка/
  объявление), добавление новых ключей на основе search terms.

### 1.2 Поисковые запросы (search terms) — то, ПО ЧЕМУ реально показались объявления
- **Что:** фактический текст запроса пользователя, не совпадает 1:1 с загруженным
  ключом (особенно на BROAD/PHRASE).
- **Ресурс:** `search_term_view` (для чистого Search — доступен полностью, в отличие
  от PMax/Shopping).
- **Действия:** минус-слово/минус-фраза (исключение), перевод хорошего запроса в
  отдельный EXACT-ключ ("harvest" — забрать конверсионный запрос под явный контроль
  ставки).

### 1.3 Площадки показа (сеть)
- **Что:** Google Search vs Search Partners — см. Правило №1 в
  [[Google-Ads-аудит-кампании-алгоритм-и-ошибки-смешения-данных]]: разные аукционы,
  никогда не смешивать при выводах. Внутри Search Partners — конкретные площадки.
- **Ресурс:** `segments.ad_network_type` на campaign/ad_group уровне,
  `detail_content_suitability_placement_view` для площадок SPN (см.
  `gads_search_partners_audit.py`, доступен только impressions без cost/conversions
  по площадке).
- **Действия:** полностью выключить показ в Search Partners в настройках сети
  кампании (это рубильник на весь network, не по отдельной площадке — Google Ads не
  даёт исключать конкретные площадки SPN для Search-кампаний с точностью, как для
  Display/PMax).

### 1.4 Устройства
- **Что:** Desktop / Mobile / Tablet.
- **Ресурс:** `segments.device`.
- **Действия:** корректировка ставки (bid adjustment, от -100% до +900% в Search),
  вплоть до фактического исключения устройства через -100%.

### 1.5 Гео (локация показа)
- **Что:** таргетинг по стране/региону/городу/радиусу, Presence vs
  Presence-or-Interest, позитивный/негативный таргетинг.
- **Ресурс:** `campaign_criterion` (location), `geo_target_constant` для расшифровки
  ID в название (см. `gads_campaign_settings.py`).
- **Действия:** корректировка ставки по региону, исключение региона (негативный
  таргетинг), сужение Presence-or-Interest → Presence only (частая причина
  нерелевантного гео-трафика, см. Ошибку 6 ниже).

### 1.6 Время показа (расписание)
- **Что:** день недели × час, ad schedule.
- **Ресурс:** `campaign_criterion` (ad_schedule).
- **Действия:** корректировка ставки по часу/дню, полное отключение показа в
  конкретные слоты (-100%).

### 1.7 Аудитории (наблюдение/таргетинг)
- **Что:** для Search — только режим "Observation" (наблюдение, не сужение
  трафика) либо RLSA (ретаргетинг списков) в режиме таргетинга. In-market,
  affinity, демография (возраст/пол/доход), Customer Match, similar audiences.
- **Ресурс:** `campaign_criterion`/`ad_group_criterion` (audience),
  `campaign_audience_view` для метрик по сегменту.
- **Действия:** корректировка ставки по сегменту (типичный случай — поднять ставку
  на ремаркетинг-аудиторию, потому что она конвертит лучше холодного трафика),
  перевод из Observation в Targeting (сузить показ только на список), исключение
  сегмента.
- **Важно:** демографические срезы (возраст/пол) в Search доступны как
  bid-adjustable измерение, в отличие от PMax, где `campaign_audience_view`
  подтверждённо не отдаёт данные (см. запись Корогва 2026-09-08 в
  [[Google-Ads-аудит-кампании-алгоритм-и-ошибки-смешения-данных]]) — это
  ограничение специфично PMax, для чистого Search демография обычно доступна,
  но перед выводом стоит проверить на конкретном аккаунте (может отсутствовать из-за
  малого трафика/настроек privacy, не путать с системным ограничением).

### 1.8 Объявления и Assets (RSA, расширения)
- **Что:** варианты заголовков/описаний внутри Responsive Search Ad, их
  performance label (Low/Good/Best), Ad Strength; расширения (sitelinks,
  callouts, structured snippets, call assets, etc.).
- **Ресурс:** `gads_ads_dump.py`/`gads_ad_extensions.py` (уже есть в `Скрипты/`),
  `ad_group_ad_asset_view` для performance по отдельному asset внутри RSA.
- **Действия:** замена/пауза низкоэффективного asset, добавление нового варианта
  заголовка/описания, добавление недостающего типа расширения (структурно повышает
  Ad Rank/CTR по документации Google, см. дисклеймер ниже про "не проверено").

### 1.9 Группы объявлений (структурный уровень)
- **Что:** сама разбивка кампании на группы — по интенту, по продукту, по гео.
- **Ресурс:** `ad_group` + агрегаты по перечисленным выше срезам внутри группы.
- **Действия:** разделение одной "смешанной" группы на несколько по интенту (когда
  внутри одной группы конкурируют высоко- и низкоконверсионные темы запросов),
  слияние избыточно раздробленных групп.

### 1.10 Стратегия и уровень ставок
- **Что:** ручные CPC vs автостратегии (Maximize Conversions/Conversion Value,
  Target CPA/ROAS), сам таргет.
- **Ресурс:** `campaign.bidding_strategy_type`, `campaign_budget`.
- **Действия:** смена стратегии, изменение таргета — это не "срез" в смысле
  сегментации трафика, а параметр самого алгоритма; рассматривается отдельно от
  срезов 1.1–1.9, но решения по срезам (что исключить/добавить) напрямую меняют
  данные, на которых автостратегия обучается — см. предостережение в Части 3.

### 1.11 Бюджет
- **Что:** дневной бюджет кампании, распределение между кампаниями одного клиента.
- **Действия:** увеличение/уменьшение — оправдано **только** если Lost IS Budget
  подтверждает нехватку бюджета (шаг 7 существующего алгоритма) — не по интуиции.

## Часть 2 — Статистический метод: байесовская оценка среза

### 2.1 Почему не голое сравнение чисел и не классический частотный тест

Голое "у среза A конверсия 8%, у среза B — 3%, A лучше" не учитывает объём данных:
при 2 конверсиях из 25 кликов и 1 из 33 разница может быть чистым шумом. Классический
частотный тест (z-test на пропорции, p<0.05) в целом верен, но:
- даёт бинарный ответ (значимо/не значимо) там, где для решения нужна вероятность
  и величина эффекта, не порог;
- при очень малых выборках (типично для отдельных срезов Search-кампании — конкретный
  час дня, конкретный узкий сегмент аудитории) его допущения (нормальное приближение)
  становятся ненадёжны;
- не даёт естественного способа включить то, что мы уже знаем про кампанию в целом,
  когда данных по конкретному срезу мало.

Байесовский подход решает все три: даёт распределение вероятностей, а не порог;
корректен при любом n, включая единицы наблюдений; естественно включает prior.

### 2.2 Модель: Beta-Binomial для конверсии

Для любого среза (ключ / гео / устройство / час / аудиторный сегмент / вариант
объявления), где событие — "клик → конверсия" (бинарный исход):

- **Prior**: Beta(α₀, β₀), заданный из данных всей кампании (или всего аккаунта,
  если кампания сама маленькая) за репрезентативный период. Не uniform Beta(1,1) —
  это выбросило бы всё априорное знание о нише/аккаунте, которое у нас есть.
  Практический способ задать: `α₀ = k · CR_kампании`, `β₀ = k · (1 − CR_kампании)`,
  где `CR_kампании` — базовая конверсия кампании, `k` — "сила" prior в эквиваленте
  наблюдений (обычно 20–50: достаточно, чтобы сглаживать шум на срезах с единицами
  кликов, но не настолько много, чтобы забить сигнал среза с уже сотнями кликов).
- **Апостериор** после данных среза (`clicks`, `conversions`):
  `Beta(α₀ + conversions, β₀ + clicks − conversions)`.
- **Оценка**: апостериорное среднее `= (α₀+conversions) / (α₀+β₀+clicks)` — это и
  есть "сглаженная" оценка конверсии среза, устойчивая при малом n (при 0 кликов
  апостериор = prior, что и правильно — ничего не узнали, значит не отклоняемся от
  базовой оценки).
- **Сравнение со средним по кампании**: вычислить `P(θ_среза < θ_кампании − δ)` —
  вероятность, что реальная (не выборочная) конверсия среза хуже средней минимум на
  δ процентных пунктов (порог δ задаётся исходя из практической значимости, не
  статистической — например δ=2 п.п. для кампании с базовой CR~5%). Считается
  численно (Monte Carlo сэмплирование из апостериора, тривиально в Python/`scipy.stats.beta`)
  или аналитически через разность двух Beta-распределений.
- **Порог действия**: не "p<0.05", а прямая вероятность, понятная в терминах
  решения — например `P(срез хуже на ≥δ) > 0.9` → кандидат на исключение/понижение
  ставки; `P(срез лучше на ≥δ) > 0.9` → кандидат на усиление ставки/выделение в
  отдельную кампанию.

### 2.3 Модель для непрерывных метрик (CPC, CPA)

Конверсия — не единственная метрика, которую нужно сравнивать по срезам (пример —
сравнение CPC разных устройств). Для метрик, которые не бинарны (стоимость клика,
время на сайте), Beta-Binomial не подходит — прямых готовых рецептов пока в базе
знаний нет, при необходимости смотреть Gamma-Normal или бутстрэп доверительных
интервалов по логарифмированным значениям (типичный подход для стоимостных метрик
с правым хвостом) — **отметить как открытый вопрос методологии**, не факт, решать
по ситуации при первом реальном случае, когда понадобится.

### 2.4 Слой "impact" поверх слоя "вероятность"

Вероятность "срез плохой" — не единственный критерий действия. Второй обязательный
слой — объём: `expected_wasted_spend = P(срез плохой) × cost_среза` (ожидаемые
потраченные деньги на срез, который вероятно плохой). Приоритизация действий — по
этому произведению, не по одной вероятности: срез с P=95% "плохой" и расходом $2 за
месяц не первый в очереди, если рядом есть срез с P=75% и расходом $200.

### 2.5 Multiple comparisons (проверка много срезов сразу)

При проверке сразу многих срезов одного измерения (напр. 50 отдельных ключей) риск
случайно найти "значимый" срез растёт с числом сравнений (проблема множественных
сравнений). Байесовский подход снижает остроту проблемы естественно (за счёт prior,
подтягивающего шумные оценки к среднему — это и есть частичное решение, известное
как "shrinkage"), но не устраняет полностью: держать в уме, что при 50 проверенных
ключах 2-3 "случайно значимых" на P>0.9 стоит ожидать даже если реального эффекта
нет нигде. Практическое смягчение — требовать не только высокую P, но и
согласованность во времени (тренд виден на нескольких подряд идущих периодах, не
на одном снапшоте) перед необратимым действием (см. также правило "тренд ≥5-7 дней"
в [[Месячный-горизонт-анализа-и-принятия-решений]]).

## Часть 3 — От статистики к действию

### 3.0 Сначала — состояние KPI проекта за месяц, ДО ранжирования срезов

Вероятность "срез плохой" и объём денег на нём (Часть 2.4) — необходимые, но не
достаточные условия для действия. Решение всегда проходит ещё через один фильтр:
**как сейчас обстоят дела с планом/KPI проекта за отчётный месяц в целом**
(бюджет/заявки/CPL — план vs факт на сегодняшний день месяца, см.
[[Месячный-горизонт-анализа-и-принятия-решений]]). Один и тот же байесовский вывод
про срез должен давать разное действие в зависимости от этого состояния — общий
KPI не обнуляет статистику среза, а модифицирует порог, с которого по ней начинают
действовать:

- **План выполняется / с запасом** — для срезов в статистической серой зоне
  (P(плохой) 0.7–0.9, то есть вероятно, но не наверняка хуже) — не трогать, если
  срез всё ещё физически приносит конверсии, продолжить наблюдение ещё период.
  Здесь цена ошибки первого рода (тронуть на самом деле нормальный срез, поймав
  шум) выше цены бездействия — общий результат месяца не требует рисковать
  работающим, пусть и неидеальным, источником трафика. Действовать сразу — только
  по срезам с P > 0.9 и заметным impact (обычный порог Части 2.2/2.4), либо по
  явным багам (см. правило в [[Месячный-горизонт-анализа-и-принятия-решений]] —
  баги чинятся вне очереди независимо от фазы/KPI).
- **План под угрозой** — порог смягчается в обратную сторону: тот же срез в серой
  зоне (P 0.7–0.9) уже стоит действия, потому что цена бездействия (не дотянуть
  план) выросла. Приоритет — не эксперименты с новыми гипотезами (см. фазу "добор
  плана", дни 21+, в [[Месячный-горизонт-анализа-и-принятия-решений]]), а
  концентрация на подтверждённо рабочих срезах и обрезание вероятно слабых, даже
  на неполной уверенности.
- Порог P=0.9 по умолчанию (Часть 2.2) двигается вместе с этой оценкой, а не
  переопределяется отдельным числом — фиксировать в логе (Часть 4), каким именно
  порогом руководствовались в конкретном решении и почему (план выполняется/под
  угрозой на момент решения), чтобы при разборе результата было видно, менялся ли
  критерий между решениями по одной кампании.

Практическое следствие: перед тем, как переходить к шагам 1-5 ниже, явно
зафиксировать одной строкой — на какой день месяца идёт разбор, план/факт по
KPI клиента на этот день, и какая фаза месяца сейчас (наблюдение/коррекция/добор
плана) — это не отдельный необязательный контекст, а прямой параметр решения.

### 3.1–3.5 Ранжирование срезов и формулировка действий

1. Для каждого рычага (Часть 1) посчитать апостериорную оценку по всем его срезам.
2. Отранжировать срезы внутри рычага по `expected impact` (Часть 2.4), не по сырой
   разнице конверсии.
3. Для срезов выше порога действия (порог — из 3.0, не фиксированный) —
   сформулировать конкретный шаг: пауза / минус-слово / bid adjustment (с
   конкретным %) / перенос в отдельную кампанию / изменение бюджета. Один срез =
   одно предлагаемое действие, с явной вероятностью и объёмом денег на кону в
   обосновании.
4. **Предостережение про автостратегии (относится к Части 1.10):** если кампания на
   Maximize Conversions/Target CPA, резкое исключение среза, дающего заметную долю
   объёма (даже плохого по конверсии), может временно разбалансировать обучение
   алгоритма — см. общий принцип "молодая vs зрелая кампания" в
   [[Google-Ads-аудит-кампании-алгоритм-и-ошибки-смешения-данных]] (порог ~30
   конверсий/30 дней для надёжной работы автостратегии). Крупные по объёму
   исключения — поэтапно, с мониторингом, не одним залпом.
5. Перед выводом уровня "этот срез/кампания не работает" — обязательна сверка
   конверсий (см. [[Сверка-конверсий-Директ-Метрика-Коллтрекинг]] и наработанную для
   ProfiMet практику сверки Ringostat vs Google Ads,
   [[../../Клиенты/ProfiMet/Решения|Решения — ProfiMet]], записи 2026-09-21).

## Часть 4 — Цикл действие → лог → проверка эффекта

Каждое действие, принятое по этой методологии, фиксируется в логе конкретной
кампании (`Клиенты/<клиент>/Кампании/Search/<кампания>.md`) записью формата
CLAUDE.md (`## [ГГГГ-ММ-ДД] Кампания/тема | действие | гипотеза | результат`),
обязательно включающей:
- какой срез, какая апостериорная P и expected impact на момент решения;
- **состояние KPI проекта на момент решения** (план/факт месяца, фаза — см. Часть
  3.0) и какой порог действия из-за этого применялся — иначе при разборе результата
  через месяц невозможно понять, почему в похожей ситуации решение было разным;
- какое именно действие предпринято (значение corrections/паузы/переноса);
- **явное предсказание** — какой эффект ожидается и когда его можно будет измерить
  (дата повторной проверки — не раньше, чем накопится статистика для новой оценки:
  для нового условия — фаза наблюдения 5-7 дней, см.
  [[Месячный-горизонт-анализа-и-принятия-решений]]).

На дату повторной проверки — пересчитать апостериор среза уже по данным ПОСЛЕ
действия и явно сравнить с предсказанием: сбылось / не сбылось / неоднозначно
(данных пока мало для вывода). Если не сбылось — отдельным пунктом того же лога
разобрать вероятную причину (внешний фактор, неверная гипотеза, недостаточный
период) — не молчать об этом и не считать цикл законченным без этого разбора.

## Как использовать в следующей сессии

1. Прогнать Часть 1 как чек-лист — по каждому рычагу собрать данные (часть уже
   покрыта существующими скриптами `Скрипты/gads_*`, часть — новые GAQL-запросы,
   которых пока нет: bid adjustments/устройства/гео/время/аудитории по конкретной
   Search-кампании отдельными срезами — на 2026-09-28 такого готового скрипта в
   `Скрипты/` нет, собирать).
2. По каждому собранному срезу — байесовская оценка (Часть 2), ранжирование по
   impact (Часть 2.4).
3. Сформировать список действий (Часть 3), согласовать с пользователем.
4. Внести в лог кампании (Часть 4), назначить дату проверки.
5. На дату проверки — вернуться к этому же документу, не собирать методологию заново.

## Статус и ограничения

Документ написан как методология "с нуля", **ни разу не применялся на практике** —
статус "не протестировано". Часть 2.3 (непрерывные метрики) оставлена как открытый
вопрос — закрыть при первом реальном случае. При первом практическом применении (на
ProfiMet, `Search | Poliweglan | Pl`) — актуализировать документ по итогам:
что из перечисленных рычагов оказалось реально применимо на конкретном аккаунте,
какие GAQL-запросы понадобились и стоит ли оформить их отдельным скриптом в
`Скрипты/` по аналогии с остальными инструментами аудита.
