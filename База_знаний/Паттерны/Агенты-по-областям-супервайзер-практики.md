# Агенты по областям + супервайзер: что говорят практики

**Вопрос пользователя 12.11:** соответствует ли наша схема (тонкий супервайзер, агенты областей с узким контекстом и карточкой скриптов, сборщик скриптов при «пробеле», запись только по «да») лучшим практикам.

**Внешние источники (не проверено на наших кампаниях):**
- Anthropic, описание своей мультиагентной системы исследований: схема «оркестратор + исполнители», у каждого исполнителя свой контекст, они возвращают сжатый результат. Приводятся: ~4× токенов у агента против чата и ~15× у мультиагентной системы; около 80% разницы в качестве объясняется объёмом токенов; первые версии плодили лишних исполнителей на простых вопросах, поэтому в промпт добавили правила масштаба (простой факт — один агент и 3–10 вызовов). Цифры взяты из пересказов, оригинал [anthropic.com/engineering/multi-agent-research-system](https://www.anthropic.com/engineering/multi-agent-research-system) полностью не перечитывался.
- Руководства по субагентам Claude Code: узкая область на агента без пересечений, конкретное описание (по нему выбирается агент), чистый контекст у каждого запуска (плюс: изоляция; минус: задержка и стартовые токены), цепочки без чёткой стратегии «съедают» токены; субагент не запускает другого субагента. Критерии «когда не нужно» поиском не найдены (есть статья Anthropic «how and when to use subagents», её содержимое не читалось).

**Сверка с нашей схемой:** совпадает — узкая область, карточка вместо общего каталога, запись отдельным вызовом, файлы вместо пересказов. Расходится/риск — нет правила масштаба: для 1–2 коротких чтений агент (старт ~25 тыс. токенов) не окупается; замер 12.11 агента GTM-чтения: 7 вызовов, вес 119 тыс. на haiku против моих 4 команд в основной сессии (оценка 50–80 тыс.).

**Вывод для правил:** агента звать, когда задача ≥ ~5 вызовов, тяжёлый вывод, повторяется или контекст супервайзера уже велик; 1–2 коротких чтения супервайзер делает сам. Пересмотреть по замерам `claude_usage.py --agents`.
