# Методология анализа кампаний: чем считаем на каждом шаге

Общая для всех клиентов, без цифр конкретных проектов. Порядок шагов и «зачем» - в [[Алгоритм_анализа_кампании]] (для клиентов с продажами ещё [[Алгоритм_анализа_кампании_продажи]]). Здесь - метод каждого шага, обоснование и статус. Числа клиента и результаты проверок на его истории - в `Клиенты/<Имя>/Калибровка_методов.md`. Риск - [[Политика-риска-планов-оптимизации]].

**Зачем:** любой вывод и действие имеют записанное обоснование - почему этот метод, этот период, этот порог, что выведено расчётом, что взято из стандартной практики, что пока рабочая оценка. Чтобы ни у аудитора, ни у клиента не было сомнения, что оптимизация делается наугад.

**Статусы параметров:** «выведено расчётом»; «стандартный метод» (статистическая практика); «рабочая оценка» (взято на глаз, проверить «экзаменом на прошлом»); «решение пользователя». Параметр со статусом «рабочая оценка» помечается «не утверждено» в каждом выводе, где участвует.

**Принцип достоверности.** Каждый вывод несёт число достоверности (интервал или вероятность). Где данных мало - так и пишем: «достоверность низкая, интервал ±X %». Действовать в окне месяца приходится и на малых данных: допустимо только с названным риском и ограничением потери (недобор вместо слива бюджета).

**Принцип плана.** Вывод «невыполнимо, не запускаем» недопустим: результат этапа 2 - всегда план действий (рычаги и тесты с долей бюджета). Успех теста - направление и вероятность выхода на цель, а не обязательное точное подтверждение за месяц.

## Для этапа 1: оценка месяца против КПИ
| Что считаем | Метод | Статус |
|---|---|---|
| Темп к плану и прогноз закрытия | расход и заявки на дату против плана; вес дней недели (выходные) считается из истории клиента, не линейно «÷ дней» | выведено из истории клиента |
| Допустимая цена заявки T | задаётся планом клиента; при учёте продаж T = P × d (интервал Уилсона для доли d) - [[Алгоритм_анализа_кампании_продажи]] | выведено расчётом |
| Нужно в день на остаток | (бюджет − потрачено) ÷ дней осталось; цена заявки на остаток = (бюджет − потрачено) ÷ (план заявок − получено) | арифметика |

## Для шага 2.2: выбор периода анализа
- **Точность по числу заявок.** Относительная полуширина 95 % интервала Пуассона ≈ 1,96/√n (нормальное приближение; при n < 20 - точный интервал Гарвуда). Для ±25 % нужно n ≈ 62. Статус: выведено расчётом.

| заявок в окне n | 7 | 15 | 30 | 60 | 120 |
|---|---|---|---|---|---|
| полуширина 95 % | ±74 % | ±51 % | ±36 % | ±25 % | ±18 % |

  Изменение цены заявки меньше полуширины в окне с n заявками от шума не отличить. Следствие: эффект правки у малой кампании за месяц подтвердить нельзя; решение опирается на механизм и априор с названной достоверностью.
- **60 заявок - ориентир точности**, не условие решения: решения принимаются по вероятности (2.4).
- **Окно под вопрос.** Окно для уровня кампании («сколько заявок сейчас и будет на следующей неделе») и окно для поиска сегментов (запросы, ключи, часы) - разные вопросы, окна подбираются отдельно. Подбор - бэктестом на истории клиента: предсказываем следующую неделю при разных окнах, берём с минимальной ошибкой; различие окон проверяется статистически (тест Диболда-Мариано, поправка Холма). Фиксированного окна для всех нет. Статус: метод стандартный; значения окон - в калибровке клиента.
- **Целые недели.** Сезонность дня недели убирается расчётом (веса или пуассоновская регрессия с днём недели), а не обрезкой. Статус: стандартный метод.
- **Календарный месяц сверху:** клиент оценивает конкретный месяц.

## Для шага 2.3: граница окна (слом по данным)
- **Метод:** смотрим дневные расход, клики, цену клика, показы; слом - отклонение > 2-3 стандартных отклонений дневных значений; для накопленного сдвига - CUSUM / точка излома. Слом ищется по показателям с большим числом событий, не по заявкам. Статус: метод стандартный; порог 2-3σ - рабочая оценка.
- **Почему не дата правки:** журнал правок не видит автоправки Google и GTM/коллтрекинг/сайт, а история в API хранится ~29 дней. Журнал - дополнительная проверка.
- **Классы правок** (для дополнительной проверки): А - меняет процесс получения заявок (пауза/включение, смена стратегии или цели CPA, посадочная, гео, расписание, списки аудиторий, правки GTM/коллтрекинга/подмены номера); Б - не сбрасывает окно (бюджет в пределах ±20 %, единичные минус-слова/ключи, ставка до 10 %). Пороги 20 % и 10 % - рабочие оценки.
- **Оговорки:** отложенный эффект правки (обучение стратегии); сломанный трекинг (заявки скачут при ровных кликах); при частых правках окно не короче двух целых недель с метками правок по дням.
- **Чистые дни:** выходные по расписанию, паузы, правки посреди дня, неполные часы не смешиваются с обычными днями.

## Для шага 2.4: достоверность и малые данные
- **Лестница методов по числу заявок n в окне:** n ≥ 60 - прямая оценка с интервалом Пуассона/Гарвуда; 15-59 - сжатие к уровню «семьи» кампаний (эмпирический байес, гамма-пуассоновская модель для заявок, бета-биномиальная для долей); 1-14 - цена заявки = цена клика ÷ конверсия (конверсия из соседних кампаний на ту же страницу); 0 - правило остановки и дата «когда можно судить». Статус: порог 60 выведен (±25 %), порог 15 - рабочая оценка.
- **«Семья»:** тип кампании, намерение/бренд, источник заявки. Сжатие к среднему по всему аккаунту недопустимо (Brand, PMax, Search - разные процессы). Нет семьи - только интервал и «данных нет».
- **Интервал Гарвуда:** нижняя граница = ХИ2.ОБР(0,025; 2n)/2, верхняя = ХИ2.ОБР(0,975; 2n+2)/2 (Excel/Таблицы; в английской версии CHISQ.INV). Цена заявки: расход ÷ верхняя граница и расход ÷ нижняя. Допущение: заявки приходят случайно, без пачек.
- **Доли (например, доля заявок, дошедших до продажи):** интервал Уилсона.
- **Уровень доверия:** 80 % - мелкие обратимые шаги; 95 % - необратимые и дорогие; задаётся ДО расчёта по цене ошибки. Статус: рабочее правило.
- **Много срезов сразу:** по случайности 2-3 из 50 «значимых»; применяем поправку Бенджамини-Хохберга или порог по расходу без заявок; малые срезы - в «прочее» с пометкой. Статус: стандартный метод.
- **Микроконверсии** (клики по номеру и т. п.) - только после проверки связи с заявкой на истории клиента.

## Для шага 2.6: правило остановки
- Расход S, допустимая цена заявки T, ожидали k = S/T заявок. Если получили 0, вероятность такого при допустимой цене P = e^(−k): 2T ≈ 13 %, 3T ≈ 5 %, 4T ≈ 2 %.
- Допущения: заявки приходят случайно без пачек; расход считается после последнего слома. Проверка допущения: отношение дисперсии заявок по дням к среднему (заметно больше 1 - переходим на отрицательное биномиальное и поднимаем k).
- Порог k задаётся по цене ошибки и политике риска; k=3 условен. Статус: формула выведена, порог - рабочая оценка; для сегментов подтверждение проверяется бэктестом на истории клиента (результаты - в калибровке).
- Тесты: доля бюджета, параллельный контроль; для оценки эффекта правки - разность разностей или CausalImpact (метод стандартный).

## Для шага 2.7: источники заявок
Конверсии кабинета могут расходиться с основным источником (звонки без привязки к кампании, пачки мусорных форм). Перед выводом «кампания слабая» - сверка по [[Сверка-конверсий-Директ-Метрика-Коллтрекинг]]. Расхождение измеряется по неделям; если нестабильно - кабинет только направление.

## Для этапа 3: тесты и доля бюджета
Формула доли бюджета на тесты - в [[Алгоритм_анализа_кампании_продажи]] (для клиентов без учёта продаж аналог по цене заявки). Тест по определению может провалиться; учёт тестов ведётся отдельной строкой, чтобы провал не выглядел как ухудшение базы.

## Непрерывная калибровка по клиенту
«Экзамен на прошлом» - постоянный процесс по каждому клиенту.
1. **Журнал предсказаний:** каждый интервал и прогноз записывается (дата, кампания, метод, окно, n, интервал/вероятность); при наступлении срока - факт.
2. **Метрики точности:** покрытие интервалов (доля фактов внутри заявленного 95 %; цель ≈95 %), ошибка прогноза (sMAPE/WAPE), для правила остановки - доля верных срабатываний и ложных тревог, для месяца - прогноз против факта.
3. **Корректировка:** параметры пересчитываются по накопленной истории клиента; у нового клиента - значения общей модели, сжатые к клиенту. Метод с покрытием ниже заявленного переводится на более консервативный.
4. **Хранение:** `Клиенты/<Имя>/Калибровка_методов.md` (сводка и решения), CSV журнала предсказаний в `Статистика/`. Скрипта нет (пробел для `script-builder`).

**План первой проверки («экзамен на прошлом»):** (1) история клиента по неделям и журнал правок; (2) окно: предсказать следующую неделю при окнах 1/2/3/4/6 недель; (3) покрытие интервалов; (4) правило остановки: верные и ложные срабатывания; (5) пуассоновость; (6) результат каждой проверки записывать в калибровку клиента и менять статус параметра. Пока проверки нет, в клиентских материалах параметры не называются «выведенными».

## Словарь простыми словами
- **Интервал (95 %).** Коридор, в который настоящее значение попадает с вероятностью 95 %. Заявки случайны; чем их меньше, тем шире коридор.
- **Пуассон.** Математика случайных событий вроде заявок: вероятность «получить 0, 5, 20 заявок», если в среднем ждём столько-то.
- **Правило остановки.** Потратили S, ждали S/T заявок. Ждали три и больше, получили 0 - вероятность такого при допустимой цене около 5 %, значит, скорее всего, кампания дороже допустимого.
- **Априор.** То, что знаем до данных кампании (например, конверсия по той же странице).
- **Эмпирический байес.** Взять такой априор из соседних кампаний и подмешать данные кампании.
- **Интервал Уилсона.** Коридор для долей.
- **CUSUM.** Накопительная проверка ряда: ловит день, с которого уровень сдвинулся.
- **CausalImpact / разность разностей.** Сравнить кампанию до и после с похожей нетронутой, чтобы понять, дала ли правка эффект.
- **Поправка Бенджамини-Хохберга.** Защита, когда смотришь много срезов: часть «значимых» случайна.
- **Экзамен на прошлом.** Предсказываем следующую неделю при разных настройках на истории и выбираем настройки с меньшей ошибкой.
- **Покрытие интервала.** Как часто факт попал в заявленный коридор; если реально 70 % вместо 95 %, метод переоценивает точность.
