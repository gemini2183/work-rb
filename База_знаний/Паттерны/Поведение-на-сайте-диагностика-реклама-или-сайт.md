# Поведение на сайте: как отличить «проблема в рекламе» от «проблема в сайте»

Концепция для всех клиентов (обсуждение 2026-10-14). Внешние источники, на наших кампаниях не проверено.
Связано: [[Сверка-конверсий-Директ-Метрика-Коллтрекинг]], [[Google-Ads-Search-байесовский-анализ-срезов-и-рычагов]], [[Месячный-горизонт-анализа-и-принятия-решений]], `Скрипты/site_page_audit.py` (статический аудит страницы).

## Зачем
Когда правки в кампаниях (ключи, минусы, ставки) не двигают заявки, причина может быть ниже по воронке: на сайте. Нужен способ доказать это цифрами, а не ощущением.

## Главная логика диагностики (один срез: посадочная × источник)
| Картина | Вывод |
|---|---|
| Плохое поведение на одной странице у ВСЕХ кампаний | страница (общая переменная) |
| Плохое поведение только у одной кампании/группы на нормальной странице | трафик: запросы, аудитория, объявление обещает не то |
| Низкий CTR при нормальном поведении | объявления |
| Хорошее поведение, но заявок нет | форма/звонок/трекинг: проверить сверку конверсий |

Источник логики: Foundry CRO (ad-or-landing-page-problem-diagnosis) — паттерн «CTR норм, конверсия плохая по всем кампаниям = страница»; сверять с оценкой «Опыт посадочной страницы» в Quality Score ([[Google-Ads-Quality-Score-компоненты-и-как-поднять]]). Источник — блог CRO-агентства, цифр и данных там нет.

## Что мерить (иерархия сигналов, от сильных к слабым)
1. **Начал заполнять форму / отправил / клик по телефону / клик по мессенджеру** — реальные микро-конверсии, ближе всего к заявке.
2. **Дошёл до ключевых блоков** (цена, форма, контакты, каталог) — событие на показ блока (IntersectionObserver / GTM «Видимость элемента»), а не процент скролла.
3. **Вовлечённая сессия GA4** (>10 с, ≥2 просмотра или key event) — грубо, но бесплатно и уже есть.
4. **Скролл**: встроенный GA4 даёт только одну отметку 90% — для карты экранов не годится; нужны свои пороги (25/50/75) через GTM.
5. **Rage/dead clicks, быстрый возврат назад** (Microsoft Clarity, бесплатно) — находят сломанные элементы; это поиск дефектов, а не метрика для KPI.

«Скролл + время» как составной индекс вовлечённости — слабый сигнал для лидогена: на коротких посадочных скролл глубокий и без интереса, на длинных читают и уходят. Использовать как вспомогательный, не как главный.

## Условия, без которых вывод недействителен
- **Проверить на своих данных, что сигнал предсказывает заявку** (доля дошедших до блока цены у сессий с заявкой vs без). Если связи нет — показатель клиенту не показываем.
- **Один знаменатель и период** во всех срезах; сравнение внутри клиента (страница с страницей, источник с источником), а не с «отраслевыми нормами».
- **Малые выборки** — сотни сессий на источник, десятки заявок: нужен байесовский интервал, а не сравнение процентов (`gads_bayesian_slice_analysis.py`).
- **Согласие на cookies / consent mode**: сессии без согласия не видны в GA4 → поведение смещено (на ProfiMet проверяли `metrika_consent_profimet.py`).
- **Сверка источника**: разметка UTM/gclid должна быть одинаковой, иначе срез «по кампаниям» ломается.
- **Боты и внутренний трафик** портят вовлечённость: исключить.
- **Что на сайте менял клиент** между периодами — иначе тренд не интерпретировать.

## Реализация (по возрастанию затрат)
- **Уровень 0 (сейчас, без правок сайтов):** GA4 Data API / Метрика: отчёт «посадочная × источник/кампания»: сессии, вовлечённые, key events, звонки. Прогон статического `site_page_audit.py`.
- **Уровень 1 (разовая настройка на клиента):** GTM: события на 3–5 важных экранов (показ блока), клик по телефону/мессенджеру, начало формы, отправка; Clarity с интеграцией в GA4.
- **Уровень 2:** скрипт-аналитик в `Скрипты/` (только чтение): конфиг клиента `site_map.yaml` (страница → роль → ключевые блоки → события), отчёт срез «страница × источник» + вывод по таблице выше.

## Открытые вопросы
- Есть ли у каждого клиента доступ к GA4/Метрике, куда пишет сервисный аккаунт (подтверждено только ProfiMet).
- Какие сайты на Tilda (событие видимости блока делается через GTM, нужны id блоков `.t-rec`).
- Влияние установки Clarity на скорость и согласие cookies — по законам гео клиента.

## Пример: Landver, tilda-страница car+truck (2026-10-15)
- Факт (проверено браузером 15.10, страница с ?utm_source=google&gclid=TEST): на странице GTM-KVLHDKJJ, GA4 G-JPLC4Q41PS, Ringostat, пиксель OpenAI; в dataLayer только gtm.js/dom/load/scrollDepth; **Microsoft Clarity не загружается** — данных Clarity по этой странице нет. GTM и GA4 Landver сервисному аккаунту недоступны.
- Опыт пользователя (2026-10-15, по работе с другими сайтами): Clarity работает плохо как источник данных для анализа — на него не опираться, основной источник — свои события в GA4.
- Почему свои события, а не Clarity: Clarity не знает gclid/ключ клика и плохо выгружается; свои события в GA4 с gclid соединяются с Ads через `click_view` (`Скрипты/gads_click_view_by_gclid.py`) → «ключ → поведение → заявка».
- Что GA4 уже собирает сам (проверено браузером 15.10, G-JPLC4Q41PS): `page_view`, `scroll` (одна отметка 90%), `form_start` (улучшенная статистика срабатывает на формах Tilda при фокусе поля); клик по `tel:` уходит как `click_tel` (тег GA4 - click_tel в GTM-KVLHDKJJ, триггер «Click URL содержит tel:»; перепроверено 15.10 — первая запись «не уходит» была ошибкой теста: я кликал по скрытой ссылке мобильной плашки). Отправку формы не проверяли (фальшивая заявка); в контейнере есть тег GA4 - form_submit (триггер customEvent submit_form). Перед планом событий для любого клиента сначала снимать, что уже уходит (скрипт-проверка браузером), — подсказка пользователя.
- Набор событий (добавить через GTM): `phone_click` (+ место номера), `form_submit` (если нет), `block_view` по id блоков Tilda (`#ldv-reviews`, `#ldv-case-process`, `#ldv-final-review`, `#ldv-faq`, `#ldv-injuries`, `#ldv-truck-cases`, примеры дел/case value), `faq_open` (+ текст вопроса), `engaged_30s/90s` (вкладка активна), `email_click`. Параметры: utm_campaign + ValueTrack `{keyword}`, `{matchtype}`, `{adgroupid}` в настройке ссылок кампании.
- Ограничение: ~20–30 кликов в неделю → корреляция с заявками только на горизонте месяцев; ближняя польза — какие группы запросов уходят сразу или не доходят до формы. Точный поисковый запрос на уровне клика недоступен (только ключ; GA4 «Google Ads query» при связке — не проверено).
- Время по блокам (`block_time`, Landver 2026-10-15): блок = последний, чей верх выше середины экрана (на длинных блоках «виден» задваивает время); таймер стоит при скрытой вкладке и после 10 с без движения; отправка при смене блока, каждые 30 с и при уходе. Тестовый прогон на странице (десктоп 1280×720 и телефон 390×844): 5 с hero + 6 с case_value + 15 с простоя на FAQ → 5/6/10 (простой ограничен 10 с) — работает. Скрипт — `Клиенты/Andverpersonalinjury/Трекинг/gtm_block_time.js`. Это время на экране, не доказательство прочтения; средние по блоку надёжны от нескольких десятков визитов.
- Реализовано на Landver 2026-10-15 (GTM-KVLHDKJJ, версия 6; [[../../Клиенты/Andverpersonalinjury/Журнал_изменений]] И-048/И-049): block_view по 17 блокам, block_time, stay_10s/engaged_30s/engaged_90s по активному времени, faq_open, email_click, click_tel + click_place, Clarity отдельным проектом. GA4 при связи с Google Ads отдаёт кампанию/группу/ключ по сессии (`sessionGoogleAdsCampaignName`, `...AdGroupName`, `...Keyword`; проверено Data API) — суффиксы ссылок для GA4 не нужны. Первый срез — после накопления визитов (~25 кликов в неделю).
