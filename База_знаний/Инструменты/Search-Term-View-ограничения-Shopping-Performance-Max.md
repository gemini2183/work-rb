# search_term_view — ограничения для Shopping и Performance Max

## Проверенный факт №1: keyword-поля в SELECT молча обнуляют Shopping-строки

`search_term_view` в принципе отдаёт данные по Shopping-кампаниям (таргетинг по
товарному фиду, без ключевых слов) — это не то же самое, что "Shopping вообще
не поддерживается". Но если в GAQL-запросе к `search_term_view` в `SELECT`
одновременно с `search_term_view.search_term` присутствуют поля
`segments.keyword.info.text` и/или `segments.keyword.info.match_type`, то
**все строки Shopping-кампаний исчезают из ответа целиком**, без ошибки и без
предупреждения — просто 0 строк по этим кампаниям, будто там нет данных.

Проверено эмпирически: один и тот же запрос (тот же customer_id, тот же
период) к кампании `Merchant_Shopping` дал:
- **13 848 строк** — без `segments.keyword.info.*` в SELECT
- **0 строк** — с этими полями в SELECT

Причина — Shopping-таргетинг не привязан к ключевому слову, а `segments.keyword`
— обязательный сегмент, требующий непустого значения для попадания строки в
выборку; для Search-кампаний (где ключевые слова есть) те же поля работают
нормально и строки не пропадают.

## Проверенный факт №2: Performance Max не отдаёт search_term_view вообще

Для кампаний `advertising_channel_type = PERFORMANCE_MAX` ресурс
`search_term_view` возвращает 0 строк независимо от состава SELECT — это
задокументированное ограничение API, не связанное с фактом №1. Поисковые
запросы по PMax доступны только через раздел "Insights" в веб-интерфейсе
Google Ads, программного доступа к ним через отчётный API нет.

## Проверенный факт №3: даже без бага из факта №1, search_term_view для Shopping покрывает не весь трафик кампании

Проверено эмпирически 2026-09-08 на кампании `Merchant_Shopping` (Корогва,
customer_id 845-234-6433), период 2026-09-01→07, БЕЗ полей `segments.keyword.info.*`
в SELECT (т.е. без бага из факта №1 — строки не обнулены):

- **Campaign-level агрегат** (`gads_campaigns_breakdown.py`, запрос к ресурсу
  `campaign`): 767 кликов, 10 018,92 расхода, 4 конверсии.
- **Тот же период, `--search-terms`** (запрос к `search_term_view`): сумма по
  всем 6381 строкам — 330 кликов, 5072,39 расхода, 1 конверсия.

Расхождение — примерно в 2 раза по кликам/расходу и в 4 раза по конверсиям
(3 из 4 конверсий "потерялись"). Не связано с фактом №1 (лишних keyword-полей
в запросе не было) и не является обрезкой на уровне скрипта (запрос идёт без
LIMIT, полным стримингом). Похоже на частичную версию ограничения из факта
№2: `search_term_view` для Shopping физически не в состоянии сопоставить
часть кликов/показов (по товарным атрибутам фида) ни с одним текстовым
search term и молча пропускает эти строки — не 0% покрытия, как у PMax, но
и не 100%.

**Практическое следствие**: `search_term_view` по Shopping-кампаниям годится
для качественного разбора (какие темы запросов вообще есть, где явно
нецелевой трафик) — но НЕЛЬЗЯ использовать суммы по нему как факт о полном
объёме кликов/расхода/конверсий кампании. Для количественных выводов
("сколько потратили", "сколько конверсий") — всегда брать campaign-level
агрегат (`gads_campaigns_breakdown.py` без `--search-terms`, или
`gads_stats_korogva.py`), а `--search-terms` использовать только для
качественного среза "по каким запросам вообще есть трафик", с явной оговоркой
о неполном покрытии при любом сравнении цифр.

## Проверенный факт №4: asset_group_signal не отдаёт метрики вообще (список сигналов — да, статистику по ним — нет)

Ресурс `asset_group_signal` (список сигналов аудитории/поисковых тем, заданных
вручную в Asset Group PMax-кампании — `search_theme.text`, `audience.audience`)
можно запросить сам по себе (список тем/аудиторий приходит нормально), но
**нельзя** добавить к нему `metrics.clicks`/`metrics.cost_micros`/
`metrics.conversions` — API прямо отвергает такой запрос
(`PROHIBITED_METRIC_IN_SELECT_OR_WHERE_CLAUSE`, "could not support requested
resources: ASSET_GROUP_SIGNAL"). Проверено эмпирически 2026-09-09, Корогва,
кампания `Merchant_Performance Max-1`.

**Практическое следствие**: можно узнать, ЧТО задано как search theme/аудитория
в конкретной Asset Group (например, найти тему вроде "прапор зсу", ранее
explicitly отклонённую клиентом в контексте Search-семантики — см.
[[../../Клиенты/Корогва/Семантика/semantics|Семантика/semantics]] раздел
"Отклонено пользователем"), но НЕЛЬЗЯ узнать через API, сколько конкретно
кликов/расхода/конверсий пришло именно по этому сигналу — метрики доступны
только на уровне всей Asset Group целиком (`gads_pmax_asset_groups.py`), не по
отдельному сигналу внутри неё.

**ВАЖНО — что такое search theme на самом деле (проверено через официальную
справку Google 2026-09-09, до этого ошибочно интерпретировано как таргетинг)**:
search theme — это НЕ ключевое слово и не жёсткий таргетинг, а мягкая
подсказка-намёк алгоритму ("directional hint", "mere suggestion" — формулировки
самого Google). PMax не обязан показываться именно по этой фразе, может
расширяться на смежные запросы по своему усмотрению и приоритизирует то, что
реально конвертит. Присутствие нерелевантной темы в списке сигналов — повод
почистить настройку из гигиенических соображений, но НЕ доказательство, что
реклама реально показывалась по этой теме, и тем более не автоматическая
причина каких-либо проблем с конверсией — не выдавать такую находку за
объяснение метрик кампании без отдельного подтверждения.

## Проверенный факт №5: shopping_performance_view и asset_group несовместимы в одном запросе

Нельзя запросить `asset_group.name` вместе с товарными полями
(`segments.product_item_id`/`product_title` и т.п.) из `shopping_performance_view`
— API прямо отклоняет: `PROHIBITED_RESOURCE_TYPE_IN_SELECT_CLAUSE`, "Cannot
select fields from the following resource: 'ASSET_GROUP', since the resource
is incompatible with the resource in FROM clause". Проверено эмпирически
2026-09-09, Корогва, `Merchant_Performance Max-1`.

**Практическое следствие**: невозможно узнать через API, КАКИЕ конкретно товары
показывались через какую именно Asset Group внутри PMax-кампании. Если найден
проблемный Asset Group (например, через `gads_pmax_asset_groups.py`, сравнение
метрик группы до/после точки разлома) — нельзя углубиться до товарного уровня
внутри этой же группы средствами API. Доступные действия на этом уровне
детализации: (1) весь товарный разрез кампании целиком, без привязки к группе
(`shopping_performance_view` без asset_group), (2) метрики по asset group
целиком, без привязки к товару (`gads_pmax_asset_groups.py`). Смешать эти два
среза нельзя — это архитектурное ограничение PMax-отчётности, не пробел
скрипта.

## Проверенный факт №6: демография (пол/возраст) недоступна для PMax через API, доступна для Shopping и Search

`gender_view`/`age_range_view` требуют `ad_group_criterion`, которого у PMax
нет (у PMax есть Asset Group, не Ad Group) — это задокументированное
ограничение (подтверждено WebSearch, groups.google.com/adwords-api). С апреля
2026 Google добавил в веб-интерфейс отчёт по демографии для PMax ("audience
report"), но это не проявилось в API ресурсе `campaign_audience_view` для
нашего аккаунта — проверено эмпирически 2026-09-09, Корогва: запрос к
`campaign_audience_view` (правильные поля — `campaign_criterion.gender.type`/
`campaign_criterion.age_range.type`, НЕ `ad_group_criterion.*` — тот сразу даёт
`PROHIBITED_RESOURCE_TYPE_IN_SELECT_CLAUSE`) без фильтра по кампании вернул
данные по всем Search-кампаниям аккаунта И по `Merchant_Shopping`
(`advertising_channel_type=4`, SHOPPING) — но НИ ОДНОЙ строки по
`Merchant_Performance Max-1` (`advertising_channel_type=10`).

**Практическое следствие**: для Shopping и Search — демографический разрез
(пол/возраст) через `campaign_audience_view` доступен и стоит использовать
при аудите. Для PMax — недоступен на практике даже там, где веб-интерфейс
теоретически может показывать что-то похожее; не тратить время на повторную
попытку без явного новго сигнала, что Google это включил для конкретного
аккаунта (проверять эмпирически заново, не полагаться на дату "обновление
было анонсировано в апреле 2026" как доказательство доступности сейчас).

## Как распознать на практике

- Кампания `advertising_channel_type` = `SHOPPING` (4) и в запросе к
  `search_term_view` есть `segments.keyword.info.*` → подозревать факт №1,
  убрать эти поля и перепроверить.
- Кампания `advertising_channel_type` = `PERFORMANCE_MAX` (10) и
  `search_term_view` пуст независимо от полей → факт №2, это ограничение API,
  не чинится.
- `campaign.advertising_channel_type` и `advertising_channel_sub_type` удобно
  проверить отдельным запросом к ресурсу `campaign`, если непонятно, с каким
  типом кампании имеем дело.

## Что делать

- Не включать `segments.keyword.info.*` в запросы `search_term_view`, если
  среди кампаний могут быть Shopping — использовать только
  `campaign.name`/`ad_group.name`/`search_term_view.search_term` + метрики.
- Если нужно сопоставление поискового запроса с загруженным ключевым словом —
  делать отдельным шагом на своей стороне (сравнение текста запроса со списком
  ключей из `keyword_view`), не одним комбинированным GAQL-запросом.
- Для PMax-кампаний не пытаться получить поисковые запросы через API — явно
  проговаривать пользователю, что это ограничение Google, а не отсутствие
  данных или брак нашего скрипта.
