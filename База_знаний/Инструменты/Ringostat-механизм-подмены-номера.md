# Ringostat: механизм подмены номера

Найдено и проверено на практике при разработке `Скрипты/phone_swap_check.py` и
настройке коллтрекинга клиентов [[../Andverpersonalinjury/index|Andverpersonalinjury]]
(landverpersonalinjury.com), [[../ProfiMet/index|ProfiMet]] (mocnaszklarnia.pl)
и [[../../Клиенты/SED Латвия/index|SED Латвия]] (darza-siltumnica.lv). Общее
знание о том, как работает Ringostat — не специфично для одного клиента.

## Как задаётся правило подмены

В кабинете Ringostat, раздел "Каналы трафика" + "XPaths" + "Пулы номеров":

1. **Канал трафика** — условие по UTM (`utm_source`/`utm_medium`/`utm_term`/
   `utm_content`/`utm_campaign`), можно использовать `.*` как "любое значение".
   Пример: канал "Google Ads" = `utm_medium: cpc` (source/term/content/campaign
   — любые).
2. **Пул номеров** — список телефонных номеров, привязанный к каналу. При
   срабатывании канала Ringostat выдаёt посетителю **один номер ИЗ ПУЛА**, не
   обязательно один и тот же при каждом заходе — похоже на ротацию по
   сессии, не строгое отображение "1 UTM-комбинация = 1 фиксированный номер"
   (подтверждено эмпирически: два прогона с идентичным `utm_source=google&
   utm_medium=cpc` дали разные номера одного и того же пула — `+18883783267`
   и `+18883025461`, оба валидны для этого канала).
3. **XPath-правило** — где именно на странице искать элемент с номером,
   чтобы его подменить. Задаётся либо через упрощённый конструктор (выбор
   "Class"/"Text"/"Id" — Ringostat сам собирает XPath по одному атрибуту),
   либо через **"Manual mode"** — единственный режим, куда можно вставить
   произвольный составной XPath (с `and`/`not`/`contains` и т.п.).
4. **Маска** — шаблон вида `(###) #-LAWINJURY (######)`, где `#` — цифра,
   остальное — фиксированный буквенный/пунктуационный текст.

## Маска должна описывать ВЕСЬ текст элемента, не только номер

Подмена всегда заменяет **весь textContent найденного по XPath узла**, а не
вырезает и заменяет подстроку внутри существующего текста. Отсюда следует
не "point-replace невозможен", а обратное — **маска должна описывать текст
элемента целиком**, включая всё, что должно остаться неизменным, а не
только фрагмент с номером.

Первая попытка на hero-тексте landverpersonalinjury.com (короткая маска
`(###) #-LAWINJURY (######)`, только под сам номер, при XPath на весь
`<span>` с предложением) стёрла весь остальной текст, оставив только голый
номер — потому что Ringostat заменил весь textContent найденного узла на то,
что попало под маску, а остальной текст в маску просто не был включён.

**Рабочее решение** — задать маску как полный текст узла, с `###` только на
месте цифр номера, весь остальной текст — 1:1 как в оригинале (включая
пунктуацию и НЕ ASCII-символы вроде типографского апострофа `’`, не обычного
`'` — Playwright/DevTools нужно использовать, чтобы получить точный текст
узла, набор вручную рискует подставить не тот символ и сорвать совпадение).
Пример реального рабочего правила из кабинета клиента ("our office",
адресный блок офиса Beverly Hills — маска включает полный адрес +
"Phone: " + номер-шаблон, не только номер) подтверждает, что это штатный,
предусмотренный Ringostat способ, не костыль.

Проверено эмпирически на hero-тексте LA-страницы: маска
`Harmed in Los Angeles? Landver Law’s tenacious personal injury attorneys
pursue top compensation for injured residents across Los Angeles. You pay
nothing unless we recover. Call (###) ###-#### for a free consultation
today.` (без буквенного "LAWINJURY" — см. следующий раздел, почему его
намеренно убрали именно в этом правиле) при том же XPath, что и раньше,
подставила номер точечно, сохранив весь остальной текст предложения.

Значит **не требуется** править вёрстку/контент сайта, чтобы получить
точечную замену внутри длинного текста — правки на стороне Ringostat
(правильно составленная full-text маска) достаточно.

## Отсутствие публичного API для пулов и правил подмены

Проверено 2026-08-18 (документация help.ringostat.com, ringostat.readme.io):
у Ringostat есть публичный API для call log, сотрудников, webhooks — но
**нет** эндпоинта для выгрузки пулов номеров или правил подмены (Traffic
Channels / Insertion settings / XPaths). Это только UI кабинета.

Следствие: пул номеров и условия подмены для автоматической проверки
(`Скрипты/phone_swap_check.py`) приходится вести **вручную** по скриншотам
кабинета — нет единого источника правды между Ringostat и вики, нужно
актуализировать при каждом изменении настроек в кабинете.

## Vanity-номера: буквенная фраза в номере может не иметь смысла для всех номеров пула

Основной ("дефолтный") номер клиента часто подбирается как vanity number —
номер, чьи цифры соответствуют запоминающемуся слову на буквенной телефонной
клавиатуре (2=ABC, 3=DEF, 4=GHI, 5=JKL, 6=MNO, 7=PQRS, 8=TUV, 9=WXYZ).
Пример: `844-452-9465` кодирует `LAWINJURY` (буквы L,A,W,I,N,J,U,R,Y →
5,2,9,4,6,5,8,7,9 → `529465 87 9`, первые 6 цифр после кода города и "4"
совпадают со словом).

**Важно:** маска в Ringostat (`(###) #-LAWINJURY (######)`) отображает
фиксированный буквенный текст "LAWINJURY" **поверх любого номера пула**,
даже если реальные цифры этого конкретного номера с этими буквами вообще не
связаны. Проверено: номера пула "Google Ads" (`8883783267`, `8883448725`,
`8883025461`) с "LAWINJURY" буквенно не совпадают — маска просто рисует
единый брендовый лейбл поверх разных номеров ради визуальной консистентности
с оригинальным vanity-номером.

**Потенциальный риск для UX:** для посетителя, кликающего по номеру (мобильный
или ПК с обработчиком `tel:`), это не проблема — реальные цифры уходят по
`href`, буквы посетитель не набирает. Но для посетителя, читающего номер с
экрана ПК и переписывающего его вручную (записать, продиктовать, ввести в
другое устройство без автоперехода по `tel:`) — текст вида "(888)
3-LAWINJURY (025461)" может запутать: неочевидно, что "3-LAWINJURY" —
это тоже цифры (первая часть номера через буквы), а "(025461)" — оставшиеся
цифры открытым текстом. Смешение двух форматов в одной строке для человека,
не знакомого с логикой vanity-номеров, читается как два разных куска
контактной информации, а не один номер. Не проверено на реальных
конверсиях/жалобах — зафиксировано как наблюдение/риск, не как
подтверждённая проблема.

## Icon-only кнопки звонка (номер без текста) и XPath для inline-SVG

Найдено на [[../../Клиенты/ProfiMet/index|ProfiMet]] (mocnaszklarnia.pl,
2026-09-01), при разработке `Скрипты/phone_xpath_discovery.py`: не любой
`<a href="tel:...">` на странице содержит видимый текст номера. Частый
паттерн для мобильной вёрстки и соцссылок — кнопка-иконка без текста
(`<a href="tel:..."><img></a>` или `<a href="tel:..."><svg>...</svg></a>`),
где номер существует только в атрибуте `href`.

Если на такой элемент завести обычное XPath-правило с текстовой маской
(full-replace, см. предыдущий раздел) — Ringostat заменяет всё содержимое
элемента целиком: иконка (`<img>`/`<svg>`) пропадает совсем, а на её месте
остаётся только голый текст с цифрами номера. Визуально было "аккуратная
иконка без текста" — становится "иконки нет, вместо неё коряво торчащий
текст номера". Отличить такой узел от обычного текстового можно заранее —
по отсутствию видимого текста / наличию `<img>`/`<svg>` внутри.

**Решение, ПОДТВЕРЖДЕНО НА ПРАКТИКЕ (2026-09-01, после двух неудачных
попыток и уточнения у поддержки Ringostat): маска может содержать
произвольный HTML, включая плейсхолдер номера `<t>` внутри атрибута — но
только если номер ТАКЖЕ продублирован текстом в скрытом `<span>` внутри
той же маски.**

Первые две попытки (маска = `<a href="tel:<t>"><img .../></a>`, плейсхолдер
только в href, без текстового дубля) на практике проваливались — Ringostat
игнорировал HTML-структуру маски и вставлял голый текст номера вместо неё,
`<img>` пропадал (см. предыдущие попытки в
`Клиенты/ProfiMet/Решения.md`, 2026-09-01). Рабочий вариант, который в
итоге применила сама поддержка Ringostat (не мы, инженер поддержки внёс
правку в кабинет напрямую) — маска с ДВОЙНОЙ подстановкой номера: один раз
в `href` через `<t>`, второй раз текстом внутри `<span
style="display:none;">` через плейсхолдер `+###########`:

    XPath:
    //div[@data-elem-type='image'][.//a[contains(@href,'tel:')]]//a[contains(@class,'tn-atom')]

    Маска:
    <a class="tn-atom" href="tel:<t>" style="transform-origin: center center;"><span style="display:none;">+###########</span><img class="tn-atom__img t-img loaded" src=".../mob_phone.svg" alt=""></a>

Подтверждено эмпирически (Playwright, ProfiMet, mocnaszklarnia.pl): в
результате в DOM реально появляется `<a href="tel:ПОДМЕНЁННЫЙ_НОМЕР">` с
рабочим кликом, иконка (`<img>`) остаётся на месте, текст номера скрыт
(`display:none`) — визуально ничего не портится.

**Вывод: одиночный `<t>` внутри атрибута БЕЗ текстового дубля номера в
маске — судя по всему, не срабатывает** (или срабатывает не всегда/не на
всех инсталляциях — проверено только на этом одном случае неудачи).
Рабочая формула — не просто "HTML в маске работает", а конкретно "маска
должна содержать И плейсхолдер в атрибуте (`<t>`), И такой же плейсхолдер
текстом где-то внутри узла (`###...`), пусть даже спрятанный
`display:none`". Возможная причина (не проверено, гипотеза): у Ringostat
может быть внутренняя логика "нашёл ли я хоть один текстовый плейсхолдер в
маске — если нет, откатываюсь к старому поведению full-replace
textContent". Не подтверждено официально, не спрашивали у поддержки
именно это.

Значит full-replace textContent (см. раздел выше про длинные тексты) —
не единственный режим работы маски, но HTML-режим требует обязательного
текстового плейсхолдера где-то в маске, не работает с одним лишь
атрибутным `<t>`.

**Известный сопутствующий баг (не устранён, не критичен):** XPath выше
самодублируется — маска создаёt вложенный `<a>` внутри `<a>` (невалидный
HTML), и тот же XPath на следующем прогоне находит совпадение уже на этом
вложенном узле, оборачивая ещё раз. См.
`Клиенты/ProfiMet/Решения.md`, 2026-09-01, для найденного (но пока не
применённого) исправления — добавить в XPath `and not(.//span[contains(
@style,'display:none')])`, чтобы исключить уже обработанные узлы.

**Настоящая первопричина, ПОДТВЕРЖДЕНО НА ПРАКТИКЕ (Andverpersonalinjury,
2026-09-04) — маска вставляется как innerHTML в НАЙДЕННЫЙ узел, а не
заменяет его outerHTML целиком.** Если маска сама начинается с полного
тега `<a href="tel:<t>">...`, а XPath уже нашёл `<a>`-узел — Ringostat
оборачивает найденный `<a>` ещё одним `<a>` изнутри, отсюда вложенность
(визуально — "кнопка меньшего размера наложена на большую").

**Рабочее решение, подтверждено эмпирически:** если XPath уже указывает на
сам `<a>` (не на его родителя), маску нужно писать БЕЗ внешнего `<a>...>` —
только его содержимое (иконка + текстовый плейсхолдер, включая скрытый
`<span style="display:none">` для номера, если видимого текста номера в
оригинале не было). `href` на самом найденном узле Ringostat подставляет
отдельным встроенным механизмом (раз узел найден именно как
`<a href="tel:...">`), не через `<t>` в маске — `<t>` в атрибуте нужен
ТОЛЬКО когда маска действительно заново создаёт обёртку `<a>` (например,
XPath указывает на родителя/контейнер, а не на сам `<a>` — тогда маска
обязана сама создать `<a href="tel:<t>">`, вложенности не будет, потому что
такого `<a>` в найденном узле изначально не было).

**Правило выбора:** если найденный по XPath узел САМ ЯВЛЯЕТСЯ `<a href=
"tel:...">` — маска = только innerHTML, без `<t>`. Если найденный узел —
контейнер/родитель, внутри которого `<a>` создаётся заново — маска включает
полный `<a href="tel:<t>">`. Раздел выше про ProfiMet (`tn-atom`) — пример
второго случая, XPath там указывал на `<a class='tn-atom'>` — тоже сам
`<a>`, но там сработало и с `<t>` внутри маски; возможное отличие — версия/
конфигурация конкретной инсталляции Ringostat, либо неточность в
воспроизведении кейса ProfiMet задним числом. Если в новом случае
innerHTML-only не сработает — резервный путь: вернуть `<a>` в маску и
добавить в XPath `and not(.//span[contains(@style,'display:none')])`
(способ выше), чтобы исключить уже обработанные вложенные узлы.

Практическое следствие: XPath для icon-only элемента не обязательно
привязывать к конкретной DOM-копии блока (fixed/sticky vs обычная — см.
следующий раздел) — можно взять widely-matching XPath по узнаваемому
признаку самой иконки (класс + имя файла в `src`), если задача — подменять
номер одинаково во ВСЕХ местах показа этой иконки на странице разом (так и
сделано на ProfiMet: одна и та же icon-only кнопка встречается в обычном
хедере, sticky-копии и блоке соцссылок одновременно — проверено
`Скрипты/phone_xpath_discovery.py` — и клиент подтвердил, что везде должен
показываться один и тот же номер за один визит).

Проверено, что блок формы "Кнопка выдачи номеров Call me" (HTML-код +
чекбоксы для мобильных/всех устройств) к этой задаче отношения НЕ имеет —
это отдельная функция экономии номеров пула при нехватке (показывает кнопку
"узнать номер", когда одновременных посетителей больше, чем свободных
номеров), не связана с подменой в icon-only элементах — не путать.

**Важный технический нюанс XPath 1.0**, всплывший при попытке составить
правило для inline-`<svg>`-иконки: голый шаг `svg` в XPath-выражении
(например, `a[svg]`) **никогда не совпадает** с реальным `<svg>`-элементом.
Причина — `<svg>` живёт в отдельном XML-namespace
(`http://www.w3.org/2000/svg`), а безымянный шаг в XPath 1.0 ищет элемент
БЕЗ namespace. При этом браузерный `querySelector('svg')` в JS находит
такой элемент без проблем — JS не требует явного совпадения namespace,
поэтому расхождение легко не заметить, если проверять структуру через
DevTools/JS, а потом составлять XPath вручную. Проверено эмпирически:
`//a[svg]` дал 0 совпадений на реальном инлайн-`<svg>` внутри соцссылки-
телефона ProfiMet, при этом `//a[*[local-name()="svg"]]` находит его
корректно. **Обход — везде использовать `*[local-name()="svg"]` вместо
голого `svg`** в любом составном XPath, где нужно проверить наличие
SVG-потомка. Это ограничение самого языка XPath 1.0, а не Playwright —
значит правило с голым `svg` не заработает и в движке XPath кабинета
Ringostat, если у клиента иконка реализована как inline-SVG (а не `<img>`
со ссылкой на файл `.svg`, что namespace-проблемы не имеет, т.к. `<img>` —
обычный HTML-элемент).

## Sticky-хедер на Tilda — отдельный DOM-узел, свой XPath (и класс должен существовать ДО скролла)

Найдено на [[../../Клиенты/ProfiMet/index|ProfiMet]] (mocnaszklarnia.pl,
2026-09-01): сайт сделан на Tilda, XPath-правило было задано по хедеру
начального экрана, но подмена не срабатывала именно в **sticky-хедере**,
который появляется при скролле вниз.

Причина — архитектура Tilda: блок хедера (`.t396`) рендерится **двумя
параллельными DOM-копиями** одного и того же контента — обычной, в потоке
документа, и sticky-копией (`position: fixed` при активации), которую Tilda
показывает поверх контента только во время скролла. Это не один и тот же
узел, который меняет позицию через CSS — это буквально второе поддерево
DOM с собственным набором дочерних элементов и собственной
`<a href="tel:...">`. XPath, ведущий к номеру в обычной копии, физически не
совпадает ни с одним узлом в sticky-копии — отсюда и несрабатывание маски
именно при скролле.

Решение — задать **второе** правило подмены (второй XPath) специально для
sticky-копии, по классу, а не по числовым индексам div (индексы уезжают при
правках вёрстки в редакторе Tilda).

**ВАЖНАЯ ПОПРАВКА (изначально найденный XPath оказался НЕРАБОЧИМ на
практике, несмотря на структурно верный DOM-анализ):** первая версия
использовала класс `t396__artboard-fixed-active`:

    //div[contains(@class,"t396__artboard-fixed-active")]//a[starts-with(@href,"tel:")]

Этот XPath корректно находит нужный элемент в Playwright/DevTools **ПОСЛЕ**
скролла — но не работал в реальном кабинете Ringostat вообще, стабильно и
воспроизводимо. Причина: `t396__artboard-fixed-active` — не статический
атрибут узла, а класс, который Tilda **добавляет динамически JS-кодом
только в момент скролла**. Сразу после загрузки страницы (`networkidle`,
до любого скролла) этого класса нет НИ У ОДНОГО элемента на странице —
у той же самой sticky-копии в этот момент класс —
`t396__artboard rendered t396__artboard-fixed-no-bg` (без `-active`).
Ringostat выполняет подмену сканированием DOM **в момент загрузки
страницы**, а не при скролле пользователя — то есть его XPath-движок ищет
совпадения ДО того, как класс `-active` вообще появляется. Отсюда 100%
воспроизводимое "не работает", которое легко спутать со случайным багом,
если проверять DOM только через Playwright/DevTools ПОСЛЕ скролла (там всё
выглядит правильно) и не думать про момент времени, когда именно
скрипт коллтрекинга делает свой проход.

Сам DOM-узел (артборд, `<a>` с `tel:`) при этом существует в разметке с
самого начала — Tilda не создаёт sticky-копию заново при скролле, а
переключает CSS-класс на уже существующем узле. Значит рабочее решение —
не «класс, который появляется при скролле», а класс, присутствующий на
этом же узле **уже в момент загрузки страницы**. На ProfiMet такой класс —
`t396__artboard-fixed-no-bg` (может отличаться по конкретному имени на
других инсталляциях Tilda, сама механика — общая):

    //div[contains(@class,"t396__artboard-fixed-no-bg")]//a[starts-with(@href,"tel:") and not(*)]

Подтверждено эмпирически: `document.querySelectorAll('.t396__artboard-fixed-no-bg')`
даёт 1 совпадение сразу после `networkidle`, до какого-либо скролла —
в отличие от `-fixed-active`, которое даёт 0 в этот момент.

**Общий вывод для будущих клиентов на Tilda (и любых конструкторов с
похожей sticky-архитектурой) — ДВЕ отдельные вещи, легко перепутать:**
1. Если XPath-правило заведено по хедеру, но подмена не работает именно
   при скролле (в статике на верхнем экране — работает) — искать вторую
   DOM-копию блока (sticky), заводить для неё отдельное правило.
2. **При составлении XPath для sticky-копии — не полагаться на класс,
   который сам DevTools/Playwright показывает ТОЛЬКО после скролла.**
   Разведку нужно делать в двух временных точках: сразу после
   `networkidle` (то, что видит скрипт подмены при сканировании) И после
   скролла (то, что видно глазом). Если класс есть только во второй точке
   — он бесполезен для XPath-правила коллтрекинга, нужен класс,
   присутствующий уже в первой. `Скрипты/phone_xpath_discovery.py` при
   следующей доработке стоит научить различать эти два состояния явно —
   на момент 2026-09-01 он этого не делает.

## Desktop и mobile — это ОДИН HTML-код, разница только в CSS-видимости

Найдено на [[../../Клиенты/ProfiMet/index|ProfiMet]] (mocnaszklarnia.pl,
2026-09-01): после настройки хедера клиент заметил, что часть текстовых
номеров в теле страницы (не хедер) не подменяется именно на мобильном —
хотя на desktop те же самые номера уже подменялись.

Проверено Playwright (одинаковый XPath на обоих viewport): **элементы,
которых "не хватает" на мобильном, физически существуют в HTML-коде
страницы и на mobile тоже** — Tilda просто ПРЯЧЕТ их от глаза через CSS на
узком экране (у скрытого элемента `is_visible() == False`, но узел при
этом в DOM есть, `getComputedStyle` показывает не `display:none`, а другой
механизм скрытия через родителя/media query). Один и тот же XPath дал
ОДИНАКОВОЕ количество совпадений на desktop и mobile (5 из 5) — то есть
разметка идентична, разница только в видимости для человека.

**Важное следствие:** Ringostat подменяет номер по XPath независимо от
того, видим элемент человеку или нет — он сканирует HTML-код, не
рендеринг. Значит "номер не виден на мобильном экране" и "номер не
покрыт правилом подмены" — НЕ одно и то же, и решение категории
"desktop работает, mobile — нет" не обязательно означает разную
разметку/разные копии блока (как было в случае со sticky-хедером выше) —
может быть и один и тот же узел, просто не покрытый ни одним правилом
вообще, случайно оставшийся "невидимым" и для человека, и для
XPath-правил одновременно.

**Практический вывод:** при разведке сайта на предмет непокрытых мест —
не ограничиваться визуальным осмотром страницы в нужном viewport (что
видно глазом), а явно искать ВСЕ `a[href^="tel:"]` в DOM, включая скрытые
через CSS — именно так нашлись 3 текстовых номера в контентных блоках и
футере, которые визуально на мобильном экране не заметны сразу (спрятаны
или экран нужно долго скроллить), но существуют в коде и требуют
собственного правила.

## Текстовые номера без общего смыслового класса — фильтр по структуре, не по классу

Продолжение находки выше: 4 непокрытых текстовых узла (скрытый desktop-
текст хедера + 2 CTA-блока в контенте + номер в футере) не имели между
собой ни одного общего "смыслового" класса — только хрупкие
автосгенерированные числовые id Tilda (`tn-elem__29060745...` и т.п.,
разные у каждого блока). Заводить под каждый отдельное хрупкое правило
избыточно, когда есть общий **структурный** признак.

Найденный признак: все 4 узла — это `<a href="tel:...">ТЕКСТ</a>` без
атрибута `class` вообще (`style="color: inherit"`, но не `class`) и без
дочерних элементов. Это отличает их и от icon-only кнопок (`class="tn-
atom"`, есть `<img>`/`<svg>` внутри), и от уже покрытых sticky-элементов
(тоже без класса, но это не мешает — правило просто продублирует уже
корректный результат на них).

    XPath:
    //a[starts-with(@href,"tel:") and not(@class) and not(*)]

Проверено — находит одинаковое количество элементов на desktop и mobile
(см. раздел выше, один и тот же HTML-код), значит правило одно и то же
для обоих viewport, заводить раздельно не нужно.

**Общий метод для будущих клиентов:** когда несколько непокрытых мест не
имеют общего смыслового класса — искать общий структурный признак самого
узла (наличие/отсутствие `class`, наличие/отсутствие дочерних элементов,
`not(*)`) вместо class-based фильтра. Часто эффективнее и устойчивее
единого хрупкого id.

## ГЕО-группа "not set" — тихая причина, почему правильно составленный XPath не подменяет номер

Найдено на [[../../Клиенты/SED Латвия/index|SED Латвия]] (darza-siltumnica.lv,
2026-09-01): XPath-правило технически корректно (найден через
`document.evaluate`-перехват на живой странице — 2 совпадения, без ошибок
выполнения), сервер Ringostat при этом отдавал номер для ВСЕХ ОСТАЛЬНЫХ
правил проекта, но именно это правило получало пустую строку `""` вместо
номера в ответе `analytics.ringostat.net/changed_number/`.

Причина — в кабинете, в форме редактирования правила, поле **"ГЕО группа"**
стояло на значении **`not set`**, тогда как у всех остальных (рабочих) правил
того же проекта — `All`. Сервер, видимо, не может сопоставить правило ни с
одной ГЕО-группой и в итоге не выдаёт по нему номер вообще — без явной
ошибки в интерфейсе или логах, недоступных снаружи кабинета.

**Диагностика:** если XPath заведомо рабочий (проверено `document.evaluate`
в консоли/Playwright — находит нужные узлы, без исключений), а подмена всё
равно не появляется в реальном DOM — прежде чем чинить сам XPath, проверить
поле "ГЕО группа" в форме редактирования конкретного правила и сравнить с
остальными правилами того же проекта. Симптом неотличим на первый взгляд от
десятка других причин (хрупкий XPath, конфликт скриптов, кэш) — единственный
надёжный способ отличить именно эту причину — посмотреть прямой ответ
сервера `changed_number` (см. раздел ниже) и сверить, в каком списке
(с номером или без) оказался индекс интересующего правила.

**Практический метод диагностики через прямой ответ сервера:**
запрос `https://analytics.ringostat.net/changed_number/?r_h=<script_hash>&...`
(параметры видны в Network-панели браузера при загрузке страницы клиента)
возвращает JSON вида:

    {"numbers":{"37167660749":[0,3,4,...],"":[1,2,21]}, "numbers":true, ...}

Ключи верхнего уровня — номера пула (или пустая строка `""` для "номер не
назначен"), значения — массивы **индексов правил** в том порядке, в каком
они объявлены в конфиге клиентского скрипта (`ee.xpaths[N]`, см. следующий
раздел про извлечение конфигурации). Индекс интересующего правила в списке
`""` — точный признак проблемы именно на уровне сервера/ГЕО-группы, не XPath.

## Как извлечь полную конфигурацию XPath-правил проекта без доступа к кабинету

Найдено на том же кейсе: клиентский JS-скрипт Ringostat
(`https://script.ringostat.com/v4/<id>/<hash>.js`) содержит **весь конфиг
XPath-правил проекта захардкоженным прямо в код** как JSON внутри объекта
`ee` — ключ `"xpaths"`, массив объектов с полями `xPath`, `mask`, `geoGroup`,
`onlyForRegion`, `checkOnClient`, `callMeAll`, `reservedNumbersPercent`,
`callMeMobile`, `callMeHTML`.

Полезно, когда нет прямого доступа к кабинету клиента, но нужно понять,
что реально настроено (или для верификации, что правки в кабинете
применились и разошлись на скрипт): скачать JS по прямому URL (виден в
Network-панели браузера как первый сетевой запрос к `script.ringostat.com`),
найти substring `"xpaths":[`, распарсить как JSON (баланс скобок, так как
последний элемент может содержать `[`/`]` внутри длинных full-text масок).
Порядок элементов массива соответствует порядку индексов в ответе
`changed_number` (см. раздел выше) — можно однозначно сопоставить, какое
именно правило получает/не получает номер.

Отдельно полезно: файл содержит функцию `findElementsByXPath` (внутреннее
имя минифицировано, но сигнатура узнаваема — вызывает
`document.evaluate(xpath, ..., XPathResult.UNORDERED_NODE_SNAPSHOT_TYPE)`
и ловит исключения в try/catch с внутренним логированием, не видимым в
консоли браузера напрямую) и функцию маскирования (принимает `mask, number`,
проверяет наличие `#` в маске, посимвольно заменяет). Обе — стандартный общий
код сервиса, не специфичны для одного проекта, полезны для понимания
механики при глубокой диагностике.

## Конфликт с посторонним MutationObserver-скриптом на странице — синхронный откат, необнаружимый обычным polling

Найдено на [[../../Клиенты/SED Латвия/index|SED Латвия]] (2026-09-01):
подмена номера технически происходила (сервер отдаёт номер, XPath находит
элемент, `document.evaluate` без ошибок), но в реальном DOM после загрузки
всегда оставался статичный исходный номер — воспроизводимо и в headless
Playwright, и в браузере пользователя (не проблема тестовой среды).

Причина — на странице клиента был установлен посторонний (не связанный с
Ringostat) inline-скрипт с `MutationObserver`, наблюдающий
`document.documentElement` (`subtree: true`, `attributeFilter: ['href']`) и
откатывающий ЛЮБОЕ изменение `href` у `a[href^="tel:"]` обратно на
захардкоженный "правильный" номер. Скрипт был поставлен ранее (не в рамках
работы с Ringostat) для исправления опечатки в номере телефона в вёрстке
сайта — благая цель, но побочный эффект: он одинаково откатывает и "плохую"
опечатку, и "хорошую" подмену коллтрекинга, потому что видит только факт
изменения атрибута, не смысл.

**Диагностический признак, отличающий этот случай от прочих причин
несрабатывания:** откат происходит СИНХРОННО, в том же тике event loop, что
и изменение — polling `href` даже с интервалом 20мс не ловит промежуточное
"подменённое" состояние, потому что откат случается раньше следующего
тика. `MutationObserver`-перехват через собственный наблюдатель тоже
показывает уже финальное (откаченное) состояние, а не оба состояния подряд.
Единственный надёжный способ обнаружить — найти сам конфликтующий скрипт в
исходном коде страницы (искать `MutationObserver` в inline `<script>`,
особенно с `attributeFilter: ['href']` или похожим), не пытаться поймать
эффект через инструментирование в реальном времени.

**Урок для будущих клиентов:** если вся диагностика (сервер отдаёт номер,
XPath корректен, нет JS-ошибок, конфигурация выглядит правильной) указывает
на то, что подмена ДОЛЖНА работать, но не работает в реальном DOM — прежде
чем тратить время на дальнейшую инструментальную диагностику, стоит
целенаправленно поискать посторонние `MutationObserver`/скрипты-фиксеры на
самой странице (через просмотр исходного HTML, не через рендеринг) — они
могут быть поставлены независимо от коллтрекинга, для совсем другой цели, и
конфликтовать с ним незаметно.

**Сопутствующий паттерн — "фиксер" может состоять из двух частей (JS + CSS),
удаление только одной ломает видимость:** в этом случае скрипт-фиксер
опирался на пару CSS-правил в custom.css сайта:

    a[href^="tel:"] { visibility: hidden; }
    a.phone-fixed { visibility: visible !important; }

JS-часть находила `tel:`-ссылки, чинила их и помечала классом
`phone-fixed`; CSS-часть безусловно прятала ВСЕ `tel:`-ссылки и показывала
обратно только помеченные. Удаление одной только JS-половины (устраняющей
конфликт с Ringostat) оставило CSS-половину активной — и поскольку
Ringostat не знает о классе `phone-fixed` и не проставляет его, все
телефонные ссылки на сайте стали невидимы целиком (элемент в DOM
присутствует, `getComputedStyle` показывает `visibility: hidden`, значит
"номер пропал визуально" — не значит "элемент исчез из DOM", это разные
диагнозы с разным решением). Общий метод: если внешний "фиксер" на сайте
использует связку JS+CSS (класс-маркер, проставляемый JS, и CSS-правило,
завязанное на этот класс) — удалять нужно ОБЕ половины вместе, поиск
только по JS/только по `<script>` тегам не гарантирует, что не осталось
завязанного на него CSS-правила где-то в другом месте настроек сайта
(в Tilda — не только head/body-вставка, но и отдельное поле "Пользовательский
CSS-код" в настройках сайта).

## Массовая замена хрупких id-правил на универсальные class-based — типовой сценарий "генеральной уборки" кабинета

Найдено на SED Латвия: кабинет содержал 36 XPath-правил, из которых
подавляющее большинство (29) были заведены не по классу, а по хрупким
числовым Tilda-id конкретных блоков (`nav1893659011`, `rec1967266793` и
т.п.) — **отдельное правило на каждую страницу сайта** и на каждую
sticky/обычную копию хедера, вместо одного универсального правила по классу.
Ожидаемо часть из них омертвела при пересборке вёрстки в Tilda, часть ещё
работала (id ещё не менялся) — картина "подмена работает на одних страницах
и не работает на других" при внешне идентичной вёрстке была прямым следствием
этого паттерна, не багом самого Ringostat.

**Метод генеральной уборки, применённый на практике:**
1. Извлечь полный список действующих правил (см. раздел выше про
   извлечение конфига из клиентского скрипта, либо напрямую из кабинета).
2. Сгруппировать по СМЫСЛУ (что физически подменяют — хедер, футер,
   адресный блок), не по имени в кабинете (имена могут быть неточными —
   см. следующий раздел про "contact lv").
3. Для каждой смысловой группы составить ОДНО XPath-правило по устойчивому
   классу/структурному признаку (`contains(@class, ...)`, текстовый маркер
   типа `contains(., 'KONTAKTI')`), которое покрывает все страницы разом.
4. Подтвердить эмпирически (Playwright, несколько реальных страниц), что
   новое правило действительно покрывает то же самое множество мест, что
   покрывали все старые id-правила вместе, ПРЕЖДЕ чем удалять старые.
5. Только после подтверждения — удалить все старые id-правила группы.

Результат на практике: 36 правил → 5 универсальных без потери охвата,
проверено на нескольких языковых версиях и нескольких типах страниц
(главная, контакты).

## Правило может называться не так, как реально работает — проверять по факту, не по имени

Найдено на SED Латвия: правило в кабинете называлось "contact lv" (подразумевая
работу только на латышской версии сайта), реально XPath-условие содержало
`contains(.,'Adrese') or contains(.,'Адрес')` (оба языка предусмотрены в
логике) — но при проверке через Playwright правило матчило 1 совпадение
только на RU-странице контактов, 0 на LV.

Причина не в тексте условия, а в структурной части того же XPath: последний
шаг `/a[starts-with(@href,'tel:')]` (одинарный слэш — "прямой потомок")
совпадал со структурой RU-страницы (`<a>` лежит прямо внутри `div.t-text`),
но не совпадал с LV-страницей, где между `div.t-text` и `<a>` было ещё два
уровня вложенности (`<ul><li>`). Исправление — заменить одинарный слэш на
двойной (`//a[...]`, "любой потомок"): `/a` → `//a`.

**Урок:** название правила в кабинете (или в базе знаний/документации по
итогам разведки) — это гипотеза о том, что правило делает, не факт. Перед
тем как полагаться на существующее правило как на "уже покрывающее X" —
проверить эмпирически на реальной странице X, а не доверять названию.
Особенно важно, если правило досталось "по наследству" от предыдущего
подрядчика/настройки — имя могло быть верным на момент создания и разойтись
с реальностью после правок вёрстки сайта.

## Точечный внутренний span vs весь `<a>` — full-replace ломает иконку/label, если целиться слишком широко

Найдено на [[../Andverpersonalinjury/index|Andverpersonalinjury]]
(landverpersonalinjury.tilda.ws, 2026-09-04), при настройке подмены на
новой посадочной странице: XPath-правило технически корректно указывало на
`<a class="ldv-h__phone">`, номер внутри реально подменялся (проверено
Playwright — `href` и текст меняются на номер из пула) — но заодно пропадали
телефонная SVG-иконка и текстовый label "Free Consultation", которые лежали
в СОСЕДНИХ дочерних `<span>` того же `<a>`, не в том же узле, что номер:

    <a class="ldv-h__phone" href="tel:...">
      <span class="ldv-h__phone-icon"><svg>...</svg></span>
      <span class="ldv-h__phone-copy">
        <span class="ldv-h__phone-label">Free Consultation</span>
        <span class="ldv-h__phone-number">(844) 452-9465</span>
      </span>
    </a>

Это тот же full-replace textContent, что и в разделе выше про длинные
тексты — просто на этот раз стёртый "лишний" контент не текст, а
иконка+label, визуально более заметная потеря (кнопка становится похожа на
сломанную).

**Решение проще, чем HTML-маска с двойной подстановкой (см. раздел про
icon-only ниже)** — если номер уже лежит в СОБСТВЕННОМ, отдельном
дочернем узле (здесь — `<span class="ldv-h__phone-number">`), достаточно
нацелить XPath не на родительский `<a>`, а прямо на этот внутренний узел:

    //a[contains(@class,"ldv-h__phone")]//span[contains(@class,"ldv-h__phone-number")]

Маска остаётся простой (`(###) ###-####`) — full-replace тогда стирает
только этот маленький span, соседние span (иконка, label) физически вне
зоны замены, не трогаются.

**Правило выбора тактики по структуре узла** (обобщение из этого и соседних
случаев на этой же странице, см. также следующий раздел про смешанный
случай "иконка + голый текстовый узел без своего span"):
- номер лежит в СОБСТВЕННОМ дочернем элементе с уникальным классом → целиться
  XPath'ом на этот внутренний элемент, простая маска;
- номера в видимом тексте нет вообще (icon-only) → HTML-маска с двойной
  подстановкой (см. ниже);
- номер — часть ГОЛОГО ТЕКСТОВОГО УЗЛА (не элемента) рядом с иконкой, без
  собственного span → XPath не может адресовать голый текстовый узел
  напрямую (`document.evaluate` работает с element node) — маска на весь
  родительский `<a>`, но в HTML-режиме, с сохранением иконки и текстовым
  плейсхолдером (не обязательно скрытым — если плейсхолдер и так должен
  быть видимым, отдельный `display:none`-дубль не нужен, единственное
  требование — плейсхолдер должен физически присутствовать текстом
  где-то в маске).

## Класс-маркер (`ringo-phone` и подобные) может исчезнуть из вёрстки независимо от Ringostat

Найдено на SED Латвия: правило, нацеленное на специальный класс-маркер
(`ringo-phone`, специально вставленный в вёрстку ради точечной подмены
внутри длинных full-text блоков типа юридических страниц) — оставалось в
кабинете нетронутым, но на живом сайте класс `ringo-phone` физически
отсутствовал на всех проверенных страницах.

Причина — контент страницы (текст политики конфиденциальности) был позже
отредактирован независимо от работы с коллтрекингом (кем именно — не
установлено), и при этом маркер `<span class="ringo-phone">` в тексте был
утрачен вместе с остальной старой версией текста. Правило в кабинете
осталось "правильным" само по себе, но ему стало нечего искать.

**Урок:** правило, завязанное на класс-маркер, специально вставленный в
контент (не автогенерируемый класс конструктора сайта), уязвимо к любому
последующему редактированию этого конкретного контента кем угодно —
не только к пересборке вёрстки блока в целом (как хрупкие id), но и к
banальной правке текста копирайтером/другим подрядчиком, который не в
курсе о существовании этого маркера и не обязан его сохранять. Периодически
стоит перепроверять, что такие маркеры всё ещё присутствуют на странице,
особенно после любых правок текста на юридических/часто редактируемых
страницах.
