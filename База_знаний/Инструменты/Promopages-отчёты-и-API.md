## Что умеет API (по документации)

[справка: `yandex.ru/dev/promopages-api/doc/ru/`] Всего **пять методов**, все на чтение:

| Метод | Что делает |
|---|---|
| `GET /api/promo/v1/campaigns` | список кампаний: настройки, стратегия, таргетинг, публикации с обложками |
| `POST /api/promo/v1/reports/{type}` | создать отчёт; типы `campaigns-daily-stats`, `campaigns-publications-daily-stats`, `campaigns-previews-daily-stats` |
| `GET /api/promo/v1/reports/{reportId}?format=json` | получить отчёт (код 202 = ещё не готов) |
| `GET /api/promo/v1/publishers/balances?publisherIds=…` | баланс кошелька |
| `GET /api/promo/v1/permissions/user` | список кабинетов (клиентов) и права `canRead` / `canWrite` |

- **Создавать и менять кампании, ставки, статьи через API нельзя**: в документации нет ни одного метода записи. Вопрос из `Хроника_2026-10`, п. 8 («умеет ли API создавать кампании и статьи») закрывается по документации как «нет»; для скриптов запуска нужны другие пути (интерфейс кабинета, ручной ввод). [справка; [в источниках нет] методов записи; не проверено на практике, например вызовом POST на `/campaigns`; мы не пробуем: запись в кабинеты запрещена протоколом]
- Доступ: приложение в Яндекс OAuth (`oauth.yandex.ru/client/new`), право `promopages:api`, токен в заголовке `Authorization`. [справка] Наш токен отдельный, не Директа/Метрики (`Инфраструктура.md`, запись 2026-08-25). Токен в самом скрипте `E:/PythonProjects/RedBird/dev/Promopages/promopages.py` захардкожен — это ограничение безопасности, не копировать в вики.
- Лимиты: «общее ограничение на количество запросов в секунду», при превышении код 429, повторить через несколько минут. Конкретное число в документации не названо. [справка; [в источниках нет] числа]
- Отчёты хранятся **30 дней, но не более 1000 последних**; период задаётся `mskDateFrom`/`mskDateTo` в формате `YYYY-MM-DD`. [справка] Формирование на практике медленное (5-15 минут по `Хроника_2026-10`; код 202 до готовности). [наши данные]
- Коды ответа: 200, 202 (не готов), 400, 401, 403, 404, 422, 5xx. [справка]

### Методы подробнее

**`GET /campaigns`** [справка + наши данные]
- Параметры: `publisherId` (обязательно), `pageLimit` ≤ 200 или `campaignIds` (до 200 через запятую), `pageLastId`, `startFrom`, `campaignTypes` (`article`, `video`, `post`, `gallery`), `campaignStrategies` (`cpm`, `full_read`, `full_view`, `clickout`).
- Ответ: `id`, `title`, `type`, `start`, `end`, `isArchived`; `strategy` {`name`, `maxDailyMoney`, `maxMoney`, `fullReadCost`, `fullViewCost`, `impressionCost`, `cpm`, `clickoutCost`, `reachFrequency`}; `targeting` {`geo[]`, `os[]`, `gender[]`, `age[]`}; `publications[]` с `previews[]` (заголовок + картинка, флаги `isDisabled`, `isDeleted`).
- **Нет**: статуса кампании (активна/остановлена), цели оптимизации у `daily_budget`, настроек «быстрых действий», UTM, интересов, сегментов Аудиторий, минус-фраз, истории изменений, баланса по кампании. [справка + наши данные]
- В реальном ответе есть то, чего нет в документации: `targeting.placements` (`rsya`, `search`) и у публикации `s2sUrlO` (адрес Scroll2Site-посадочной; у 12 из 45 наших публикаций заполнен). Значение `daily_budget` встречается в ответе, но не указано в фильтре `campaignStrategies`. [наши данные]
- В документации тип стратегии `clickout` помечен «оплата за переходы»; `cpm` и `full_view` у нас отсутствуют.

**Отчёты** [справка + наши данные]
- Параметр `trafficSource`: `total` (по умолчанию), `ya_search`, `rsya` — **разделение Поиска и РСЯ**. Наш скрипт `promopages.py` его не передаёт, значит все выгрузки — `total`. [наши данные]
- Поля по документации: `campaignId`, `publicationId`, `previewId`, `mskDate`, `impressions`, `reach`, `budget` (без НДС), `cpm`, `clickouts`, `clickoutCost`, `clickoutPercent`, `fullReads`, `fullReadPercent`, `ctr`, `videoExpands`, `videoFullViews`, `videoExpandPercent`, `videoFullViewPercent`, `metricaVisits`, `metricaVisitPercent`, `metricaVisitCost`.
- Реальные строки нашего отчёта содержат ещё `views`, `clicks`, `fullReadTimeSec`, которых в документации нет; поля `video*` для статей не приходят. Смысл (по арифметике на данных 28.09-27.10.2026): `ctr` = `views`/`impressions`, `fullReadPercent` = `fullReads`/`views`, `clickoutPercent` = `clickouts`/`fullReads`, `metricaVisitPercent` = `metricaVisits`/`fullReads`. [наши данные, формулы — см. [[Promopages-стратегии-и-оплата]]]
- `clickoutPercent` по справке — «процент внешних переходов от дочитавших или досмотревших». [справка]
- **Третий отчёт `campaigns-previews-daily-stats` (по обложкам: заголовок × картинка) мы ни разу не запрашивали.** Он даёт CTR и расход по каждой комбинации заголовок-картинка и нужен для теста заголовков и обложек. [наши данные + справка; пробел скрипта]
- Региона, пола, возраста, устройства, места показа внутри отчёта нет; только суммарно и (через `trafficSource`) Поиск против РСЯ. [справка]

## Отчёты в кабинете

[справка: `statistics/extended`, `statistics/conversion-report`, `statistics/search-queries`, `statistics/settings`]

| Отчёт | Что показывает | Заметки |
|---|---|---|
| По кампаниям, публикациям, заголовкам/обложкам | расход, дочитывания, цена дочитывания, CTR, внешние переходы, цена перехода, визиты и цена визита (из Метрики), активные визиты, показы, охват, среднее время дочитывания, оценка интереса, карта просмотров и оттока | период по умолчанию 30 дней; «Свернуть публикации»; расход можно показать «с НДС» и «с учётом скидки» |
| Excel | стандартные отчёты (по дням, публикации) и **по расписанию** на e-mail: ежедневно (2 месяца), еженедельно (6 месяцев), ежемесячно (12) | период 1-99 дней или прошлая неделя; в выгрузке есть лист «Сводная статистика обложек» |
| Отчёт по конверсиям | достижения цели **по последнему значимому клику** и **отложенные** от дочитывания, дни и визиты до первой цели, новизна посетителя | данные с 1 апреля 2023, без последних 4 дней; окно атрибуции по умолчанию 7 дней (до 90); видны только цели, достигнутые хотя бы раз; считает «Достижения / Целевые визиты / Целевые посетители» |
| Отчёт по поисковым запросам | запросы, по которым показывали публикации на Поиске, с целями | только при показах на Поиске; максимум 90 дней |
| Карта оттока | где в тексте уходят читатели (зелёный 0%, жёлтый 5%, красный 10% и более); нормальный отток после первого экрана 20-25% | появляется после 100 просмотров публикации |
| Оценка интереса | процент положительных ответов на вопрос «Заинтересовались?» в конце статьи | служит сигналом для стратегии «Заинтересовавшиеся»; макрос `{interest}` передаёт ответ в ссылку |
| Прогноз бюджета, бенчмарки | по категории, гео, полу/возрасту | см. [[Promopages-площадки-и-бюджет]] |
| Уникальные тексты | публикации, набравшие 1000 дочитываний, и среди них с уникальностью более 50% | раздел «Клиенты» |

- **Атрибуция в кабинете**: конверсия привязывается к дате **дочитывания** (по умолчанию), а не к дате визита; вручную можно выбрать «по дате совершения конверсии». Метрика, напротив, датирует действие в момент совершения; расхождение дат нормально. Советуют подводить итоги месяца через 7-14 дней после его окончания. [справка] У нас `Решения.md` 2026-10-27 считает заявки по дате визита с конверсией (Метрика), расход — по датам API; октябрь сошёлся с кабинетом (6 заявок, 2 688,81 ₽). [наши данные]
- Расхождение «кабинет vs Метрика»: кабинет считает только оплаченные визиты (без органики и отфильтрованных антифродом); Метрика — все. Расхождение 90-100% — проблема на сайте; 30-40% — обычно: ушёл до загрузки Метрики (порог 2 секунды), не ответил на pop-up (cookie), потеря UTM (редиректы, трекинговая ссылка, http→https), нет интереса. [справка: `statistics/metric`]

## Связка с Яндекс Метрикой

[справка: `statistics/metric`, `statistics/settings`, `advertising/macros`; практики]

- **Подключение счётчика сайта**: «Статистика → По кампаниям → Выбрать цель → Счётчики → Добавить»; при разных логинах — «Запросить доступ» у владельца. Показатели Метрики (визиты, цель) попадают в статистику ПромоСтраниц. Выбранная атрибуция по умолчанию — «первый переход».
- **UTM, подставляются автоматически** при привязке публикации к кампании: `utm_source={yandex.promopages}` (обязательна), `utm_medium={publication_type}` (обязательна), `utm_campaign={campaign}` / `{campaign_eng}`, `utm_content={title}` / `{title_eng}` (первые 50 символов), `utm_term={link_name}` (`Scroll2Site`, `feedback`, `click_through` или текст ссылки). Можно переопределить: «Кампания → UTM-метки → Изм», действует на все публикации кампании. В редакторе по умолчанию добавляется `{preview_id}` — идентификатор обложки (заголовок × картинка), по нему в Метрике видно конверсию каждой комбинации. [справка]
- Наша фильтрация `UTM Source содержит promopages` корректна по значению `yandex.promopages`. Наблюдение из `Решения.md` 2026-08-25: в `utm_content` у нас технический тег (`history`), а не название публикации — значит UTM вручную переопределены на ссылках. Какие макросы стоят на ссылках (в частности `{preview_id}`, `{region_name}`, `{device_type}`, `{interest}`), надо посмотреть в «UTM-метки → Изм». [наши данные + справка; пробел]
- **Макросы для среза в Метрике** [справка: `advertising/macros`]: `{region_name}` (регион показа), `{device_type}` (desktop/mobile/tablet), `{keyword}` (фраза показа на Поиске), `{interest}` (interested/uninterested/unrated), `{preview_id}`, `{campaign_id}`, `{id}` (публикация), `{logid}`, `{rand}`. Через них можно закрыть пробел «нет разреза по гео/устройству в API»: срезать заявки по параметру в самой Метрике. [справка; не проверено на практике]
- **Отдельный счётчик «Метрика публикаций»**: даёт пол, возраст, гео, интересы **читателей**. Не указывать в нём счётчик сайта: иначе все посетители попадут в источник «Внутренние переходы». Нужен именно новый счётчик под публикации. [справка: `statistics/settings`] Есть ли он у клиента — неизвестно (см. [[Promopages-таргетинги-и-аудитории]]).
- **Метрика для медийной рекламы**: пиксель «на показ» (по справке — на событие «Открытие» в кампании) даёт post-view конверсии за 90 дней после дочитывания; её CTR/CPM не совпадают с кабинетом (пиксель на показ поставить нельзя). Три уровня оценки отложенных конверсий: post-view (открытие, медийная Метрика), **post-read** (отчёт по конверсиям в кабинете — «самый оптимальный»), post-click (Метрика сайта с атрибуцией первого перехода: не учитывает дочитавших, но не перешедших). [справка]
- Пиксели Аудиторий: события «Открытие», «Полный просмотр», «Внешний переход»; допустимы любые сторонние пиксели, согласованные для медийных размещений Яндекса.
- Стратегия «Оптимизация конверсий»: часть статистики ПромоСтраниц уходит в источник «Яндекс Директ. Не определено»; Яндекс советует смотреть отчёт по UTM. Если когда-нибудь включим конверсионную стратегию, наш фильтр по `firstUTMSource` надо перепроверить. [справка; не проверено на практике]
- Практики советуют оценивать ПромоСтраницы по **первому клику/переходу** и анализировать конверсии по первому клику, так как аудитория холодная (MediaGuru 2024; справка `statistics/settings`, `statistics/rating`). Совпадает с решением `Цели/goals.md` и `Решения.md` 2026-10-27. [справка + практики + наши данные]
- Метод оценки по справке (`statistics/rating`): Excel-отчёт кабинета (дочитывания, расход по публикации) + отчёт Метрики «Метки UTM» с целью → сопоставление по названию публикации → цена целевого действия. Наш `dzen_campaigns_scorecard` делает то же на уровне кампаний. [справка + наши данные]

## Пробелы и что делать

1. **Статус кампании** недоступен через API → перед выводами по активным кампаниям нужен скриншот «Текущие» (`CLAUDE.md`, правило для этого клиента).
2. **Разрез по обложкам** (`campaigns-previews-daily-stats`) и **Поиск vs РСЯ** (`trafficSource`) не запрашивались: добавить в скрипт чтения (задача для `script-builder`, режим только чтение).
3. **Цель оптимизации у `daily_budget`** и **галочка быстрых действий** в API нет → скриншот настроек.
4. **Гео, пол, возраст, устройство, интерес** в статистике ПромоСтраниц нет → брать из Метрики через макросы `{region_name}`, `{device_type}`, `{interest}` (если они стоят в ссылках) и «Метрики публикаций» (читатели).
5. **Пересчёт заявок 2023-2026** по `firstUTMSource` и новому счётчику `goal143150284reaches` (`Задачи.md` клиента) остаётся открытым.
6. **Независимые источники** по API и отчётам (практики, не справка) в поиске не нашлись: обзоры агентств описывают интерфейс и показатели, не API. Утверждения этой страницы про API опираются на документацию и на наши выгрузки. [в источниках нет]
