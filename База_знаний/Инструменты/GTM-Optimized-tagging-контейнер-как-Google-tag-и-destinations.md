# GTM: «Optimized tagging experience» — контейнер как Google tag

> **Не проверено на практике.** Источники: статья Simo Ahava (читал через пересказ, не глазами; дата в пересказе 13.10.2026) и справка Google «Updates to Google tag and Google Tag Manager». В наших контейнерах мастер оптимизации пока не запускали и не видели.

## Суть одной фразой
Google склеивает Google tag и Tag Manager: контейнер GTM сам становится «Google tag», а GA4, Google Ads и Floodlight подключаются к нему как **destinations** с общими настройками на уровне контейнера.

## Что нового
| Что | Как было | Как станет |
|---|---|---|
| Настройки Google tag | В каждом теге «Google tag» / конфигурации GA4 свои | Общие, во вкладке **Settings** обзора контейнера (+ сворачиваемая вкладка **Advanced**: триггеры, переменные, шаблоны, папки) |
| Подключение продуктов | Отдельный тег на каждый, каждый тянул свой `gtag.js` | **Destination-теги** (Google Analytics, Google Ads, Floodlight); данные уходят напрямую, без отдельной загрузки `gtag.js` |
| Теги «Google tag» и «Conversion Linker» | Основа схемы | Считаются **legacy**, сами не заменяются |
| Согласие | Consent Mode | Destination-теги учитывают согласие; новая настройка **Manage data transmission** — задерживает хиты до согласия и отправляет их повторно (надстройка над Advanced Consent Mode, только для тегов Google) |
| Сайты только с Google tag | Нет интерфейса GTM | Google tag апгрейдится до полноценного контейнера: интерфейс тегов, предпросмотр, версии |
| Preview | — | Вкладка **Hits sent**, видны активные Settings |
| Overview | — | Диаграмма потока данных, **Destination details** (какие теги ссылаются на destination) |

## Что это даёт
- Быстрее: страница не грузит отдельный `gtag.js` под каждый продукт.
- Одно место для настроек (раньше разъезжались между тегами) + история версий, как у любого ресурса GTM.
- Меньше путаницы с порядком срабатывания: инициализация настраивается триггером `gtm init`.
- Контейнер автоматически связывается с аккаунтами destinations (по умолчанию доступ «Read»).
- Попутно: Visual tagging (бета, пока только конверсии покупки в Google Ads) — события без кода.

## Что НЕ меняется / ограничения
- Ничего не применяется автоматически и не обязательно (в источниках сроков и принудительной миграции нет). Запустить оптимизацию могут пользователи с правами edit / approve / publish; результат сначала попадает в рабочую область и **не публикуется сам**.
- Поведение тегов на странице, по заявлению Google, не меняется.
- Общие настройки действуют на все destinations. Настройка в самом теге может только **ужесточить**, но не ослабить общую (контейнер запретил user-provided data — тег его не включит).
- Конфликты между настройками разных тегов мастер не подсвечивает — сравнивать «До/После» (Show details) надо глазами.
- Manage data transmission не распространяется на сторонние теги.
- Доступ несимметричен: у кого есть доступ к Google tag, получает Read к контейнеру; наоборот — нет. Перед включением проверить, кто что увидит (External account links).

## Мастер оптимизации (порядок)
Баннер в GTM → выбрать теги для привязки (снятые остаются legacy) → решить про Read-доступ → View settings по каждому тегу → выбрать набор настроек за основу (или с нуля) → Show details, сравнить Before/After → Add to workspace → Preview → публикация. Откат: опубликовать предыдущую версию контейнера.

## Что нам надо будет сделать
Контейнеры, о которых знаем: ProfiMet `GTM-TKGN4NT`, EkspertAgro `GTM-5FBCZLMC`, SED Латвия `GTM-TMV7VSWQ` (Tilda, Ringostat-скрипт). Срочности нет — это опциональное обновление.

1. **Ничего не жать в боевых контейнерах «по баннеру».** У ProfiMet есть нестандартика: теги с согласием `ad_storage`, Enhanced Conversions с переменной телефона, тег записи заявки в Supabase, кастомный UTM-тег (версия 62) — общие настройки могут это задеть ([[GTM-сохранение-UTM-в-браузере-для-форм]], [[Расширенные-конверсии-Google-Ads-ручная-настройка]]).
2. **Сначала инвентаризация только чтением** (`Скрипты/gtm_read_container.py`): какие Google tag / Conversion Linker / конфигурации GA4 / Ads-теги есть, у каких свои переопределения (page_view, consent, user-provided data, server-side). Это основа для сравнения «До/После».
3. **Проверить, видим ли баннер** в каждом контейнере и у кого права (наш сервисный ключ `rb-cloud-admin` — только чтение; мастер запускает человек в интерфейсе).
4. **Пилот — на самом простом контейнере** (кандидат: SED Латвия, мало тегов; не ProfiMet), в рабочей области, без публикации; Preview → «да» → публикация по протоколу записи в вики; откат — предыдущая версия.
5. **Согласие:** выяснить, у каких клиентов включён Advanced Consent Mode; только там имеет смысл Manage data transmission.
6. **Доступы:** до запуска проверить, кому из внешних аккаунтов контейнер даст Read через связку с destinations.
7. **Свериться с чек-листами по конверсиям:** после любой публикации сравнить число конверсий в Ads/GA4 за 2–3 дня с базой — тут реальный риск (двойной счёт, пропавшие хиты).
8. **Если делаем через API/MCP:** хиты и настройки Settings — это новые ресурсы GTM; поддерживает ли их наш скрипт и API, не проверено.
