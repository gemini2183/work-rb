# Ringostat → GA4: какие звонки передаются и как делать цели по типам

**Статус: документация — "не протестировано"; раздел 6 — проверено на данных ProfiMet
(GA4 Data API, 2026-10-06). Параметры события `call_status`/`call_unique` в GA4 ProfiMet как
измерения НЕ зарегистрированы — по ним отчёты не построить (доступны только `event_category`,
`event_label`, и те пустые).**

Связано: [[Ringostat-Google-Ads-интеграция-и-нехватка-номеров-искажают-атрибуцию]],
[[GA4-два-разных-экрана-настроек-атрибуции]], [[Ringostat-механизм-подмены-номера]].

## 1. Что уходит в GA4 по умолчанию

По официальным страницам Ringostat ([GA4 key events — все категории](https://help.ringostat.com/en/articles/6240462-setting-up-google-analytics-4-goals-all-categories-of-the-call),
[статистика звонков в Ringostat и GA4](https://help.ringostat.com/en/articles/6462893-call-statistics-in-the-ringostat-and-google-analytics-4),
[гайд по целям](https://blog.ringostat.com/ru/tseli-v-ga-4-dlya-kolltrekinga/)):

- Событие **`Ringostat_calls`** создаётся автоматически, включено после подключения
  интеграции. Цитата: "The Ringostat_calls event includes all incoming calls in the
  project and calls from the Callback widget." То есть **не только принятые и не только
  уникальные — каждый входящий звонок отдельным событием**, в том числе пропущенные,
  автоответчик, повторные.
- Событие **статического коллтрекинга** (звонок по номеру без сессии на сайте)
  включается отдельной галочкой в настройках интеграции. Название расходится между
  страницами Ringostat: `Ringostat_static_calls` (гайд по целям) и `Ringostat_calls_static`
  (страница про key events; так же называется конверсия в Ads у ProfiMet). Какое реально
  приходит в GA4 — **не проверено**.
- Вместе с событием уходят параметры: **статус звонка** (`call_status`), **длительность**,
  **тип** (входящий / callback). Из гайда по целям — также `call_unique` и `pool_name`.
- Задержка: GA4 показывает данные с задержкой до 24 часов (в отчётах по ходу дня — только
  Realtime).
- Страница про интеграцию **не называет** порог длительности, точный состав параметров
  и правила отправки (одно событие на звонок или на номера) — только категории. "По одному
  событию на каждый звонок" прямо написано на странице статистики звонков.

## 2. Что значат статусы звонка (`call_status`)

Из [описания статусов журнала звонков](https://help.ringostat.com/en/articles/6413217-call-log-description-of-call-statuses):

| Статус | Значение (дословно по документации) |
|---|---|
| `PROPER` | целевой звонок; определяется настройкой **минимальной длительности целевого** и **цикла продажи** в проекте (в документации пример 30 секунд, универсального порога нет) |
| `REPEATED` | повторный звонок **после первого целевого в рамках цикла продажи**; первый звонок номера не может быть `REPEATED` |
| `ANSWERED` | "non-target answered call" — принят, но не целевой (короче порога) |
| `NO ANSWER`, `BUSY`, `NO-FORWARD`, `FAILED`, `VOICEMAIL`, `DECLINE`, `NO EXTENSION`, `WRONG EXTENSION` | пропущенные / не дошедшие |

Длина цикла продажи в днях на странице не указана (в примере "один день") — это
настройка проекта, **значение у ProfiMet не проверено** (смотреть в кабинете Ringostat).

**Проверено на наших данных (API звонков Ringostat, поле `disposition`):** за 22.09–05.10.2026
по `Search | Poliweglan | Pl` встретились `PROPER` 13, `REPEATED` 11, `NO ANSWER` 3, `ANSWERED` 1,
`VOICEMAIL` 1. Значения совпадают с документацией; поле звонка в API называется
`disposition`, а в GA4-параметре — `call_status` (соответствие по названию — предположение).

## 3. Цели по типам звонков — настраиваются, но вручную

Ringostat рекомендует (гайд по целям) не одну цель, а набор, на параметрах события:

| Цель | Условие по параметру события |
|---|---|
| Все звонки | событие `Ringostat_calls` целиком (отметить звёздочкой как key event) |
| Принятые | `call_status` соответствует regex `(PROPER\|REPEATED\|ANSWERED)` |
| Целевые | `call_status` = `PROPER` |
| Уникальные | `call_unique` = `1` |
| Пропущенные | `call_status` regex `(CLIENT NO ANSWER\|NO-FORWARD\|NO ANSWER\|BUSY\|FAILED\|VOICEMAIL\|NO EXTENSION)` |
| Callback | `pool_name` = `callback` |

Способ настройки по гайду — **через аудиторию + триггер аудитории + конверсия** (не через
"создать событие по условию"), имена аудитории/триггера/конверсии должны совпадать и быть
без пробелов (`Proper_Calls`, `Answered_Calls`, `Unique_Calls`…). Для GA4 есть и штатный путь
"Создать событие" с условием по параметру — но он в источниках Ringostat не описан, это
общее знание GA4, **не проверено**.

Что страница Ringostat **не объясняет**: точный порог `PROPER`; полный список значений
`call_status`; как сделать отдельной целью именно `REPEATED`; как параметры доходят до GA4
технически.

**Важная оговорка по `call_unique`.** Определение "уникальный" в Ringostat — "первый звонок
с уникального номера" **или** звонок со ссылкой на сессию пользователя на сайте. Это НЕ то же
самое, что "уникальный" в нашем скрипте `ringostat_stats_profimet.py` (первый звонок номера за
всю историю с 2025-08-01 по любому источнику). Числа могут не совпасть — не сравнивать как
одно и то же.

## 4. Как это считается дальше (счёт, повторные звонки)

- **GA4, ключевое событие:** два способа счёта — "once per event" (каждое вхождение; по
  умолчанию для новых) и "once per session" (не чаще раза за сессию). Меняется в Admin →
  Data display → Events → ⋮ → Change counting method; действует только вперёд. Какой способ
  стоит на `Ringostat_calls` у ProfiMet — **не проверено** (нужен доступ к GA4).
  Старая статья Ringostat про расхождения ("цель в сессии достигается один раз") написана
  под Universal Analytics, для GA4 по умолчанию не применима.
- **Google Ads, импорт ключевого события:** режим счёта "Every" (много на клик) / "One" (одна
  на клик, `ONE_PER_CLICK`). **Проверено через Ads API (2026-10-06) у ProfiMet:** конверсия
  `Ringostat_calls` — `ONE_PER_CLICK`; `Звонки по объявлениям` — `MANY_PER_CLICK`. Значит
  несколько звонков с одного клика (gclid) в Ads дают **одну** конверсию.
- Ringostat кладёт gclid в поле `utm_content` звонка (`...|gclid_<значение>`; **проверено** на
  звонках динамического пула) — это позволяет считать "сколько разных кликов" среди звонков.

## 5. Практический вывод (на сегодня)

1. По умолчанию в GA4 уходит **всё**, поэтому "в Ads не дошли пропущенные" — не причина
   разницы с Ringostat сама по себе: пропущенные там тоже есть. Разница — на счёте GA4
   (событие/сессия) и импорте в Ads (один на клик, атрибуция по каналу).
2. Если нужна цель, оптимизирующая по смыслу (разговор ≥ порога), отдельная цель
   `Proper_Calls` / `Answered_Calls` технически возможна — но не проверена; выбор влияет на
   автостратегию, решать отдельно.
3. Чтобы закрыть неизвестное, нужно: доступ к GA4 `349001266` (Viewer для
   `rb-cloud-admin@redbird-196813.iam.gserviceaccount.com` + включённый Analytics Data API),
   либо скриншоты: Events → `Ringostat_calls` (параметры, counting method), настройки
   интеграции Ringostat→GA4 (галочки), настройка минимальной длительности целевого звонка.

## 6. Проверено на ProfiMet: Search | Poliweglan | Pl, 22.09–05.10.2026 (GA4 Data API)

Ресурс GA4 `349001266`. Событие GA4 приходит со временем **окончания** звонка (старт +
`duration` из журнала Ringostat), это позволило сопоставить каждый звонок с событием по минуте
(сопоставились все 12 событий GA4 с кампанией Poliweglan). Срез: звонки Ringostat, у которых
`utm_campaign` содержит id кампании; Ads — конверсия `Ringostat_calls` по **дате конверсии**.

| Звено | Звонков/событий |
|---|---|
| Ringostat, сырых звонков (динамический пул) | 29 |
| → дошло до GA4 как `Ringostat_calls` (любая кампания) | 15 |
| → из них GA4 пометил кампанией Poliweglan | 12 (ещё 1 — `pmax1_test`, 2 — `(not set)`) |
| → GA4 засчитал как key event (`conversions`=1) | 14 из 15 (Poliweglan: 11) |
| → Google Ads, `Ringostat_calls`, Poliweglan | 12 |

Что видно (факты):
- **Статусы не фильтруются**: в GA4 дошли и `NO ANSWER` (звонок 0 секунд, 28.09 20:30 — дал
  конверсию в GA4 и в Ads за 28.09), и `ANSWERED` 11 секунд, и `REPEATED`. Пропущенные звонки
  попадают в Ads как конверсии.
- **Не дошли до GA4 вообще 14 из 29.** 9 из них — один номер (48692542903), у которого не ушёл
  ни один из 9 звонков (в т. ч. `PROPER` 200 с и 7 звонков за 05.10); причина не определена
  (тестовый/сотрудник? нет сессии? исключён?). Остальные 5: 23.09 (`PROPER` 761 с), 24.09
  (`NO ANSWER`), 28.09 13:44 (`PROPER` 207 с), 29.09 (`REPEATED` того же номера), 30.09 (`PROPER`
  319 с). Без этого номера дошло 15 из 20. Причина (нет сессии/согласия/блокировщик) не
  проверена.
- **Дошедшие повторные звонки**: `REPEATED` дошли 4 из 11 (один недошедший — тот же номер, что и
  не дошедший первый звонок). Сам статус `REPEATED` не мешает отправке.
- **Одна сессия — одна конверсия**: звонок 28.09 09:24 (повторный того же номера, через 7 минут)
  дошёл в GA4 событием, но `conversions`=0. По всему ресурсу за период 54 события → 44
  конверсии. Это похоже на счёт "once per session", но настройку counting method прочитать не
  удалось (Admin API выключен в проекте) — **гипотеза**.
- **Метка кампании в GA4 ≠ метка Ringostat**: звонок 29.09 10:01 Ringostat относит к Poliweglan, GA4
  — к `pmax1_test`; два звонка GA4 — `(not set)`.
- **GA4 → Ads**: 11 конверсий Poliweglan в GA4 → 12 в Ads. По дням: 26.09 — в GA4 1, в Ads 0;
  29.09 — в GA4 0 (событие помечено pmax), в Ads 1; 01.10 — в GA4 3, в Ads 4 (4-е — событие GA4
  `(not set)`). Похоже, Ads относит конверсию по gclid клика, а не по метке кампании GA4 —
  **гипотеза**, на уровне отдельных событий не доказана.

Ограничения: 29 звонков — малая выборка; один номер даёт 9 из 29 и искажает проценты;
дата конверсии в Ads для импорта из GA4 принималась как дата события.

## 7. Проверено: "уникальный" в Ringostat и в нашем скрипте (2026-10-06)

API звонков Ringostat отдаёт собственный признак **`unique_call`** (0/1) и `client_id`
(посетитель). Поля `call_unique`, `first_call` и т. п. API не знает — `call_unique` из справки
Ringostat это название параметра в GA4, а не в API (соответствие по смыслу — предположение).
История звонков в API Ringostat доступна **с 2023-08-31** (наш скрипт `ringostat_stats_profimet.py`
берёт только с 2025-08-01).

- **Search | Poliweglan | Pl, 22.09–05.10.2026, 29 звонков:** `unique_call`=1 у 11, наш скрипт
  даёт 11, скрипт с историей с 2023-08 — 11; совпадение по каждому звонку 100% (0 расхождений).
  Статусы уникальных: PROPER 8, NO ANSWER 2, ANSWERED 1 — уникальность не равна "принятый".
- **Вся история Google Ads, входящие с 2025-08-01 (7219 звонков):** `unique_call` совпадает с
  "первый входящий звонок номера за всю историю (2023+)" почти везде (13 расхождений). С нашим
  скриптом расходится в 488 из 3912 случаев "скрипт: уникальный", то есть в 12.5% скрипт
  завышает уникальные, потому что не видит звонки до 2025-08. На свежих периодах (13+ месяцев
  истории) эффект нулевой, на первых месяцах после 2025-08 — заметный. Тот же срез истории в
  прод-скрипте `ringostat_profimet2` (методология скопирована 1:1) — **не проверено**.
- Доля `unique_call`=1 среди входящих Google Ads с 2025-08: пул `Google CPC_dyn` 51%,
  `Google CPC_search` 35%, `Callback` 64%.
- Вывод про цель по уникальным: она оставила бы 11 из 29 звонков Poliweglan (из них до GA4
  дошли 8), потеряла бы 5 звонков `PROPER` от вернувшихся номеров и 3 повторных звонка, которые GA4
  засчитал, и сохранила бы 2 `NO ANSWER` и 1 короткий `ANSWERED`. Уникальность — про дедупликацию
  по номеру, а не про качество звонка.

## 8. Проверено: доля звонков, дошедших до GA4 (ProfiMet, 2026-08-01 — 2026-10-05)

Метод: входящий звонок Ringostat сопоставлялся с событием GA4 `Ringostat_calls` по времени
окончания (старт + duration), допуск ±2 минуты, один к одному. Из 240 событий GA4
не сопоставилось 1. Минуты "дошло / не дошло" — оценка, не прямое знание о доставке.

| Срез | Звонков | Дошло в GA4 |
|---|---|---|
| Google Ads, динамические пулы (все кампании) | 281 | 167 (59%) |
| из них **уникальные** (`unique_call`=1) | 168 | **107 (64%)** |
| из них неуникальные | 113 | 60 (53%) |
| Search Poliweglan, уникальные | 53 | 34 (64%) |
| Facebook | 86 | 65 (76%) |
| Google SEO | 177 | 5 (3%) |

Что видно:
- **Теряется около трети уникальных звонков** (36%), и это стабильно: август 63%, сентябрь 64%,
  октябрь 64%. Доля от месяца к месяцу не меняется, неделя с долей 38% (31.08–06.09) — единичный
  провал, не исследован.
- **Статус, длительность, час звонка, неуникальность на доставку почти не влияют** (дошло 48–64%
  при любом статусе; ANSWERED 92%, но звонков 13). Уникальные доходят чуть чаще (64% против 53%).
- Слабые сигналы (не доказательство): звонки с пустым `referrer` доходят в 30% (10 из 33)
  против 62% при `referrer` google; звонки с десктопа 51% против 64% с мобильных.
- **Причина не найдена.** Рабочая гипотеза — у посетителя нет сессии GA4 (нет согласия на cookie,
  блокировщик, не сработал тег), и Ringostat не отправляет событие. Не проверено. Нужны: в
  Ringostat — условие отправки события в GA4 (отправляется ли без GA client id); в GA4 — сравнение
  числа сессий cpc с кликами Ads.
- Три конкретных недошедших уникальных звонка Poliweglan (24.09 17:51, 28.09 13:44, 30.09 14:11):
  у первых двух нет событий Ringostat в GA4 ±6 минут, у третьего рядом одно общее событие
  `Ringostat_calls_static` без источника, которое может быть случайным (ожидаемо ~0.26 такого
  события на окно из-за фонового потока 444 событий за 14 дней).
