# GA4: конверсии "приписываются" платёжному шлюзу (referral hijacking)

## Симптом

В отчёте GA4 (Трафик по источникам/каналам) весь или почти весь объём ключевых
событий (конверсий) числится за источником вида `pay.monobank.ua / referral`
(или аналогичным доменом другой платёжной системы), независимо от того,
откуда реально пришёл пользователь (реклама, органика, прямой заход).

Пример (клиент [[../../Клиенты/Корогва/index|Корогва]], 2026-09-08): 45 из 45
событий `custom_purchase` (100%) приписаны `pay.monobank.ua / referral`.

## Механизм

Стандартная связка "оплата на стороннем домене платёжной системы":

1. Пользователь заходит на сайт с рекламы/органики — GA4 фиксирует исходный
   source/medium в сессии.
2. В чекауте нажимает "оплатить онлайн" → браузер уходит на домен платёжного
   шлюза (`pay.monobank.ua` и т.п.) — **это уход на другой домен**.
3. После оплаты шлюз делает редирект обратно на сайт, на страницу
   "Спасибо за заказ" (где обычно и стреляет конверсионное событие).
4. GA4 по умолчанию не знает, что уход на этот домен и возврат с него —
   легитимный шаг оплаты, а не переход по внешней ссылке с чужого сайта.
   Он видит новый заход "с домена pay.monobank.ua" и **создаёт новую сессию**
   с этим источником, затирая исходный канал. Конверсия на странице
   "Спасибо" записывается уже в новую (реферальную) сессию.

## Как исправить

**Основной механизм — список нежелательных переходов (Unwanted referrals):**

GA4 → Администратор → поток данных (Веб) → Настроить тег (Configure tag
settings) → Показать все настройки → **"Создание списка нежелательных
переходов"** → добавить домен(ы) платёжных систем (`pay.monobank.ua`, и
любые другие шлюзы, если используется несколько — LiqPay, Portmone, Fondy
и т.д.).

Как работает: GA4 при построении сессии смотрит на реферер. Если домен
реферера — в списке нежелательных переходов, GA4 **не создаёт новую сессию**
и не переатрибуцирует источник, а сохраняет исходный source/medium через
переход.

**Дополняющий механизм — настройка доменов (Cross-domain measurement):**

Там же, в настройках тега — пункт **"Настройка доменов"**, чуть выше списка
нежелательных переходов. Стоит добавить туда те же домены платёжных систем.
Разница: список нежелательных переходов просто "не путает" источник задним
числом, а cross-domain measurement протаскивает клиентский ID (`_gl`
параметр) через сам redirect на шлюз и обратно, обеспечивая более полную
и надёжную склейку сессии как одного визита. Механизмы дополняют друг
друга, не взаимоисключающие — имеет смысл настроить оба.

Путь в интерфейсе подтверждён скриншотом пользователя 2026-09-08 (Admin →
Data Streams → поток → Configure tag settings → Show all → "Создание
списка нежелательных переходов" / "Настройка доменов").

## Ограничения

- Правило **не ретроактивное** — уже накопленные исторические конверсии,
  ошибочно приписанные платёжному домену, не переразметятся задним числом.
  Эффект будет виден только на новом трафике после настройки.
- Если на сайте несколько способов онлайн-оплаты (разные платёжные шлюзы),
  нужно добавить домен каждого, иначе часть конверсий продолжит утекать.

## Подтверждённая на практике находка: почему GTM-тег `ignore_referrer` НЕ работает

**Проверено на [[../../Клиенты/Корогва/index|Корогва]], 2026-09-28** (реальная покупка на
1 ₴, полный проход DevTools + GTM Preview — см. [[../../Клиенты/Корогва/Решения|Решения]],
запись 2026-09-28). У клиента был настроен не Admin-список нежелательных переходов, а
альтернативный способ через сам GTM: RegEx-переменная `Is Unwanted Referrer` на
`{{Referrer}}` (паттерн покрывал monobank.ua/liqpay.ua/privatbank.ua/wayforpay.com/
fondy.eu/portmone.com), подключённая к параметру `ignore_referrer` в GA4
Configuration-теге (Google Tag) с триггером "Initialization - All Pages". По
описанию это должно работать так же, как Admin-настройка — на практике не сработало:

- `document.referrer` на реальной странице "Спасибо" после возврата с оплаты
  подтверждённо равен `https://pay.monobank.ua/` (это ожидаемо и нормально сам
  по себе — браузер не подделывает referrer, `ignore_referrer` не должен на это
  влиять).
- Payload реального `collect`-запроса с событием `custom_purchase` (проверено
  через Network → фильтр `collect` → вкладка Payload) показал `dr:
  https://pay.monobank.ua/` **и** `sct: 1` (session count = 1, то есть GA4 всё
  равно завёл это как новую сессию) — параметр `ignore_referrer` в payload
  вообще не появляется.
- Вероятная причина (не подтверждена на уровне исходников GA4/gtag.js,
  архитектурная гипотеза по потоку выполнения тегов): GA4 обрабатывает
  referrer и решает, заводить ли новую сессию, в момент самого раннего hit'а
  на странице — `ignore_referrer`, заданный в GTM-теге с триггером
  Initialization, физически не успевает примениться раньше этого момента.
  Настройка при этом выглядит полностью корректной (переменная, паттерн,
  триггер, подключение параметра — всё верно), баг не в опечатке конфигурации,
  а в том, что сам подход "клиентский `ignore_referrer` через GTM" ненадёжен
  для перехвата session-defining referrer.

**Практический вывод**: если у клиента настроен именно такой GTM-подход (а не
родной Admin → Unwanted referrals в самом GA4-ресурсе) — не считать вопрос
закрытым только по виду конфигурации, проверять эмпирически через реальную
покупку + Network payload (см. методологию проверки ниже), даже если тег и
переменная выглядят технически правильными.

## Как проверить эмпирически (методология, не полагаться на конфиг "на глаз")

1. Пройти реальную покупку до конца (нужен тестовый товар на минимальную сумму)
   с открытыми DevTools, включить "Keep log on navigation" (Console) и
   "Preserve log" (Network) заранее — переход на платёжный шлюз и обратно
   может не быть автоматическим редиректом, а кнопкой на стороне шлюза,
   старые логи иначе потеряются.
2. На странице "Спасибо" в Console выполнить `document.referrer` — если там
   домен платёжной системы, это ожидаемо и само по себе не говорит о поломке
   или её отсутствии.
3. В Network найти реальный `collect`-запрос конверсионного события (искать по
   `en=custom_purchase` или названию своего события, и/или по `transaction_id`
   в параметрах) — общих `collect`-запросов на странице может быть много
   (просмотр страницы, scroll-события, несколько параллельных GA4-ресурсов,
   Google Ads conversion), важно найти именно тот, что относится к покупке.
4. В Payload смотреть `dr` (referrer, дошедший до события) и `sct`/`sid`
   (session count/id — покажет, посчиталась ли сессия новой). Наличие/отсутствие
   `ignore_referrer` в самом payload — тоже сигнал, что параметр физически не
   передался туда, где мог бы повлиять.
5. Если используется GTM (не только нативная настройка GA4) — дополнительно
   зайти в сам контейнер и посмотреть, к какому типу тега (Configuration vs
   Event) и с каким триггером подключена переменная-исключение — Configuration
   тег с Initialization-триггером не гарантирует, что успеет сработать раньше,
   чем GA4 определит сессию.

## Статус

Частично протестировано на практике: **GTM-вариант (`ignore_referrer` через
RegEx-переменную на Configuration-теге) подтверждённо НЕ работает** — см. кейс
[[../../Клиенты/Корогва/index|Корогва]] выше. **Родной Admin-механизм GA4 (Unwanted
referrals / Cross-domain measurement, описанный в разделе "Как исправить" выше)
ещё не проверен на практике** — это следующий шаг, который нужно настроить и
протестировать тем же методом (реальная покупка + payload), прежде чем считать
его надёжным решением. Не путать эти два статуса.
