# Google Ads: номер звонящего недоступен через API, только вручную

Найдено на [[../../Клиенты/LuxeBrokers/index|LuxeBrokers]] (2026-09-04) при
попытке автоматически выгрузить номера звонящих по конверсии "Calls from ads"
для сверки с колл-трекингом (Ringostat).

## Ограничение

Ресурс `call_view` в Google Ads API отдаёт код страны (`caller_country_code`)
и код региона/города (`caller_area_code`) звонящего, но **не полный номер
телефона** — это намеренное privacy-ограничение Google, подтверждено
официальной документацией (developers.google.com/google-ads/api/fields/.../call_view)
и форумом разработчиков Google (groups.google.com/g/adwords-api). Полный номер
в API не выдаётся ни в одной версии.

При этом тот же полный номер **виден в интерфейсе** Google Ads — отчёт
"Call details" (Reports → предопределённые отчёты → Calls, либо через
Tools → Conversions → сама conversion action "Calls from ads" → сегмент Call
details). Экспортируется вручную в CSV/Excel с колонками: Start time,
Duration, Caller country code, Caller area code, **Caller phone number**,
Recording, Status, Call source, Call type, Campaign.

## Практическое следствие

Если нужна сверка звонков Google Ads с внешним колл-трекингом (Ringostat,
Callibri и т.п.) по факту "тот же самый номер" — автоматизировать выгрузку
номеров со стороны Google Ads через API нельзя, только ручной экспорт отчёта
Call details клиентом/аккаунт-менеджером из интерфейса. Сверка объёмов
(количество звонков, конверсий) через API — доступна как обычно
(`metrics.conversions` по campaign/segments), не хватает именно номера для
поштучного сопоставления.

**Технический нюанс формата ручного экспорта:** файл экспортируется в
кодировке UTF-16 (с BOM) и разделителем-табуляцией, не обычная UTF-8 CSV —
первые 2 строки файла содержат заголовок отчёта и период дат, реальные
колонки начинаются с 3-й строки. При автоматической обработке такого файла
скриптом — явно указывать `encoding="utf-16"` при чтении, иначе
получается нечитаемая кириллица/мусор вместо текста (не ошибка, файл валиден,
просто неверно угадана кодировка).

## Статус
Подтверждено на практике 2026-09-04 (LuxeBrokers) — реальный экспорт Call
details из интерфейса клиента содержал полный номер звонящего, попытка
получить его же через Google Ads API (`call_view.caller_area_code`/
`caller_country_code`) технически невозможна в принципе, не ошибка настройки
запроса.

## Дополнение 2026-11-05: звонки из объявлений по кампаниям — сопоставление с Ringostat по времени (протестировано)
Номера нет, но `call_view` отдаёт для каждого звонка **время начала, длительность, код региона и кампанию** (`campaign.name`). Фильтр `segments.date` для него недопустим, фильтровать надо по `call_view.start_call_date_time >= 'ГГГГ-ММ-ДД 00:00:00'`. Время в часовом поясе аккаунта (Варшава); у Ringostat `calldate` приходит со смешанными смещениями, парсить с `utc=True` и переводить в Варшаву.
- **ProfiMet, 20.10–05.11:** 13 звонков в `call_view`, все 13 нашлись среди входящих Ringostat пула «Google CPC calls from ads» по времени с точностью 0–2 секунды. Длительность у Google на 10–20 с больше (считает с набора, Ringostat с ответа); звонки Google 7–11 с у Ringostat имеют 0 с разговора. Без пары в Google остались 5 звонков Ringostat (3 повторных звонящих, 2 «PROPER» 28.10 и 29.10), причину не знаю.
- **EkspertAgro, 20.10–05.11:** 5 звонков `call_view`, все кампании `general_pmax_rozmiary`; в Ringostat они лежат в пуле «Google CPC General - pmax» (отдельного пула «из объявлений» нет). Этот пул сторож не относит ни к одной кампании (`__unresolved_pmax__`), поэтому разбивку по кампаниям даёт только Google Ads.
- **Вывод:** кампанию для звонка из объявлений можно узнать без отдельных номеров на кампанию: звонок Ringostat ↔ строка `call_view` по времени ±3 минуты. Работает для звонков через подменный номер Google (звонковый ассет, call-only); звонки с сайта по номеру не из ассета сюда не попадают.
- Скрипты проверки — одноразовые, в scratchpad сессии 05.11; постоянный инструмент — в задаче «Единый стандарт заявки».
