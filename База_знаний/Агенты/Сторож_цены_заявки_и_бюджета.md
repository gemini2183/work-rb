# Агент «Сторож цены заявки и бюджета»

Режим: чтение + запись по заранее согласованному правилу (пауза, возобновление, бюджет). Правила и обоснование — [[../Паттерны/Сторож-цены-заявки-допустимый-расход-и-бюджет-по-шагам]]. Инструмент: `Скрипты/gads_spend_guard_cpa.py` (по умолчанию dry-run).

## Вводные
- Клиент, `customer_id`, id кампаний под охраной.
- Цель заявки по кампании (из плана месяца «Цели2 Адвайта», `read_plan`; тесты чуть мягче), аванс (2.0), базовый бюджет и предел бюджета, дневной план проекта.
- Источники заявок: конфиг проекта мониторинга `E:\PythonProjects\RedBird\monitoring scripts\monitoring\config\<клиент>.yaml` (Ringostat, Supabase, Telegram) — см. `Инфраструктура.md`, запись 2026-10-12.

## Шаги
1. **Подготовка (чтение).** Снимок кампаний (статус, стратегия, бюджет, расход, заявки сегодня); план месяца и «нужная цена заявки на остаток»; проверка, что нет конфликтующих старых сторожей (процессы `gads_spend_guard*.py`).
2. **Таблица плана и параметры.** Цели, базы, пределы, режимы (`--allow-reenable`, `--allow-budget`, `--telegram`). Показать, что сторож сделает на текущих цифрах (прогон без `--execute`).
3. **«Да» пользователя**, затем запуск с `--execute`. Если система блокирует запуск как запись в рабочий кабинет — остановиться, объяснить, получить явную просьбу «запусти».
4. **Наблюдение.** Фоновый процесс + Monitor по строкам `ПАУЗА|ВОЗОБНОВ|БЮДЖЕТ|ПРЕДУПРЕЖД|ошибка`; тишина не успех — периодически проверять процесс и последнюю строку.
5. **После событий.** Прочитать обратно бюджет и статус из кабинета; записать в `Журнал_изменений.md` (было → стало, снимок «до», откат, для отчёта EN).
6. **Конец дня и сессии.** Процесс живёт, пока открыта сессия: при закрытии перезапускать командой из `Задачи.md`; вечерний возврат бюджета происходит только при запущенном сторожe.

## Утренняя проверка (договорённость пользователя 12–13.10)
Пользователь согласовал, что утро по клиенту — это одна последовательность, а не отдельные просьбы: (1) жив ли процесс сторожа и последняя строка лога; (2) бюджеты на день возвращены к базовым (то, что вчера подняли люфтом или вручную, откатывается) — сторож делает это первым тактом дня, при остановленном сторожe — скриптом `gads_set_campaign_tcpa_budget.py`; (3) запуск сторожа `gads_spend_guard_cpa.py --client <Имя> --execute --telegram`; (4) проверки дня из `Задачи.md` и отчёт одной таблицей. 13.10 агент вместо этого трижды предложил «поставить 50 € после «да»» — это ошибка исполнения договорённости, не правило. Если система блокирует запуск процесса или запись из сессии — сказать об этом первой строкой и дать готовую команду.

## Ошибки и уроки (12.10)
- Файл состояния за сегодня, созданный прежней версией скрипта, ломал ветку бюджета (`KeyError`): при изменении формата состояния дописывать недостающие поля.
- Явно заданный `--base-budget` важнее сохранённого, иначе после ручного подъёма сторож «возвращал» старую базу.
- Первая проверка занимает ≈ 30 секунд (выгрузка Ringostat с 2025-08-01); цикл 2 минуты.
- Нет заявок по группам PMax (идентификатор группы в звонке пуст) — охрана только на уровне кампании.
- Сторож считает формы Supabase только с UTM: формы без кампании не учитываются (риск ложной паузы).
- Не обещать «мгновенную защиту»: расход в API с лагом, бюджет — единственный мгновенный тормоз.
- Объяснять пользователю одним примером и по-человечески: слова «аванс», «люфт», «стоп-линия» без расшифровки он не принимает.

## Ошибки и уроки (13.10)
- **Режим «только план» не должен менять состояние.** 13.10 пробный прогон записал в боевой файл отметку «утро сделано»; боевой запуск пропустил откат бюджета 100 → 50. Теперь план пишет в `*_plan` файлы, отметка ставится только после реальной записи.
- **Правило «темп» после перезапуска.** Опорная точка могла оказаться на 44 минуты раньше окна, и рост «+20.8 € за 30 минут» на деле был 22% бюджета за 30 минут: ложная пауза `pmax01_call_test`. Рост приводится к окну по фактическому возрасту точки.
- **В конфиге нельзя задавать период цикла для пробного такта.** `loop_min` из `guard_config.yaml` зациклил «один такт»; для одного такта — `--once`.
- **Процесс на компьютере умирает молча** (12.10 в 18:07, 13.10 около 09:30). Пульс `heartbeat_min` — сообщение «сторож жив» в Telegram; пауза в сообщениях = процесс остановлен.
- **Один сторож на клиента.** Правило «(аванс + заявки) × цель» подходит любому типу кампании; `hard_mult`, `total_limit`+`since` и `budget_control` задаются на кампанию в `Клиенты/<Имя>/guard_config.yaml`; старый `gads_spend_guard.py` — только для разовых случаев.
- **Заявки Demand Gen с динамическим пулом по `utm_campaign` не проверены на живом звонке** — при первом расходе смотреть `n` в логе.

## Запуск и присмотр (с 2026-11-05)
Боевые сторожа поднимаются сами при входе пользователя в Windows: задачи `AdWhite Guard ProfiMet` и `AdWhite Guard EkspertAgro` → `Скрипты/run_guard.ps1`. Вручную `python … --execute --telegram` больше запускать не нужно: если процесс клиента уже работает, обёртка его не дублирует, а следит за ним. После правки кода или `guard_config.yaml` сторож надо перезапустить: остановить python-процесс клиента (`Stop-Process -Id <PID>`), обёртка поднимет новый через ≤ 60 с (или сразу запустить вручную, обёртка подхватит). Диагностика: `_guard_wrapper_<Клиент>.log` (события обёртки), `_guard_*.out` (вывод), сообщение «Сторож запущен» в Telegram на каждый старт, тишина «сторож жив» > 2 ч = охраны нет. Подробности и риски — `Инфраструктура.md`, запись 2026-11-05 (12:15).

## Ошибки и уроки (04.11)
- **«Темп» только при нуле заявок за день.** Условие «в окне заявок не прибавилось» давало ложные паузы на днях, где заявки уже были (23.10, 26.10 EkspertAgro). Порог выбирать по истории клиента: `Скрипты/guard_pace_calibration.py`; новому клиенту сначала 40% бюджета за 30 минут. Подробности — `Инфраструктура.md`, запись 2026-11-04.
- **Вмешательства и незнакомые кампании (04.11).** Сторож охранял только кампании из списка; новая включённая кампания, бюджет, снижённый посреди дня руками, или смена стратегии оставались незамеченными (15.10 `pmax1_test`: расход 157 при бюджете 120 разделили на уже сниженные 50 и получили ложное «3× бюджета»). Теперь: сравнение с прошлым тактом, пределы от максимума бюджета дня, незнакомая кампания под защиту с `default_target`. Ключи верхнего уровня `guard_config.yaml` писать до списка `campaigns`, иначе файл не читается.

## Ошибки и уроки (05.11)
- **Сбой чтения Ads не должен быть тихим.** 04.11 в 21:40:39 упали оба процесса в одну секунду (`ServiceUnavailable`), кампании пропускались без повтора. Теперь: повтор чтения, быстрый повторный такт (30 с) и сообщение в Telegram после 3 тактов подряд. Подробности — `Инфраструктура.md`, 2026-11-05.
- **Звонки из объявлений: кампанию даёт `call_view` по времени** ([[../Инструменты/Google-Ads-Calls-номер-звонящего-недоступен-через-API]]). Пока сторож берёт их из конверсий Ads; переход на `call_view` — в задаче «Единый стандарт заявки».
- **Счёт заявок сторожа — единый стандарт (05.11):** Ringostat + Supabase + `call_view`, не конверсии Ads. Источники заявок, диагностика безметочных форм и ограничения — `Скрипты/README.md`, раздел `leads_standard.py`. Старый счёт и новый на истории 29.10–04.11 отличались на 2 из 28 (ProfiMet) и 1 из 7 (EkspertAgro).
