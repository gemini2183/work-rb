# Проект: агент ежемесячного клиентского отчёта

Разработан по запросу пользователя (2026-10-08): «делай проект месячного агента, возможно, мы потом возьмём идеи». Источники данных, которые вики уже копит: [[../../Клиенты/ProfiMet/Журнал_изменений]], [[../../Клиенты/ProfiMet/Эксперименты]], [[../../Клиенты/ProfiMet/Хроника_2026-10]]. Короткие требования к данным — [[Отчёт_клиенту_ежемесячный]].

## Цель и принципы
1. Клиент за 2 минуты понимает: сколько заявок, сколько стоит заявка, как это относится к плану и к прошлому месяцу, что мы сделали и зачем, что будет дальше.
2. Главный результат — **объём заявок и цена заявки**; потом качество и объяснения.
3. Честность: измеренное отделено от гипотез; отрицательный результат подаётся как проверенная гипотеза («проверили → узнали → что делаем»), не скрывается и не приукрашивается.
4. Выглядеть экспертами через **логику решений** (основание → ожидание → итог), а не через красивые слова.
5. Внутренняя кухня (методики сверки, пороги, стоп-правила тестов, поправки по ходу) в отчёт не попадает; она остаётся в вики.

## Архитектура: три слоя
| Слой | Роль | Режим | Выход |
|---|---|---|---|
| 1. Сборщик данных | скрипт без LLM: цифры из Ads API, Ringostat, форм, плана; разбор журнала и реестра экспериментов | чтение | `report_data_<клиент>_<ГГГГ-ММ>.json` (контракт ниже) |
| 2. Автор | LLM по шаблону и данным; пишет текст отчёта | чтение | черновик отчёта |
| 3. Проверяющий | LLM + правила: сверяет каждое число с JSON, ищет гипотезы в роли фактов, нарушения формата, внутренний жаргон | чтение | список замечаний или «чисто» |
Человек (специалист) читает итог и отправляет; агент сам клиенту не пишет.

## Контракт данных (JSON, поля сборщика)
- `period`, `prev_period`, `client`, `plan` (заявки, CPA, бюджет — Google-таблица плана `read_plan`).
- `totals` для периода и предыдущего: `leads` (= звонки Ringostat + формы), `calls`, `forms`, `cost`, `cpa`, `clicks`, `impressions`, `conversion_rate`; для каждого числа поле `source` (ads / ringostat / form) и `slice` (кампании, сети, даты).
- `by_type`: Search / Performance Max / Display / Demand Gen — те же поля (общая картина → части).
- `by_campaign`: по каждой кампании, где расход больше порога; «ретро» и тесты помечены `kind: test`.
- `changes`: из журнала изменений: `id`, `date`, `object`, `what`, `why`, `result_status` (measured / hypothesis / no_data), `result`, `client_line_en`, `experiment_id`.
- `experiments`: из реестра: `id`, `hypothesis`, `basis`, `expectation`, `verdict` (confirmed / not_confirmed / partial / running), `outcome`, `next`.
- `caveats`: флаги ограничений (клик по номеру завышен; звонки статического канала без кампании; потеря на пути Ringostat → GA4; малые выборки с числом конверсий).
- `baselines`: значения «до» из реестра для оценки эффекта.

## Шаблон отчёта
1. **Итог месяца** (таблица): заявки, цена заявки, расход; месяц против прошлого и против плана; одна фраза вывода.
2. **Что изменилось в результатах**: Search, Performance Max и т. д. — общая картина, потом кампании; в каждом блоке три оси: объём, стоимость, качество.
3. **Что мы сделали и зачем** (5–8 пунктов): из `changes` со статусом `measured` или понятной пользой; формулировки «Для отчёта клиенту (EN)» переписываются на язык клиента.
4. **Что проверяли**: для каждого завершённого теста одна строка: гипотеза → результат → что решили; для идущих — «узнаем к такой-то дате», без внутренних порогов.
5. **План на следующий месяц**: 3–5 пунктов с ожидаемой пользой.
6. **От клиента** (если нужно): подтверждения фактов, акции, материалы.

## Как писать отрицательный результат
Шаблон: «Мы проверили [идея] — [цифра: что получили против того, что ожидали]. Это показало [причина, измеренная]. Поэтому [решение и срок]». Примеры для ProfiMet: «возврат старых кампаний на цель „клик по номеру“ дал 105 € за звонок вместо ожидаемых 40 €: клики по номеру в 4–6 раз чаще реальных звонков, поэтому мерим эффект только по звонкам»; нельзя: «тест не удался», «к сожалению», «из-за сложной ситуации».

## Правила статуса результата
- `measured`: есть цифра, период, источник и база сравнения → можно в клиентский текст.
- `hypothesis`: в клиентский текст только как «проверяем», без обещания эффекта.
- `no_data`: не упоминать как результат; можно как «запущено, оценим к дате».

## Чек-лист проверяющего (автоматический + LLM)
1. Каждое число есть в JSON; суммы сходятся (заявки = звонки + формы; части = целое с допуском округления).
2. В каждом блоке есть объём, стоимость и качество.
3. Периоды и срезы названы; один знаменатель в одном сравнении.
4. Нет гипотез в роли результатов; нет слов-заглушек («значительно», «заметно» без цифры).
5. Нет внутреннего жаргона и пометок («важная поправка», «validate_only», «окно покоя», стоп-правила).
6. Нет фактов о продукте, не подтверждённых `Креативы/Факты_сайта_*` (например, «100 000+ заказов»).
7. Порядок: таблица → вывод → буллеты; от общего к частному.
8. Малые тесты не вынесены отдельным разделом без влияния на вывод.

## Промпты (черновики)
**Автор:** «Ты специалист по контекстной рекламе. Напиши ежемесячный отчёт для клиента по JSON и шаблону. Главный результат — заявки и цена заявки; сначала таблица, потом короткий вывод и буллеты; от общего к частному. Используй только факты из JSON; гипотезы подавай как „проверяем“. Отрицательные результаты — по шаблону „проверили → узнали → решили“. Без внутренней терминологии. Язык: [язык клиента].»
**Проверяющий:** «Проверь отчёт по чек-листу из восьми пунктов; для каждого замечания укажи строку отчёта и поле JSON. Не переписывай отчёт, только перечисли проблемы.»
