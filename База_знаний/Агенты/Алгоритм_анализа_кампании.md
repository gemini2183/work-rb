# Алгоритм анализа кампании

Что делаем, в каком порядке и зачем. **Чем считаем на каждом шаге** - в [[Методология-выбора-метода-и-периода-анализа-кампаний]] (у каждого шага ниже указан её раздел). Алгоритм общий, без цифр клиентов: числа и особенности источников клиента - в `Клиенты/<Имя>/Калибровка_методов.md` (ProfiMet: [[Калибровка_методов]]). Клиентам с учётом продаж добавляется [[Алгоритм_анализа_кампании_продажи]]. Риск - [[Политика-риска-планов-оптимизации]].

Три этапа. Этап закрывает пользователь, следующий без этого не начинаю.

## Этап 1. Оценка месяца против КПИ
**Зачем:** понять, где мы против плана месяца, и выбрать целевые показатели для этапа 2. Без этого анализ кампаний не знает, какой цели добивается.
**Метод:** методология, «Для этапа 1».
1. План месяца из таблицы КПИ: заявки, цена заявки, бюджет (`read_plan`).
2. Факт на дату, темп к плану, прогноз закрытия (`pace_vs_plan.py`, раздел [4] `state_digest.py`).
3. Допустимая цена заявки T (у клиентов с продажами - по приложению о продажах).
4. Сколько нужно в день до конца месяца и цена заявки на остаток.
5. Какие кампании не входят в проект (Паспорт клиента).

**Выход:** (а) разрыв до плана и целевые показатели (T, нужный объём в день) - объяснение простыми словами, число с «откуда взялось»; (б) обновлённая таблица клиента с графиками, где пользователь сам проверяет тренды: [[Дашборд_этапа_1]]. Без обновлённой таблицы и ссылки на неё этап не считается готовым. У клиентов с продажами в Этап 1 добавляется расчёт доли «заявка → продажа», T и прогноз цены продажи ([[Алгоритм_анализа_кампании_продажи]]).

## Этап 2. Анализ кампаний
Источник данных: срезы `Скрипты/campaign_slices.py` (шаг 2.9) и заявки по основному источнику клиента.

### 2.1 Выход: 5 ответов
1. Где разрыв до плана по кампаниям (вклад каждой).
2. Из-за чего: показы → CTR → цена клика → коэффициент конверсии (потеря показов по бюджету / по рейтингу).
3. Насколько верить: интервал у каждой цифры, «данных нет» при малых n, альтернативные причины исключены (правки, трекинг, сезон, выходные).
4. Рычаги с оценкой эффекта и неопределённости при средней цене заявки ≤ T.
5. Что не знаем: пробелы и недостающий источник.

Итог: приоритизированная таблица «кампания → причина → рычаг → эффект и неопределённость».

### 2.2 Выбрать период анализа (до разложения)
**Зачем:** слишком короткое окно даёт шум, слишком длинное смешивает разные состояния кампании. **Метод:** методология, «шаг 2.2». Сверху окно ограничено календарным месяцем.

### 2.3 Найти границу окна
**Зачем:** данные до реального сдвига описывают другую кампанию. Граница - слом по данным, а не дата правки. **Метод:** методология, «шаг 2.3» (слом, оговорки, чистые дни). Инструмент: `window_check.py`.

### 2.4 Оценить достоверность и обойтись малыми данными
**Зачем:** решения принимаются в рамках месяца на малых данных, поэтому у каждой цифры названа достоверность, а решение - по вероятности. **Метод:** методология, «шаг 2.4» (лестница методов, семья кампаний, интервалы, уровни 80/95 %, поправка на много срезов).

### 2.5 Горизонт
Остаток календарного месяца. Действия быстрые и обратимые, окно действия от ~недели до конца месяца; медленное (новые кампании, PMax с обучением) - только из выделенной доли бюджета. **Окно анализа ≠ окно действия.**

### 2.6 Быстрые замеры и правило остановки
**Зачем:** заранее знать, что считаем сдвигом, и когда остановить рычаг. **Метод:** методология, «шаг 2.6».
| Рычаг | Ведущий показатель |
|---|---|
| бюджет | показы/клики в тот же день |
| ставки / CPA | показы, доля показов, цена клика, 1-3 дня |
| тексты | CTR |
| аудитория | охват, CTR, цена клика, микроконверсии |

Порог «сдвинулось» задаётся заранее. Тесты - доля бюджета и параллельный контроль, не «до/после».

### 2.7 Источники заявок
**Зачем:** кабинет может занижать или завышать заявки. **Метод:** методология, «шаг 2.7».
- Основной источник - независимый от кабинета (коллтрекинг, база форм, CRM); звонки из объявлений - `call_view` Google Ads.
- Конверсии кабинета - направление. Из кабинета без оговорок: показы, клики, CTR, цена клика, расход, потеря показов.
- Источники клиента и их расхождения - в его `Калибровка_методов.md`.

### 2.8 Что не знаем
Допустимые рычаги, размер шага, срок проверки, стоп-правило, политика риска («можем недобрать заявки, но не сольём бюджет»).

### 2.9 Срезы кампании (обязательно перед рычагами)
**Зачем:** найти, где теряются деньги и объём. Один заход скрипта за точные даты окна (`--client-folder`, `--out-dir`, `--from/--to`, `--exclude-days`, `--compare-from/--compare-to`; параметры - в `Скрипты/campaign_slices.py`).
- **Срезы:** потеря показов по дням (рычаг бюджета только если потеря по бюджету > 0); группы; ключи + тип соответствия; поисковые запросы; устройства; регионы; час; день недели; пол; возраст; сеть; объявления и ассеты RSA; посадочные; аудитории; группы ресурсов (PMax).
- **Каждая таблица:** показы, клики, CTR, цена клика, расход, доля расхода, конверсии кабинета, цена конверсии с интервалом, итог и сверка с итогом кампании.
- **«Расход без конверсий»:** 0 конверсий и расход ≥ 2T - кандидат на проверку, не вывод (смотрим, не набрал ли срез расход недавно, правки/паузы, конверсии по основному источнику). Много срезов - ложные находки, необратимые шаги - по 95 %.
- **Заявки по срезу** привязывать только где возможно (день недели, час звонков); иначе - конверсии кабинета как направление.
- **Нет в данных** для типа кампании печатается в конце файла. Особенности PMax - [[Аналитик_PMax_диагностика]].

## Этап 3. План «было → станет»
**Зачем:** правка в кабинете - только осознанная и обратимая.
1. Таблица `Объект | Действие | Было → Станет | Откуда факт`, допущения отдельным блоком (протокол записи в кабинеты, CLAUDE.md).
2. Для каждого рычага: ожидание, порог успеха, стоп-правило, дата оценки, откат (`Эксперименты.md`).
3. Тесты - из заранее выделенной доли бюджета (методология, «Для этапа 3»).
4. Запись только после «да»; затем чтение обратно и запись в вики.
