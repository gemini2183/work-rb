# Оптимизация агентов: где мы и что дальше

**Как использовать.** В сессии «займёмся оптимизацией агентов» читать только этот файл, затем по ссылкам из раздела 6. После каждой сессии оптимизации дописывать разделы 3–7 (а не только журналы клиента). Журналы (Хроника, Журнал_изменений) ссылаются сюда.

## 1. Цель и критерии
- **Конечная цель (пользователь, 2026-11-12):** всё работает автоматически с минимальным участием пользователя: он даёт ОДНУ задачу, оркестратор сам раздаёт её нужным агентам, агенты выполняют и отчитываются. Точки согласования «да» остаются там, где запись во внешние кабинеты (политика протокола записи). Это направление, не задача текущей сессии; ближайшие шаги — разделы 4–6 ниже и схема `Супервайзер_и_исполнители.md`.
- **Что мешало 12.11 на практике (Landver, Ped/Bike), учесть при построении оркестратора:** (1) правило сверки текстов лежало в памяти строкой-указателем, я его не открыл и ошибся повторно — правила для агентов держать в `CLAUDE.md` и в плейбуке самого агента, а не только в памяти; (2) в середине сессии узкие агенты (fact-checker, page-check, planner, executor и др.) стали недоступны как типы, остались универсальные — оркестратор должен уметь запустить универсального агента с плейбуком из `База_знаний/Агенты/` как задание; (3) тонкие проверки (ассеты) я сначала сделал не по всем типам — у оркестратора должен быть чек-лист полноты («какие типы ассетов / уровней проверены»), а не память исполнителя.
- Не терять лимит Claude Code на груз до первой команды и на перечитывание журналов.
- Критерий готовности (П-016): агент-исполнитель получает **бриф**, а не список «прочитай всё»; последний контекст агента < 100 тыс., вес < 1 млн (`python Скрипты/claude_usage.py --agents --session <id>`).
- «Вес» — сравнительная мера из шапки `claude_usage.py` (ввод 1,0; запись кэша 1,25 / 2,0; чтение кэша 0,1; вывод 5,0). Множитель вывода для Sonnet 5.5 не проверен.

## Итоги обсуждения 2026-11-12: схема экосистемы (диалог с пользователем)
**Статус:** принято в целом («план очень нравится»); детали проверяются в фазе 1. Отдельно помечено: «решение пользователя» и «предложение, ответа нет».

### 1. Цель и фазы (решение пользователя)
Конечная цель — минимум участия пользователя: одна задача на входе, остальное делают маршруты и агенты; «да» остаётся на записи во внешние кабинеты. До полной доработки пользователь участвует активно. Автоматизацию строим в три фазы, раннер — последним, на проверенных маршрутах:
1. **Вручную с пользователем.** Схема, недостающие скрипты и математика аналитика, формат плана, пакет контекста, отладка на **боевых задачах**: они и так идут постоянно, агентов, скрипты и поправки встраиваем в них (решение пользователя 12.11). **Песочница** (тестовое юридическое направление в отдельной папке клиента и тестовые кампании в аккаунте) — только для сценариев, которых сейчас нет среди реальных задач (например, «новое направление с нуля», пока такого реального заказа нет). Замеряем вес каждого шага.
2. **Полуавтомат.** Маршруты идут по рецептам, пользователь даёт только «да» (таблица решений).
3. **Раннер.** Утренний автозапуск по проектам: скрипт-раннер читает доску, по рецепту маршрута запускает короткие неинтерактивные сессии (`claude -p` по документации Claude Code; в нашей среде не проверено), пересоздаёт их сам, останавливается на воротах «да» и при ошибках, шлёт уведомления. Нарезку на этапы делает раннер (код), LLM — только там, где нужно суждение. Параллель по клиентам: блокировка на клиента, общая квота API (15 000 операций в день) и общий лимит подписки.

### 2. Оси схемы: задача = маршрут, агент = роль
- **Задача** (то, что пользователь ставит) — это **маршрут**: короткий рецепт, какие роли звать и в каком порядке. Задачи независимы, анализ нужен не всегда. Библиотека маршрутов: 8–10 страниц, по странице на маршрут. Её сейчас нет (маршруты — в Хрониках и в голове супервайзера).
- **Агент** — роль, нарезанная по режиму доступа, риску и нужному контексту, а не по объектам (семантика, тексты, ставки — разделы внутри карточки, не отдельные агенты). Причина: старт агента ~24 тыс., дробление веса не снижает (замер wiki-recorder 12.11).
- **Задачи Google Ads, независимые** (список с пользователем): новое направление с нуля; правка существующей кампании (ключи, минуса, тексты, ассеты, ссылки, ставки, бюджет, расписание, гео, статус); смена посадочной; новый тест; разбор кампании; оценка результата правки/теста; сводка состояния; сверка конверсий; проверка текстов и ассетов на соответствие странице; план месяца и бюджета; сторожа; отчёт клиенту.
- **Директ** по задачам почти совпадает с Google Ads, но набор доступных срезов другой (Директ: условия показа, регионы, устройства, места показа, объявления, пол, возраст, доход; отчёт по запросам только за 180 дней; статус обучения стратегии API не отдаёт; Google: сети, запросы, потеря показов по бюджету/рейтингу, оценки качества, позиции/часы, гео кликов, недействительные клики, `change_event`, срезы PMax). Решение по структуре: **чтение общее, карточки срезов на каждую площадку**; **запись — отдельный исполнитель на площадку** (Директ пишется через ЕПК v501, другой протокол). Срезы задаются параметром задания; нет среза на площадке — «срез недоступен», без молчаливой подмены. Пробелы идут в очередь `script-builder`.
- В «Протоколе записи» `CLAUDE.md` назван Google Ads (и OpenAI Ads), запись в Директ не прописана — решить (нужно «да» пользователя на правку `CLAUDE.md`).

| Планировщик | агент (чтение и план) | выбор и расчёт; предлагает рекомендуемый вариант по политике риска и честно перечисляет альтернативы, пользователь утверждает |

### 4. Маршрут «новое направление с нуля» (эталонная схема)
Касаний пользователя: 4 (фраза на входе, «да» на план, тестовая заявка/звонок, «включай»).
```
0 пакет контекста [скрипт] → 1 разведка страницы и трекинга [агент]
   страница не готова → стоп, одной строкой пользователю
 → A рынок и конкуренты [агент, веб]: объявления, сайты, офферы → 05_рынок.md (наблюдаемые факты со ссылками)
 → B семантика + минус-слова [агент + скрипты]: ключи из рынка/словаря тем/Keyword Planner, конфликты с минусами других кампаний; пользователь перепроверяет → 22_семантика.md
 → C прогноз стоимости и вероятностей [скрипт]: приор по аналогам (цена клика, коэффициент конверсии), Монте-Карло, P(цена заявки ≤ цели) при разных бюджетах
 → D решение о запуске: бюджет, доля на тест, стоп-правила [пользователь + супервайзер]
 → тексты по группам (копирайтер → контролёр фактов, смысл против страницы) → план (машинный + таблица для пользователя, поля для вики)
 → «да» на план (кампания только на паузе) → запись [скрипт-раннер] + чтение обратно

 → день оценки: window_check → аналитик → «Итог: ожидали / получили».
```
Семантика идёт **после разведки и до текстов**: тексты и группы зависят от тем и ключей (адаптер объявлений подставляет фразу темы). Проверка конфликтов с минусами старых кампаний — в семантике, не после записи (ProfiMet `montaz`). Списки ключей остаются в файле, в ответ — сводка по группам. Для PMax и Shopping этот этап другой (сигналы аудиторий, фид); не проработан. Точки, где пользователь решает по семантике (темы и услуги, match type, жёсткость минусов), — открытый вопрос.

### 6. Аналитик: только математика (решение пользователя)
- Любой вывод строится только на формулах статистики и теории вероятностей; никаких выдуманных объяснений.
- Реализация: (а) LLM не считает, числа приходят из скриптов; (б) формат утверждения «метрика → значение → n → метод → интервал/вероятность → источник», утверждение без метода не попадает в отчёт; (в) проверяющий скрипт сверяет каждое число текста с JSON скриптов, не нашлось — отчёт отклонён; (г) ниже минимума данных — «вывода нет», решение тогда принимается по политике риска, а не аналитиком; (д) причину доказывает только эксперимент, наблюдения дают вероятность связи; версии допустимы только как помеченные гипотезы с планом проверки.
- **Математический аппарат построен не весь** (по `Алгоритм-анализа-эффективности-кампании-блок-схема.md` на 05.10; что сделано позже, не проверено): готов блок 1 `campaign_analyzer` (сверка с Ringostat, план против факта); подшаги 3–7 (окно данных, история правок, рынок, всплески, ранжирование «деньги × вероятность») не построены; байесовский анализ срезов — по группам, устройствам, дням недели, а гео, аудитории, запросы — нет. Порядок: сначала достроить скрипты, потом оформить агента, который их только вызывает.
- **При нехватке данных** (не 99 %): байесовская оценка с информативным приором (бета-биномиальная для конверсии, гамма-пуассоновская для темпа заявок), иерархическое сжатие, решение по ожидаемым потерям, заранее заданные стоп-правила, планирование «сколько стоит узнать» (если дороже доли теста — «вывод невозможен в этом бюджете»), распределение бюджета между вариантами по Томпсону, опережающие метрики только после калибровки, причина — Google Ads Experiments. Порог уверенности по классу риска: 70–80 % для обратимого и дешёвого, выше для необратимого. Запрещено: перебор срезов без поправки, остановка по «красивому» результату, причина по совпадению дат. В отчёте обязательный блок «чего не знаем» (какой вывод невозможен, сколько кликов и дней нужно).
- **Прогноз для нового направления:** приор из аналогов (другие направления клиента и юридические клиенты), Монте-Карло, результат — распределение цены заявки и вероятность достичь цели при каждом бюджете; помечать «опора на аналоги, своих данных 0». API прогноза Keyword Planner в нашем стеке не проверялся.

### 7. Контекст и токены: модель, порог, правило сессий
- Каждый ход перечитывается весь контекст; накопление растёт как квадрат числа ходов (модель по весам из шапки `claude_usage.py`; на сессиях супервайзера не мерили). Оптимизировать нужно **число ходов × размер контекста**, а не число агентов.
- Рычаги по силе: (1) роль постоянная, прогон одноразовый, состояние в файлах; (2) лимит прогона (≤15 ходов и ≤100 тыс. контекста для агентов) и чекпоинт в файл; (3) «толстые» скрипты, тонкие ходы (цикл — в скрипт, на выходе сводка); (4) контекст слоями по запросу (роль и контракт всегда, карточка по разделам, пакет контекста); (5) длинные тексты пишут скрипты (вывод весит ~5×); (6) стабильное в начале промпта ради кэша (протухание кэша при простое не проверено).
- **Решение пользователя (согласен с предложением): правило «одна сессия до конца» меняется.** Этап — точка, где допустимо начать чистую сессию со старта от доски, если контекст > ~150 тыс. или ходов > ~25 (оценка: при S = 55 тыс. и росте ~5 тыс. за ход разрез окупается после 20–30 ходов, при тяжёлом выводе ~15 тыс. за ход — после ~14; веса допущены, не замерены). Мелкие шаги группируются в одну сессию, резать «на каждой задаче» не нужно.
- **Первое — уменьшить стартовый груз S** (главная сессия ~55 тыс., субагент ~24 тыс.): он платится на каждом ходу и при каждом перезапуске. Для автозапусков — облегчённый проект с коротким `CLAUDE.md` (S ~15–20 тыс.). Возврат в работавшего агента (`SendMessage`) тянет весь его контекст; гипотеза: при контексте > ~50 тыс. дешевле новый агент с файлом (проверить `claude_usage.py --returns`).

### 8. Машинный формат плана и результатов (делать с первой фазы)
- `30_план` пишется не только таблицей для человека, а файлом с фиксированными полями (YAML/JSON): для каждого пункта `id`, объект, действие, было → станет, `command` (скрипт и аргументы без `--execute`), класс риска, `approval` (pending / ok / правка / нет), `readback` (чем и что ожидаем прочитать обратно), `rollback`, блок `wiki` (зачем, гипотеза, порог, стоп-правило, дата оценки, «для отчёта клиенту (EN)»).
- Таблица для пользователя и таблица решений (Google Sheets) **строятся из этого файла скриптом**, а не пишутся отдельно; статус `approval` синхронизируется со столбцом «ок / правка / нет».
- Валидатор схемы отклоняет неполный план до «да» (нет отката, нет проверки обратного чтения, нет полей для вики).
- Результаты агентов: шапка файла в YAML (вердикт, статус, числа с источником и временем) + текст ниже; супервайзер и раннер читают шапку без LLM.
- Почему сразу: раннер, скрипт-исполнитель и скрипт вики читают именно эти поля; перевод свободного текста в поля позже потребует переписать плейбуки, агентов и планы. Для пользователя ничего не меняется: он видит ту же таблицу.

### 9. «Да»: канал и классы риска
- **Канал (решение пользователя):** таблица решений со статусом «ок / правка / нет» — основной; Telegram — для мелочей и уведомлений. Раннер читает статус из таблицы сам.
- **Предложение, ответа нет:** классы риска вместо «да» на каждый пункт. Низкий и обратимый (минуса, тексты на паузе, новая кампания на паузе) — стоящее разрешение на класс; средний (ставки, бюджет в пределах правила) — одно «да» на весь план; высокий (включение, смена стратегии, удаление) — отдельное «да». Расходится с правилом «один пункт — одно решение» (оно про стратегию, не про исполнение утверждённого).
- Права записи без человека: в неинтерактивной сессии подтвердить некому, в Auto-режиме классификатор блокировал запись (11.11). Предложение: автозапуски — только чтение и планы; запись — отдельным узким запуском после «да», с разрешением на конкретный скрипт; примет ли классификатор такое разрешение, не проверено.

### 10. Другие модели, в том числе бесплатные (предложение, ответа пользователя нет)
