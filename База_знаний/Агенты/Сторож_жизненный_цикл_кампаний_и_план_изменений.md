# Жизненный цикл кампаний и общий план для сторожа

Один файл на клиента: `Клиенты/<Имя>/Паспорт_кампаний.yaml` (в git, сторож читает каждый такт). Журнал_изменений = факты, паспорт = состояние и намерения. Задачи.md — только действия человека (ссылка на номер изменения).

## 1. Состояния кампании
| Состояние | Кто ставит | Что делает сторож |
|---|---|---|
| `active` | мы при заведении | охраняет по правилам; сам ставит и (по правилам) снимает свои паузы |
| `guard_paused` (причина: цена / темп / предел / лимит) | сторож (в state, причина хранится между днями) | по причине см. п. 2 |
| `hold_rebuild` (пересборка / оптимизация до включения) | мы, в той же записи, где выключили; поля `why`, `to_enable_when[]`, `review_by` | не трогает, не возобновляет; напоминание раз в неделю; если кто-то включил — сообщение и минимальная защита как у незнакомой |
| `hold_off` (пауза «ждём»: сезон, решение клиента) | мы | то же, без чек-листа |
| `staging` (создана на паузе) | мы | не трогает; включение — отдельное «да» |
| `retired` | мы | игнорирует |
Пауза, поставленная не сторожем и без записи в паспорте → сообщение «что это?» один раз, ответ записываем в паспорт. Включение из `hold_rebuild` — только по «да» и когда все пункты `to_enable_when` отмечены (после смены посадочной — проверка ассетов по правилу 26.10); после включения кампания переходит в `active` и вносится в `guard_config.yaml`.

## 2. Возобновление после паузы сторожа
- Причины «цена заявки» и «темп»: утром следующего рабочего дня (первый такт после 00:05 по времени аккаунта, с учётом расписания показов) сторож включает кампанию сам. Основание: одна пауза по 2×цель у здоровой кампании — ложная в 13,5% дней.
- Вторая пауза сторожа по цене за 3 дня: утреннее возобновление отключается, состояние → `needs_review` (человек/разбор). Основание: две ложные подряд у здоровой кампании ≈ 1,8% (0,135²) — это уже сигнал, не случайность.
- Причины «предел 2× бюджета» и «общий лимит теста»: сам не включает.
- Если пока кампания стояла на паузе, её изменил человек (детектор вмешательств) → не включает, пишет.
- Возобновление и причина паузы пишутся в лог и в Telegram; запись в `Журнал_изменений.md` — мы.

## 3. Обратный сценарий: недобор расхода
Условие запуска (по чистым дням, `window_check.py`): медиана расхода за ≥ 3 чистых дня < 50% дневного бюджета (стартовое значение пользователя) И потеря показов по бюджету = 0 (для PMax — без этого показателя, только доля расхода). Дальше диагноз по цене заявки (Gamma–Пуассон по кампании):
- вероятность «CPL ≤ цель» ≥ 80% → предложение поднять рычаг: Search на ручной цене / «Максимум кликов» — потолок цены клика; на tCPA — tCPA; шаг +15–20%, оценка через 3 чистых дня; запись по «да»;
- вероятность < 80% или данных мало → ничего не двигаем, сообщение «недобор, цена не подтверждена»;
- недобор дольше 14 дней без эффекта от рычагов → предложение снизить бюджет до ≈ 1,3 × фактический расход, чтобы сумма бюджетов проекта отражала реальность.
Бюджет вверх — как сейчас: только если расход упирается в бюджет и цена ≤ цели. Сторож сам рычаги ставок не меняет (пока только предлагает).

## 4. Общий план «решения ↔ сторож»
Раздел `agreed_changes` в паспорте: `id` (И-/Э-номер), кампания, параметр, было → станет, дата «да», срок, `apply: manual | guard`, статус `agreed | applied | expired | cancelled`.
- Сторож каждый такт сверяет кабинет с `станет`: совпало → `applied`, сообщение; не совпало к сроку → сообщение «согласовано, не сделано» (по умолчанию ничего не меняет).
- `apply: guard` — только по явной отметке в этом изменении и только для того, что сторож уже умеет писать (возобновление, бюджет в пределах base…max); запись, чтение обратно, сообщение.
- Базовые бюджеты и пределы сторож берёт из паспорта (одно место), а не из `guard_config.yaml`: согласованное «поднять до 60» не будет откатываться вечерним возвратом.
- Мы вносим строку при «да» в том же ходе, что запись в Журнал/Решения; расхождение «план есть, в кабинете нет» — такой же сигнал, как вмешательство.

## 5. Что решает пользователь
1. Утреннее возобновление по причинам «цена»/«темп» с остановкой после второй паузы за 3 дня — да/нет.
2. Паспорт кампаний одним файлом на клиента как место состояния и общего плана — да/нет.
3. Недобор: порог 50% бюджета, 3 чистых дня, вероятность цены ≥ 80% — стартовые значения, пересмотр по данным.
4. Метки в самом кабинете (`guard:hold_rebuild`) — не сейчас (запись в кабинет), позже по желанию.

## 6. Иерархия: страховка сторожа → курс из глубокого анализа → тактические подсказки (добавлено 2026-11-04 по вопросу пользователя)
Три уровня, в таком порядке приоритета:
1. **Страховка (всегда включена, выше всего).** Паузы по цене заявки, «темпу», пределам. Не ждёт анализа и не отменяется курсом: защита денег.
2. **Курс из глубокого анализа (главнее тактических подсказок).** Результат сессий анализа и оптимизации (в том числе других агентов) после вашего «да» записывается в паспорт, раздел `курс` по кампании: `режим` (тест / масштаб / держим / сворачиваем), `заморозка_до` (период теста по `Эксперименты.md`: пока идёт оценка, тактические подсказки молчат, чтобы не портить эксперимент), `коридор` (бюджет и tCPA / потолок клика: минимум и максимум), `основание` (номер Э-/Р-/И-, дата анализа, кто делал), `review_by`.
3. **Тактические подсказки сторожа (недобор, рост базы).** Предлагаются только внутри коридора курса и не в период заморозки; если подсказка противоречит курсу, она не показывается как совет, а пишется как «сигнал расхождения».
Связь обратно: сторож ведёт `Статистика/guard_signals.csv` (дата, кампания, тип подсказки, цифры, ваш ответ да/нет, эффект через N чистых дней). Агент глубокого анализа читает паспорт (курс, холды, согласованные изменения) и этот журнал как входные данные, а по итогам обновляет курс. Если реальность несколько раз подряд расходится с курсом (например, по курсу «растим бюджет», а цена заявки выше цели), сторож пишет «курс устарел, нужен пересмотр», сам курс не переписывает. Записывает курс в паспорт только оператор (я) по протоколу «таблица плана → «да» → запись», а не агент или сторож самовольно.

## 7. План следующей сессии (записано 2026-11-04 вечером; код ещё НЕ написан, боевые сторожа работают на версии 15:16)
**Что отложено по уточнению пользователя:** только заморозка тактических подсказок на время эксперимента и использование раздела `course` (после завтрашней оптимизации). Подсказки «недобор расхода» и журнал сигналов — можно делать сразу.
**Порядок работ:**
1. **Правило «расход без заявок подряд» (решает проблему маленьких бюджетов).** Если бюджет < ≈ 2,3 цены заявки (`exp(−бюджет/цена) > 10%`), нулевой день у здоровой кампании обычен, поэтому внутридневное «N × бюджет при нуле заявок» там не работает. Доказательство копится по дням: хранить `state["_dry"][id]` = расход с последней заявки через дни (`carry`, `last_lead_cost`, `n_seen`, на смене дня `carry = dry_now`; начальное значение — проигрыш `gads_spend_guard_cpa_log.csv`). Пауза, если `dry_now ≥ 3 × цель` (вероятность ложной паузы за один «интервал между заявками» exp(−3) ≈ 5%); причина «расход без заявок подряд», утром сам не включается (нужен разбор); не применять, пока источник заявок помечен недоступным. Перед включением показать, у кого сейчас `dry_now` близок к порогу (чтобы не было пауз «с места»). Для `shop_tail` (EkspertAgro) после этого убрать личный `hard_mult: 1.0` (решение пользователя: «переделываем по-новому»; при цене заявки 87 zł и бюджете 70 zł нулевой день ≈ 45%); `total_limit: 600` оставить.
2. **Подсказки «недобор расхода» в сторожe:** медиана расхода за 3 чистых дня < 50% бюджета, потеря по бюджету 0, обе модели цены заявки дают P(цена ≤ цель) ≥ 80% (`guard_threshold_calc.py --underspend`, `k0 = 3`); подсказка — сообщение «поднять tCPA / потолок клика на 15–20%», действие только по «да».
3. **Журнал сигналов** `Клиенты/<Имя>/Статистика/guard_signals.csv`: дата, кампания, тип, цифры, ответ да/нет, эффект через N чистых дней.
4. После завтрашней оптимизации: заморозка подсказок на период эксперимента (`course.freeze_until`) и коридор из `course`.
**Пояснение для пользователя («незнакомая кампания»):** каждый такт сторож читает список ВКЛЮЧЁННЫХ кампаний аккаунта; если id нет в `campaigns` и в `unmanaged_ok` (и это не Local Services), он берёт её под минимальную защиту и пишет в Telegram. «Новая» — любая включённая вне конфига, не только созданная сегодня.

## 8. Политика риска (решение пользователя 2026-11-04): при сомнении режем, а не сливаем; смелость зависит от состояния проекта в месяце
1. **Асимметрия.** Если данных не хватает для уверенного вывода, выбираем вариант, при котором можем недобрать заявки, но не сольём бюджет. Недобор конверсий из-за ошибки — допустимая цена; слив без заявок — нет. Поправка консультанта: «резать» не бесплатно, когда проект отстаёт от плана по объёму (`state_digest.py` раздел [4]); тогда цена урезания — недовыполнение плана, и в оценке она учитывается наравне с риском слива.
2. **Режим риска проекта вычисляется, а не назначается:** по плану месяца («Цели2») и фактам месяца (расход, заявки по Ringostat+Supabase, не по конверсиям Ads). Показатели: доля месяца, число заявок за месяц N, байесовская оценка цены заявки проекта (Gamma–Пуассон) и P(цена проекта ≤ план), запас/просадка относительно плана. Режимы: **«аккуратно»** (прошло < 30% месяца, или N < 15 заявок, или P < 70%: одна заявка меняет цену в разы), **«норма»**, **«смелее»** (больше половины месяца, N ≥ 30, P ≥ 90%, нет просадки: один плохой день картину не ломает). Границы — стартовые рабочие оценки, пересмотреть по данным.
3. **Что от режима зависит:** допустимый расход `(grace + заявки) × цель` (grace 2 в «аккуратно» → до 3 в «смелее»); порог вероятности для подсказок «поднять рычаг» (90% / 80% / 70%); готовность поднимать бюджет и предлагать рост. Страховочные паузы по пределам (2 × бюджета, «темп») от режима не зависят.
4. **Как говорить с пользователем:** выводы — только из расчёта (формулы, интервалы), без вопросов «поднимаем или нет» там, где расчёт отвечает; везде, где данных не хватает, прямо написано «данных нет, выбран вариант с недобором заявок, но без слива». Код режима риска — задача следующей сессии.
