## 1. Шаг 0. Что `leads_standard.py` делает со звонками из объявлений

Вердикт одной строкой: **делает частично.** Звонок статического канала остаётся заявкой по Ringostat; `call_view` Google Ads только подставляет ему кампанию (по времени +-3 мин). Статический номер из Ringostat НЕ исключается, `call_view` как самостоятельный источник заявок НЕ используется: строки `call_view` без пары в Ringostat в заявки не входят.

### (а) Что делает код (`Скрипты/leads_standard.py`)
| Что | Где в коде | Факт |
|---|---|---|
| Звонки Ringostat | `ringostat_google_calls`, стр. 48-96 | только входящие (`call_type == "in"`, стр. 78); источник Google Ads по меткам (стр. 76-77); уникальность по звонящему в окне `unique_window_days` = 60 (стр. 88, конфиг `profimet.yaml`); фильтра по длительности и статусу звонка нет |
| Строки `call_view` | `call_view_rows`, стр. 99-104 | GAQL `call_view` (время, длительность, id и имя кампании), `start_call_date_time >= d0`; фильтра по длительности, статусу, типу звонка нет; все кампании аккаунта |
| Сопоставление | `attach_call_view`, стр. 107-128 | для каждого уникального звонка Ringostat, кроме пулов с `_dyn` в имени (стр. 115): ближайшая строка `call_view` в пределах 180 с (`MATCH_SEC`, стр. 33), каждая строка `call_view` используется один раз (`used`, стр. 113, 119-122) |
| Подстановка кампании | стр. 123-125 | кампания берётся из `call_view`, только если Ringostat кампанию не знает (`UNRESOLVED` или «(без кампании)») или имя пула содержит «calls from ads»; тогда `via_call_view = True` (колонка «из объявл.»). Если кампания известна обоим и не совпадает, это считается в `cv_mismatch` и не меняет строку (стр. 126-127) |
| Звонки `call_view` без пары | возврат `cv[~cv.index.isin(used)]`, стр. 128 | в заявки не входят; печатаются отдельной строкой (стр. 332-335) |
| Двойной счёт | - | не обнаружен: заявка = строка Ringostat, одна строка `call_view` привязывается не более чем к одной строке Ringostat; число заявок от `attach_call_view` не меняется, меняется только поле кампании |
| Кампания звонка | - | по кампаниям (не по аккаунту); без пары остаётся «Google без кампании» (строка в отчёте) |

### (б) Как определяется статический номер
Номера в коде нет. Канал определяется косвенно: по имени пула Ringostat («calls from ads», стр. 123) или по нераспознанной кампании из метки (стр. 92-93, 123). В `Клиенты/ProfiMet/Коллтрекинг/Пул_номеров.yaml` статический пул «Google CPC calls from ads» записан справочно: `+48579773187` (раздел `static_pool_calls_from_ads`, не прогоняется `phone_swap_check.py`). Скрипт этот файл не читает, поэтому сходимость «номер из файла = канал в скрипте» не проверена; проверено только то, что файл называет тот же канал по имени. Отдельные статические номера Display-ретаргета и YouTube (Пул_номеров, строки 118-145) в коде отдельно не выделяются.

### (в) Заявки аккаунта до и после учёта `call_view`
Режима «без `call_view`» в `leads_standard.py` и `pace_vs_plan.py` нет (флаги `pace_vs_plan.py`: `--customer-id --client-folder --month --today --weeks --weekend-weight`). **Пробел: нет режима «до/после».** Из кода следует (стр. 107-128), что число заявок от него не зависит, зависит только кампания.
Факт 01-14.11 (`PYTHONUTF8=1 python pace_vs_plan.py --customer-id 7552781705 --client-folder ProfiMet --today 2026-11-15`, расход аккаунта без `yt_`): расход 871 €, заявок 58, цена заявки 15 € (871 / 58 = 15,0). `leads_standard.py --from 2026-11-01 --to 2026-11-15` (с `yt_`): 62 заявки = 43 звонка по метке + 4 звонка из объявлений + 15 форм; из них `yt_warm` 4 звонка по метке, 62 - 4 = 58. Совпадает с `pace_vs_plan.py`.
Чего не показано: сколько уникальных звонков Ringostat на статическом канале осталось без пары (в отчёте они сидят в «Google без кампании» вместе с динамическими звонками без распознанной кампании; разделения нет), поэтому число заявок аккаунта «по правилу пользователя» (динамические + формы + все `call_view`) посчитать нельзя. Известно только: из 5 строк `call_view` за 01-15.11 в заявки не входит 1.

## Что в плане не обосновано (где пришлось бы подставить порог или метод на глаз)
- Окно по кампании («минимальное число целых недель, в которых ~60 заявок», реестр п. 2, 3, 8): числа 60, 6 недель, добор с весом 0,8 - рабочие оценки, экзамен на прошлом не проводился. Нужно: утвердить числа или провести экзамен.
- Лестница методов по числу заявок (реестр п. 9): порог 15 - рабочая оценка. Без неё нельзя пометить «данных мало» у кампании: поэтому в 20_ситуация.md даны только n.
- Определение «крупной правки» (п. 5): пороги 20% бюджета, 10% ставки - рабочие оценки; без них нельзя назвать «последнюю крупную правку» по кампании кроме как перечнем всех правок.
- «Кандидат в минус-слова» (раздел 11): ярлык скрипта; правила в реестре нет. Нужно утвердить критерий (например, расход без конверсий не ниже порога, выраженного через цену заявки) до того, как слово «кандидат» используется как оценка.
- «Упор в бюджет» (раздел 6): скрипт пишет «Если «потеряно по бюджету» ~0, повышение бюджета расход не поднимет»; число-порог «~0» не записан. Приведены только числа.
- «Мало заявок / выборка мала»: порог не утверждён; у кампаний приведено n.
- Сравнение «свежие дни против прежних» (динамика): метод (разность разностей, CUSUM, пуассоновская регрессия) в реестре как «не реализован».
- Метод разноса `yt_`/без метки при «Google без кампании»: правила, как относить заявки без кампании, нет.
- Определение «чистых дней» для кампании: `window_check.py` не запускался, правило границы дня (правки внутри дня) не утверждено числами.
