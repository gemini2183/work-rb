# 35. Окно анализа кампании: что определяет методология и чего не хватает (ProfiMet, без yt_)

Источники: `База_знаний/Паттерны/Методология-выбора-метода-и-периода-анализа-кампаний.md` (далее М), `База_знаний/Агенты/Процедура_догон_плана_месяца_лог.md` строки 61-63 (далее Л). Ни у одного параметра в М нет статуса «утверждено».

## 1. Что методология определяет для выбора окна

| Правило | Формула / порог | Источник | Статус |
|---|---|---|---|
| Размер окна задают заявки, не клики и не дни | ~60 заявок на ±25 % при 95 %; целые недели, не меньше двух; константа «14 против 14» отозвана | Л стр. 63; М реестр п. 2, 3 | решение пользователя 16.11 + расчёт |
| Точность по числу заявок n | полуширина 95 % интервала цены заявки ≈ 1,96/√n; n >= (1,96/0,25)² ≈ 62; при n < 20 - точный интервал Гарвуда (ХИ2.ОБР(0,025; 2n)/2 ... ХИ2.ОБР(0,975; 2n+2)/2) | М реестр п. 2, раздел «Что можно различить», «Как считается интервал Пуассона» | выведено расчётом |
| Таблица n -> полуширина | 7: ±74 %; 15: ±51 %; 30: ±36 %; 60: ±25 %; 120: ±18 % | М «Что можно различить» | расчёт |
| Лестница методов по n | >=60 / 15-59 / 1-14 / 0; порог 60 выведен, порог 15 - рабочая оценка | М п. 9-12 | 15 не выведено |
| Целые недели (вес выходных 0,13 по расходу и заявкам, окно 05.10-15.11) | окно кратно 7 | М п. 3 | выведено из истории ProfiMet |
| Начало окна - последняя крупная правка ЭТОЙ кампании (класс А: пауза, стратегия, цель CPA, посадочная, гео, расписание, аудитории, GTM/Ringostat; Б: бюджет ±20 %, ставка ≤10 % - пороги 20 % и 10 % рабочие оценки). Дата = более поздняя из журнала и излома (CUSUM) | | М п. 4-6 | не реализовано |
| Потолок окна 6 недель (для уровня); для сегментов 3 недели (21 день) | вес 0,8^k по затуханию | М п. 7, 8; строка про сегменты | не выведено; бэктест: 4+ недель хуже динамической модели у аккаунта (p_Холм 0,045 при 4 нед., 0,006 при 5 нед.) |
| Бэктест следующей недели (WAPE) | окно 7 дн. лучше 14 и 21 у аккаунта (0,321 / 0,385 / 0,431), Brand, Poliweglan, pmax01; у pmax1_test и малых окна не различимы; вес 0,8 не подтверждён | М «Окно по бэктесту» | выведено расчётом; относится только к вопросу «уровень заявок и прогноз на следующую неделю» |
| Правило остановки | ожидали k=S/T заявок; k>=3 и 0 заявок -> сигнал (e^-3 ≈ 5 %) | М п. 13; Л стр. 64 | порог условный; проверка сегментов (segment_backtest 16.11) порог не нашла |
| Если заявок мало | цена заявки = цена клика ÷ конверсия соседних кампаний на ту же страницу; байес; микроконверсии только после проверки связи | Л стр. 64; М п. 11, 12, 15 | не реализовано |
| Жёсткое правило применения | окно, веса, пороги берутся из М и считаются, не назначаются; параметры без утверждения помечаются «не утверждено» в каждом выводе | М «Правило применения» | действует |

Противоречие в самих источниках, на решение пользователя: бэктест (М) советует 7 дней для уровня, решение 16.11 (Л) требует >= 2 недель и ~60 заявок. Это про разные вопросы (прогноз следующей недели против оценки кампании с интервалом); в М так прямо не сведено.

## 2. Чего не хватает для расчёта окна по каждой кампании

Ориентир по темпу (моя оценка по заявкам 01-15.11 из М и 10_данные.md, скриптом окно не считалось): окно = 60 / (заявок в неделю), округление вверх до целых недель, не меньше 2.

| Кампания | Темп заявок (оценка) | Окно под ~60 заявок (оценка) | Что упирается |
|---|---|---|---|
| Аккаунт без yt_ | 58 за 15 дн. ≈ 27/нед. | ≈ 3 нед. | дата правок по аккаунту |
| `Search | Brand | Pl` | 19 за 15 дн. ≈ 9/нед. (за 2025-08-01..2026-11-15: 1038 заявок) | ≈ 7 нед., выше потолка 6 нед. | потолок 6 нед. не выведен; конфликт с «от последней крупной правки» |
| `pmax1_test` | 25 за 15 дн. ≈ 12/нед. (всего 294 с 23.04) | ≈ 5 нед. | дата последней правки; конверсия клика по номеру завышалась YouTube/Discover (п. 15) |
| `Search | Poliweglan | Pl` | 7 за 15 дн. ≈ 3/нед. (1004 за весь период) | ≈ 18 нед., окна нет в рамках потолка | n=60 недостижимо; по лестнице метод 15-59 или 1-14 (байес / цена клика ÷ конверсия) |
| `search / montaz` | 1 заявка с 12.11 | в данных этого нет (n=1) | только метод n 1-14 |
| `dspl_rtg_basket`, `dspl_rtg_engage_mid` | 0 и 1 | в данных этого нет | то же |

Не хватает (все пункты «в данных этого нет» или «не реализовано»):
- **Заявки кампания x день по стандарту `leads_standard`:** 10_данные.md стр. 86 - `--daily` печатает только аккаунт, `live_maps` не вызывается из командной строки. Есть панель `Клиенты/ProfiMet/Работы/2026-11-16_selector/panel_day_campaign.csv` (её строит period_backtest.py), но её актуальность по правилу звонков из объявлений (call_view) не проверена; `leads_standard.py` режим `--calls-from-ads call_view` существует, у `period_backtest.py` он не упомянут.
- **Дата последней крупной правки по кампании:** не рассчитана; `gads_change_history.py` хранит ~29 дней, журнал `Журнал_изменений.md` не размечен классами А/Б, CUSUM не реализован (М стр. 46, 117).
- **Пороги не утверждены:** 60, 15, 20 %/10 %, 6 недель, 0,8, 3 недели для сегментов.
- **Селектор** (кампания -> метод и окно по n и дате правки): не построен (М «Статус реализации»).
- **Калибровка по клиенту** (журнал предсказаний, покрытие интервалов): скрипта нет, `Калибровка_методов.md` не заведён.
- **Состав «заявки» по кампании:** разделить звонки статического канала без пары и динамику без метки в «Google без кампании» (1003 заявки) нельзя; кампания части заявок неизвестна.
- **Заявка против продажи:** ограничение цены продажи считается по аккаунту, по кампаниям соответствия заявка -> продажа нет (М п. 1).

## 3. Готовые скрипты (Grep по Скрипты/, README не читал)

- `Скрипты/period_backtest.py` - есть: `--history`, `--backtest`; выбирает окно по бэктесту следующей недели (7/14/21 дн.), заявки как в `leads_standard`, без yt_. Это не селектор «окно под число заявок»; даты правок не использует.
- `Скрипты/window_check.py` - есть: «чистые» дни кампании по дню (выходной, пауза, правка, сокращённый); заявки у него = конверсии Ads, не стандарт.
- `Скрипты/leads_standard.py` (заявки, --daily по аккаунту), `Скрипты/pace_vs_plan.py` (темп, вес выходных), `Скрипты/segment_backtest.py` (окно и порог сегментов, не подтвердил), `Скрипты/sales_pace.py` (допустимая цена заявки).
- Готового скрипта «число заявок -> окно в целых неделях с интервалом Гарвуда» и определения даты крупной правки в Скрипты/ нет (Grep по `крупн` ничего не дал). Это работа для `script-builder` после согласования правил.
