# Решения — ProfiMet (Теплицы, Польша)

## [2026-09-01] Коллтрекинг Ringostat | нашли XPath для sticky-хедера | текущий XPath не покрывал fixed-копию хедера | ожидает внесения в кабинет и проверки

Клиент задал в Ringostat XPath для номера телефона в хедере, но подмена не
срабатывала именно в sticky-хедере, который Tilda показывает при скролле
(хедер начального экрана — отдельный DOM-узел, sticky — другой).

Разведка через Playwright (headless, скролл + чтение computed style/DOM)
показала: сайт mocnaszklarnia.pl сделан на Tilda, и хедер блока (`.t396`)
рендерится Тильдой в виде **двух параллельных копий** одного и того же
блока — обычной (в потоке документа) и fixed (`t396__artboard-fixed-active`,
активируется JS при скролле). XPath, заданный по обычной копии, не
покрывает fixed-копию — у неё свой отдельный поддерево DOM.

Найденный устойчивый XPath для sticky-копии (по классу, не по индексам div,
чтобы не сломаться при правках вёрстки в редакторе Tilda):

    //div[contains(@class,"t396__artboard-fixed-active")]//a[starts-with(@href,"tel:")]

Текст ссылки — чистый номер (`+48 794 771 451`), без окружающих слов, так что
маска в Ringostat может быть простой (`+## ### ### ###` под номер) — это не
случай точечной замены внутри длинного текста, см.
[[../../База_знаний/Инструменты/Ringostat-механизм-подмены-номера|Ringostat-механизм-подмены-номера]]
(раздел про Tilda и двойной хедер дописан туда же).

Общий факт про Tilda (двойная копия sticky-блока) вынесен в базу знаний как
кросс-клиентское знание — статус "не протестировано" до подтверждения, что
XPath реально заработал в кабинете Ringostat клиента.

**Дальше:** внести этот XPath в кабинет Ringostat ProfiMet, проверить вживую
(скролл + смотрим на номер) и прогнать `phone_swap_check.py` — см. [[Задачи]].

## [2026-09-01] Коллтрекинг Ringostat | XPath для sticky оказался слишком широким, задел мобильную иконку без текста | одно правило не годится сразу для desktop-текста и mobile-иконки | нужно два отдельных правила + открыт вопрос в поддержку Ringostat про href

После внесения XPath из предыдущей записи клиент сообщил: в мобильной версии
sticky-хедер показывает иконку телефонной трубки (без текста номера), и
после подмены рядом с иконкой криво вписывается номер текстом.

Причина — правило `//div[contains(@class,"t396__artboard-fixed-active")]//a
[starts-with(@href,"tel:")]` слишком широкое: под него подпадают СРАЗУ два
разных элемента внутри fixed-копии хедера — desktop-версия (`<a
href="tel:...">+48 794 771 451</a>`, чистый текстовый узел) и mobile-версия
(`<a class="tn-atom" href="tel:..."><img ...></a>`, кнопка-иконка без
текста, показывается на мобильном через CSS вместо десктопной ссылки — обе
версии присутствуют в DOM одновременно, Tilda переключает видимость по
media query, не по разметке). Одна и та же текстовая маска (`+## ### ### 
###`) применяется к обоим — на desktop это корректный full-replace текста,
на mobile — Ringostat вписывает те же цифры текстом рядом с `<img>`,
которого там раньше не было, ломая вид кнопки.

Проверено Playwright: точно такая же icon-only кнопка (`<a class="tn-atom">
<img></a>`, без текста) существует ещё в ДВУХ местах — в обычном (не-sticky)
мобильном хедере верхнего экрана, и, предположительно, там же на десктопе
не проверялось так как на десктопе в шапке используется текстовая ссылка.
На эту icon-only кнопку верхнего экрана раньше не было заведено ВООБЩЕ
никакого XPath-правила — поэтому кривости там никто не видел, проблема
проявилась только сейчас, когда наше новое правило её случайно захватило.

**Решение — разделить на два разных правила** (не одно на весь артборд):

    XPath 1 — desktop/текстовый узел (без дочерних элементов):
    //div[contains(@class,"t396__artboard-fixed-active")]//a[starts-with(@href,"tel:") and not(*)]
    маска: +## ### ### ### (как сейчас)

    XPath 2 — mobile icon-only кнопка (содержит <img>):
    //div[contains(@class,"t396__artboard-fixed-active")]//a[starts-with(@href,"tel:") and img]
    что писать в маску — ОТКРЫТЫЙ ВОПРОС, см. ниже

По итогу решили трекать оба места сразу — и sticky-копию, и такую же
icon-only кнопку в обычном (не-sticky) хедере верхнего экрана — раз уж
разбираемся с этим паттерном, лучше закрыть его целиком, а не только там,
где сейчас заметна кривость.

**Открытый вопрос — как корректно подменять номер в icon-only кнопке:**
у элемента нет текстового узла вообще (только `<img>`), значит подмена
через обычную текстовую маску всегда будет вписывать цифры рядом с
картинкой и портить вид. Нужен способ подменить **только атрибут `href`**
ссылки, не трогая видимое содержимое.

Проверено в UI кабинета (форма "Редактировать XPath"): помимо XPath и
Маски, там есть отдельный блок "Кнопка выдачи номеров Call me" (HTML код +
чекбоксы "для всех устройств"/"только для мобильных") — сначала подумали,
что это то самое решение, но по документации Ringostat (help.ringostat.com,
статья "Кнопка выдачи номеров Callme") это **другая функция**: экономия
номеров пула при нехватке (показывает кнопку "узнать номер" вместо
автоподмены, когда одновременных посетителей больше, чем свободных номеров
в пуле) — к нашей задаче отношения не имеет, в блоке не копаемся.

Прямого ответа в документации Ringostat, можно ли XPath-правилом подменять
только `href` без изменения текста/содержимого элемента, найти не удалось
(WebSearch + WebFetch по help.ringostat.com, 2026-09-01) — **вопрос отправлен
в поддержку Ringostat**, ждём ответа.

**Запасной план**, если поддержка скажет, что подмена только href
невозможна: добавить в вёрстку Tilda (редактор блока хедера) скрытый
текстовый `<span>` внутри той же ссылки-иконки (спрятанный CSS, например
`font-size:0`/`position:absolute;opacity:0`), задать XPath на этот span для
подмены текста, и синхронизировать `href` самой ссылки с этим текстом через
JS на сайте (простой обработчик, копирующий число из span в href при
изменении DOM) — сложнее in-Ringostat решения, применять только если
прямого способа через кабинет нет.

**Статус:** ждём ответа поддержки Ringostat, вносить оба XPath-правила
(desktop + mobile) в кабинет пока не стали — решение по mobile ещё не
финализировано. См. [[Задачи]].
