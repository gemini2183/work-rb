# Скрипты

Один общий скрипт на источник данных для клиентов без спец-условий — разница
между ними только в логине/токене/номерах целей, структура запроса одна и та же.

Если у клиента есть спец-условия для сверки/анализа (например, кампанию нужно
исключать по UTM, как letnie у ЕГЭ Merlin — см. `conditions` на вкладке
"Metrika" общей таблицы) — под него заводится **отдельный** скрипт
(`<источник>_stats_<клиент>.py`), который использует функцию сбора из общего
скрипта, но добавляет свою фильтрацию поверх. Не зашивать клиент-специфичные
условия в общий скрипт — это 1:1 повторяет архитектуру прод-пайплайна
(`google-cloud-jobs`), где под такими клиентами тоже отдельные job'ы со своим
`apply_client_filters`, а не общая логика для всех.

## Два агентства — две отдельные таблицы

В этой вике ведутся клиенты двух разных агентств:
- **Redbird** — контекстная реклама Яндекс.Директ (Директ/Метрика/Callibri
  и т.п.), таблица `SHEET_URLS["redbird"]` в `_config.py`.
- **Adwhite** — контекстная реклама Google Ads (Google Ads API/Merchant
  Center), таблица `SHEET_URLS["adwhite"]` в `_config.py`.

Обе таблицы одинаковы по паттерну (клиент — строка на вкладке источника,
`status=active`), но разные по адресу и структуре вкладок. `get_client_row(...,
agency="redbird"|"adwhite")` — по умолчанию `"redbird"`, для Adwhite-клиентов
передавать `agency="adwhite"` явно.

Логин/токен/счётчик/client_id **не хранятся в этой вики** — берутся напрямую
из соответствующей общей Google-таблицы, той же, что питает продовый
BigQuery-пайплайн в `E:/PythonProjects/RedBird/google-cloud-jobs`. Это единый
источник правды: если токен клиента поменялся, обновляется в одном месте, а не
дублируется в нескольких проектах. Здесь только облегчённая локальная версия
сбора — без BigQuery, снапшот сразу кладётся в `Клиенты/<клиент>/Статистика/`
для анализа агентом.

## Установка

```
pip install -r requirements.txt
```

`gads_semantics_generator.py` дополнительно требует `pyyaml` (для чтения
словаря тем клиента) — добавить в `requirements.txt`, если ещё не стоит.

## Требование к таблице

Клиент должен быть заведён строкой на нужной вкладке общей таблицы своего
агентства (`Директ`/`Metrika`/`Calibri` для Redbird, `Google_Ads_API` для
Adwhite), с `status=active`, и значением колонки `client`, которое передаётся
скриптам как `--client`.

Доступ — через service account `Скрипты/secrets/rb_cloud_service.json` (не в
git, скопирован из `google-cloud-jobs`; тот же service account, что использует
продовый пайплайн, доступ read-only к обеим таблицам).

Для Google Ads API (Adwhite) дополнительно нужен `Скрипты/secrets/google-ads.yaml`
(developer_token/OAuth/MCC login_customer_id — не в git, скопирован из
`google-cloud-jobs/adwhite/func/<любой gads-job>/google-ads.yaml`, общий для
всего аккаунта Adwhite, не per-клиент).

## Запуск — Redbird (Директ/Метрика/Callibri)

```
python direct_stats.py --client "ЕГЭ Merlin" --client-folder "ЕГЭ Merlin" --days 30
python metrika_stats.py --client "ЕГЭ Merlin" --client-folder "ЕГЭ Merlin" --days 30 --goals 123456,789012
python callibri_stats.py --client "ЕГЭ Merlin" --client-folder "ЕГЭ Merlin" --days 30
```

`callibri_stats.py` тянет звонки (колл-трекинг) с вкладки "Calibri" общей
таблицы — сырые данные без дедупликации и без вычисления источника трафика.
Использовать напрямую только для клиентов без спец-условий; для ЕГЭ Merlin —
см. клиент-специфичный скрипт ниже.

### Клиент-специфичные скрипты (Франшиза Мокрый Нос Дзен)

```
python metrika_stats_mokry_nos_dzen.py
python metrika_stats_mokry_nos_dzen.py --date-from 2024-01-01 --date-to 2026-08-24
```

Счётчик 66145201 общий на всю франшизу "Мокрый Нос" — этот проект выделяет
только трафик с сервиса Яндекс Promo Pages (`UTM Source содержит
promopages`), цель "Отправка любой формы" (ID 143150284), атрибуция "первый
источник, cross-device" (`cross_device_first`, не дефолтная last-click).
Клиент не заведён отдельной строкой в общей таблице — токен берётся с любой
активной строки таблицы с этим же счётчиком (токен общий на аккаунт).

Выгружает ТРИ отдельных CSV (`*_articles_*`, `*_demographics_*`, `*_geo_*`)
вместо одного отчёта со всеми измерениями разом — при таком фильтре (низкая
кардинальность, десятки визитов по цели) 10 измерений в одном запросе
(дата+источники+UTM+цель+пол+возраст+город) API отдаёт 200 с пустым телом
без ошибки; 9 измерений (без города) уже отдают данные корректно. Причина
не выяснена до конца (не задокументированный лимит API на число групп),
поэтому разбивка на 3 отчёта — это обходное решение, не архитектурный
выбор. Также весь период с 2023-01-01 одним запросом даёт `400 Запрос
слишком сложный` — скрипт сам бьёт диапазон на годовые куски.

Название статьи Promo Pages передаётся в UTM Campaign, не UTM Content
(например "Промостатья: Моя история 1 / Цена перехода / Ж25-54") — UTM
Content у этого трафика несёт только технический тег.

### Клиент-специфичные скрипты (ЕГЭ Merlin)

```
python metrika_stats_ege_merlin.py --date-from 2026-06-01 --date-to 2026-07-17
```

Поверх сбора `metrika_stats.py` фильтрует только рекламный трафик, схлопывает
Source в YaDirect, исключает letnie по UTM Content и исключает трафик
неактивного проекта "Merlin - Курсы Python" по UTM Content (1:1 логика
прод-job `ym2_merlin_ege`).

```
python callibri_stats_ege_merlin.py --date-from 2026-06-01 --date-to 2026-07-17
```

Поверх сбора `callibri_stats.py` (`fetch_callibri_calls`) классифицирует
Source (Контекст/YaDirect по traffic_type+utm_source), исключает letnie по
utm_content и дедуплицирует звонки по (phone, месяц) — 1:1 логика прод-job
`callibri2_merlin_ege`. Использовать вместо общего `callibri_stats.py` для
этого клиента — общий не делает ни классификацию, ни дедупликацию.

```
python reconcile.py --client "ЕГЭ Merlin" --client-folder "ЕГЭ Merlin" \
    --date-from 2026-06-01 --date-to 2026-07-17
```

Общий скрипт сверки конверсий по кампаниям (Директ vs Метрика+Callibri) —
реализация методологии
`База_знаний/Паттерны/Сверка-конверсий-Директ-Метрика-Коллтрекинг.md`.
Сопоставление идёт по `CampaignId` — UTM-метки устроены одинаково во всех
проектах (Директ отдаёт CampaignId готовым числом, Метрика — в UTM Campaign,
Callibri — как `cid_<id>` в utm_content), так что это общая логика без
клиентских вариаций. `goal_id`/`ct_goal_id` (какая колонка direct-файла —
форма, какая звонок) берутся не флагом, а с вкладки "Metrika" по `--client`.
Не собирает данные сам — сначала нужно прогнать `direct_stats.py`,
`metrika_stats*.py` и `callibri_stats*.py` за тот же период.

## Запуск — Adwhite (Google Ads / Merchant Center)

```
python gads_stats.py --client "Клиент - Google Ads" --client-folder "Клиент" --days 30
```

Тянет трафик (Cost/Clicks/Impressions) и конверсии одним проходом через
Google Ads API (не REST+токен, как у Директа/Метрики — используется
библиотека `google-ads`, OAuth через `google-ads.yaml`). Конверсии
разбиваются по `segments.conversion_action_name` — не суммируются в одну
цифру, чтобы не терять смену основной цели конверсии во времени (если у
клиента конверсия была переопределена в середине периода, в снапшоте видно
оба названия отдельными строками).

### Клиент-специфичные скрипты (Корогва)

```
python gads_stats_korogva.py --date-from 2026-06-01 --date-to 2026-07-17
```

Один аккаунт Google Ads (client_id 845-234-6433), разбитый на два подпроекта
по названию кампании, не по отдельному customer_id (1:1 логика прод-job'ов
`gads_korogva_gads`/`gads_korogva_merchant`):
- "Корогва - Google Ads" — обычные кампании
- "Корогва - Merchant Center" — товарные кампании (название содержит "Sales"
  или "Merchant_")

Собирает оба подпроекта за один запуск, сохраняет раздельно (`gads_korogva-gads_*`
и `gads_korogva-merchant_*`, плюс `*-goals_*` для конверсий каждого).

`--client` — как записано в колонке `client` таблицы (может отличаться от имени
папки в `Клиенты/`, поэтому `--client-folder` — отдельный параметр).

Результат — TSV/CSV файл в `Клиенты/<клиент>/Статистика/` с диапазоном дат в имени.
Номера целей для `--goals` берутся из `Клиенты/<клиент>/Цели/goals.md`.

## Семантика Google Ads — ключевые слова и поисковые запросы

```
python gads_semantics.py --client "Клиент - Google Ads" --client-folder "Клиент" --days 60
```

Дополняет `gads_stats.py` разбивкой на уровень ключевого слова (`keyword_view`)
и уровень реального поискового запроса (`search_term_view`) — нужно, чтобы
понять, какие загруженные ключи реально работают, а какие простаивают, и какие
поисковые запросы приносят трафик/конверсии, но не покрыты явно ключами в
семантическом ядре.

Трафик (показы/клики/стоимость) и конверсии могут считаться за разные периоды:
`--conversions-date-from` позволяет укоротить только окно конверсий, если часть
периода признана ненадёжной по конверсиям (см. методологию у клиента в
`Цели/goals.md`), не обрезая при этом статистику кликов/показов по всему `--days`.
Это важно для устойчивости выводов: при малом числе конверсий под конкретным
ключом/запросом нельзя делать вывод "ключ плохой" — недостаточно данных для
статистически значимого решения, это нужно явно помечать, а не подгонять под
бинарный вердикт "работает/не работает".

**Важное ограничение `fetch_search_terms`:** запрос намеренно НЕ включает
`segments.keyword.info.text`/`match_type` в SELECT. Проверено на аккаунте
Корогвы: для Shopping-кампаний (таргетинг по фиду, без ключевых слов)
добавление этих полей в тот же GAQL-запрос молча обнуляет ВСЕ строки такой
кампании — с полями `Merchant_Shopping` давал 0 строк, без них — 13848 строк
за тот же период. Это не баг скрипта, а особенность API: сопоставление с
ключевым словом требует поисковой (SEARCH) кампании. Если нужно сопоставить
поисковый запрос с загруженным ключом — делать отдельным шагом (сравнение
текста `SearchTerm` со списком из `fetch_keywords`), не через один GAQL-запрос.

Другое ограничение API (не решается на нашей стороне): кампании типа
Performance Max в принципе не отдают данные через `search_term_view` — это
задокументированное ограничение Google Ads API, аналитика по их поисковым
запросам доступна только через "Insights" в интерфейсе Google Ads, не через
отчётный API.

### Клиент-специфичные скрипты (Корогва)

```
python gads_semantics_korogva.py --days 60
```

Ключевые слова — только по не-Merchant кампаниям (у Merchant Center/Shopping
нет текстовых ключей, таргетинг по фиду). Поисковые запросы — по обоим
подпроектам отдельно (`*-gads-searchterms_*` и `*-merchant-searchterms_*`),
чтобы найти в Merchant/Shopping запросы, которых ещё нет как ключей в обычных
Search-кампаниях, и расширить охват. Из двух Merchant-кампаний данные реально
приходят только по `Merchant_Shopping` (обычный Shopping) — `Merchant_Performance
Max-1` не отдаёт поисковые запросы из-за ограничения API на PMax, см. выше.
Конверсии по умолчанию считаются с 2026-07-09 (см. `Клиенты/Корогва/Цели/goals.md`
— данные по старой цели до этой даты признаны ненадёжными), переопределяется
через `--conversions-date-from`.

## Гео-расширение групп объявлений Google Ads

```
python gads_geo_ad_group_builder.py --customer-id 213-621-6123 \
    --client-folder "Юристы США" --campaign "search / all injuries" \
    --target-campaign "search / all injuries / la" \
    --ad-groups "Bicycle Injury,Dog Bite Injury,Motorcycle Injury" \
    --geo "LA" --geo "Los Angeles" --group-suffix "LA" --ad-geo-text "LA"
```

Строит из вручную отобранных групп кампании-источника (`--ad-groups`, список
через запятую) гео-расширенные группы: ключи + RSA-объявления. На каждую
исходную группу — одна новая группа `<имя> <group-suffix>`, ключи внутри неё
дублируются в вариантах под каждый `--geo` (кроме ключей, где geo-вариант уже
есть в тексте — не задваивается), текст объявления один на группу с "CA"/
"California" заменённым на `--ad-geo-text`. Не заливает ничего сама — только
собирает CSV в формате Google Ads Editor bulk upload в `Статистика/` клиента,
заливка — вручную через Editor (Import -> From File, "Use Campaign/Ad group
columns" при маппинге). Может указывать целевую кампанию (`--target-campaign`),
отличную от источника — например, у Andverpersonalinjury кампания
"search / all injuries / la" уже существует и заполняется по частям (см.
`Клиенты/Andverpersonalinjury/Решения.md`, запись 2026-08-18).

Рабочий цикл — диалоговый, не автоматический: сначала выгружается список групп
кампании-источника (кол-во ключей/объявлений на группу) для отбора, отобранные
группы передаются в `--ad-groups`, результат (превью новых ключей/объявлений,
предупреждения о превышении лимита символов) утверждается перед тем, как
получившийся CSV идёт на заливку.

## Генератор базовой семантики (broad-фразы по словарю тем)

```
python gads_semantics_generator.py --client-folder "Юристы США"
python gads_semantics_generator.py --client-folder "Юристы США" --theme car --theme motorcycle
python gads_semantics_generator.py --client-folder "Юристы США" --theme car --geo "LA" --geo "Beverly Hills"
```

Не ходит в Google Ads API — читает словарь тем/синонимов клиента
(`Клиенты/<client-folder>/Семантика/Словарь-тем.yaml`) и строит все комбинации
"<тема> <modifier> <suffix>" как broad-фразы (напр. "car accident lawyer",
"car crash attorney"). У каждой темы свой набор modifiers в словаре — не один
общий на все темы, т.к. "accident"/"crash" естественны для транспортных тем, но
не для slip_and_fall/dog_bite/wrongful_death (см. `Клиенты/Andverpersonalinjury/Решения.md`,
запись 2026-08-18). `--geo` опционально достраивает гео-вариант на каждую фразу
(тот же принцип дублирования, что в gads_geo_ad_group_builder.py, но раньше по
процессу — до группировки по группам объявлений).

Выводит только список фраз на экран (и опционально в `--out файл.txt`) для
просмотра и одобрения — группировка одобренных фраз по группам объявлений и
заливка в аккаунт делаются отдельным следующим шагом (сверка с уже
загруженными в аккаунте ключами сознательно не делается здесь — см. решение).

Новую тему — добавить в YAML-словарь клиента вручную в Obsidian, скрипт
подхватит её на следующий запуск без изменений в коде.

## Адаптер объявлений и sitelinks по эталону

```
python gads_ad_adapter.py --client-folder "Юристы США" \
    --campaign "search / all injuries / la" --group-suffix "LA" \
    --theme bicycle --theme dog_bite --theme motorcycle \
    --with-sitelinks
```

Штампует по одному RSA-объявлению на тему из эталона, зафиксированного вручную
в `Клиенты/<client-folder>/Кампании/Search/Эталонное-объявление-и-sitelinks.yaml`
(headlines/descriptions с role=themed заменяются по полю `ad_phrase` темы из
`Словарь-тем.yaml`, role=universal копируются без изменений — см. пример
разметки в самом YAML-файле эталона и `Клиенты/Andverpersonalinjury/Решения.md`, запись
2026-08-18). `--with-sitelinks` добавляет в тот же CSV блок sitelinks на
уровень КАМПАНИИ (пустой Ad group — не дублируются по группам).

Автоматически укорачивает заголовки/описания, превышающие лимит Google Ads
(30/90 симв.) из-за длинной темы, срезая geo-хвост "in CA"/"CA" вне
{KeyWord:...}/{LOCATION(...):...} вставок (сами вставки не трогает — их лимит
считается по видимому тексту после двоеточия, не по всей записи). Что не
удалось уложить — выводится в предупреждение для ручной правки в CSV перед
импортом.

Чтобы завести эталон под нового клиента/кампанию — снять образец объявления
и sitelinks вручную (см. структуру полей в существующем YAML-файле как
референс) и разметить role themed/universal построчно вместе с пользователем.

## Сборка новой кампании "с нуля" из словаря тем

```
python gads_campaign_builder.py --client-folder "Юристы США" \
    --campaign "search / all injuries / broad" \
    --theme car --theme auto --theme motorcycle --theme rideshare \
    --budget 50
```

Комбинирует три блока выше (генератор broad/phrase-семантики + адаптер
объявлений + sitelinks) в один CSV для кампании, которой ЕЩЁ НЕТ в аккаунте —
в отличие от `gads_geo_ad_group_builder.py` (расширяет существующую кампанию
гео-дублями уже загруженных ключей), здесь ключи строятся ИСКУССТВЕННО из
словаря (см. `gads_semantics_generator.py`), а не копируются из другой
кампании. На каждую тему — одна группа с именем `label` из словаря (без
гео-суффикса), заполненная ключами (по умолчанию match type PHRASE — не
BROAD, для консистентности с остальным аккаунтом, переопределяется
`--match-type`), плюс адаптированное объявление и (один раз для всей
кампании) sitelinks — если не передан `--no-ads`/`--no-sitelinks`.

CSV включает строку `Campaign` (Search, статус Paused, бюджет-заглушка из
`--budget`) — Google Ads Editor обычно требует существующую кампанию для
импорта групп/ключей, поэтому она создаётся тем же файлом, но намеренно на

## Байесовский анализ срезов Search-кампании (тренд vs шум, план/факт)

```
python gads_bayesian_slice_analysis.py --customer-id 7552781705 \
    --client-folder "ProfiMet" --campaign "Search | Poliweglan | Pl" \
    --slice-by ad_group --weeks 8

python gads_bayesian_slice_analysis.py --customer-id 7552781705 \
    --client-folder "ProfiMet" --campaign "Search | Poliweglan | Pl" \
    --slice-by device --weeks 8
```

Реализация методологии
`База_знаний/Паттерны/Google-Ads-Search-байесовский-анализ-срезов-и-рычагов.md`
(Часть 2) — регулярный инструмент периодического аудита, не разовый скрипт.
Для заданного среза (`--slice-by ad_group|device|dow`) считает **sequential
Bayesian Beta-Binomial апостериор по неделям** (не по одному агрегату на весь
период и не независимо по каждой неделе) с discount factor (затухание веса
старых недель), сравнивает с апостериором кампании целиком (НЕ с prior — это
была первая ошибка реализации 2026-09-28, из-за которой P никогда не
поднималась выше ~0.3 ни для одного среза, см.
`Клиенты/ProfiMet/Решения.md`), классифицирует тренд (`TREND_UP`/`TREND_DOWN`/
`NOISE`/`STRUCTURAL_BREAK`/`INSUFFICIENT_HISTORY`) и выдаёт `Verdict`:
`CANDIDATE_ACTION_BAD/GOOD` (порог P пройден И тренд подтверждён),
`GREY_ZONE_WATCH_BAD/GOOD` (тренд подтверждён, P ниже порога — решение
зависит от состояния KPI месяца, см. Часть 3.0 методологии, не считается тут
автоматически), `WATCH_UNCONFIRMED_TREND` (высокая P, но тренд не
подтверждён — возможен шум), `NEED_MORE_DATA`, `WITHIN_NORMAL_RANGE`.

Параметры метода настраиваются флагами (`--prior-strength`, `--discount`,
`--delta`, `--action-threshold`, `--min-weeks`) — значения по умолчанию не
откалиброваны под конкретную нишу, это отправная точка, см. docstring
скрипта. Скрипт только считает и выводит — никаких изменений в аккаунте сам
не делает.

## Сверка звонков Ringostat vs конверсии Google Ads (ProfiMet)

python gads_calls_stats_profimet.py --date-from 2026-08-01 --by-week

Диагностика разрыва "сколько звонков реально зафиксировал коллтрекинг" vs

у Search (см. `gads_semantics.py`, ограничение `search_term_view` для PMax).
Клиент-специфичные скрипты (customer_id ProfiMet и AUTH_KEY Ringostat

диагностики этой конкретной задачи.

`ringostat_stats_profimet.py` копирует методологию уникальности звонков 1:1
из прод-скрипта `ringostat_profimet2` (единое множество caller по всем
источникам сразу, история для подсчёта — с 2025-08-01, вне зависимости от

искусственной меткой-заглушкой (`utm_campaign=calls_from_ads`) — кампанию
для них Ringostat физически не знает, в отчёте они помечаются отдельной
строкой, не путать с "источник не определён" по другой причине.

`gads_calls_stats_profimet.py` тянет конверсии Google Ads по кампаниям,

(на практике за 2026-08-01+ конверсий не дают), плюс встроенный тип Google
Ads `AD_CALL` ("Звонки по объявлениям") — отдельный от Ringostat механизм
замера звонков по номеру в объявлении.

## История изменений кампании (change_event) — для проверки причинности аномалий

```
python gads_change_history.py --customer-id 7552781705 \
    --client-folder "ProfiMet" --campaign "Search | Poliweglan | Pl"

python gads_change_history.py --client "Клиент - Google Ads" \
    --client-folder "Клиент" --date-from 2026-09-15 --date-to 2026-09-29
```

Реализация Gate-проверки 2 из `База_знаний/Паттерны/Алгоритм-анализа-
эффективности-кампании-блок-схема.md`: прежде чем объяснять колебание метрики
внешней причиной (рынок/сезонность/конкуренция/алгоритмическое переобучение),
нужно исключить более простое объяснение — правку, которую внесли в саму
кампанию (ставка/бюджет/target CPA/расписание/статус) в это же время. Без
этого скрипта такие причинные выводы оставались недоказуемыми гипотезами
(см. `Клиенты/ProfiMet/Решения.md`, запись 2026-09-30, и Ошибку 6 в
`Google-Ads-аудит-кампании-алгоритм-и-ошибки-смешения-данных.md`).

**Жёсткое ограничение API, не устранимое на нашей стороне** (подтверждено
эмпирически 2026-09-30 на ProfiMet, официальная документация Google заявляет
"30 дней", но реально `START_DATE_TOO_OLD` уже на ровно 30 днях назад —
скрипт использует запас 29 дней): ресурс `change_event` отдаёт историю
максимум за последние ~29-30 дней от даты запроса, максимум 10 000 строк.
Для периода анализа шире месяца (типичный случай для Шага 1 блок-схемы,
горизонты 30/90 дней) часть истории физически недоступна — скрипт печатает
явное предупреждение и обрезает `--date-from` до допустимой границы, не
подменяет отсутствующие данные молчанием. `change_status` даёт 90 дней, но
без old/new значений полей — только факт "что-то изменилось", без "как
именно" (недостаточно для проверки масштаба правки, п.2 чек-листа в
блок-схеме) — не заменяет `change_event` для этой задачи.

Выводит только изменения, потенциально влияющие на метрики (ставки/бюджет/
таргетинг/расписание/статус) — фильтр по ключевым словам в `changed_fields`,
не весь возможный шум (напр. правки текста объявлений сюда не подмешиваются,
если явно не влияют на показ/ставку). Отдельно печатает "правок по дням" —
прямая диагностика случая "неконтролируемые условия" из блок-схемы (частые
хаотичные правки за короткий период, когда причинность между конкретной
правкой и эффектом уже не разделима).

`--campaign` резолвит имя кампании в id отдельным запросом (change_event
не отдаёт имя кампании напрямую, только resource name с id) — без флага
показывает изменения по всему аккаунту.

## Проверка подмены номера коллтрекинга

> **С 2026-10-06 проверка строгая:** КАЖДЫЙ элемент с номером (tel:-ссылка — и `href`, и текст; текстовые узлы
> вне ссылок) должен показывать номер из пула, иначе MISMATCH с секцией и CSS-классом элемента. Каждый случай
> прогоняется на десктопе и мобиле (`--desktop-only` отключает мобилу). Номера сравниваются по последним 10
> цифрам; необязательный `ignore_numbers: [...]` в YAML пула — для номеров, которые законно не подменяются.
> Прежняя версия ("хоть один номер пула = OK") пропускала частичную подмену — см. [[../Инфраструктура]], 2026-10-06.
> Пулы: `Коллтрекинг/Пул_номеров*.yaml` клиента (для tilda-страниц Andverpersonalinjury — отдельные файлы по странице).

```
python phone_swap_check.py --client-folder "Andverpersonalinjury"
```

Проверяет, что сайт клиента правильно подставляет номер коллтрекинга для
заданного источника трафика. Открывает URL через headless-браузер (Playwright,
нужен реальный браузер — подмена делается JS-скриптом коллтрекинга
(Ringostat/Calltouch/CoMagic/Callibri) ПОСЛЕ загрузки страницы, в исходном
HTML/curl её не видно), подставляет тестовую UTM-комбинацию канала, снимает
`tel:`-ссылки и сверяет с пулом допустимых номеров этого канала — совпадение
с ЛЮБЫМ номером пула засчитывается как OK, т.к. сервисы коллтрекинга (см.
Ringostat) отдают номер из пула по сессии/ротации, а не жёстко один номер на
одну UTM-комбинацию (см. `Клиенты/Andverpersonalinjury/Решения.md`, запись 2026-08-18).

Пул номеров и условия подмены — ручной YAML `Клиенты/<клиент>/Коллтрекинг/
Пул_номеров.yaml` (формат описан в docstring скрипта), заполняется по
скриншотам из кабинета сервиса коллтрекинга. У Ringostat нет публичного API
для выгрузки пулов/правил подмены (проверено 2026-08-18) — авто-синхронизация
сейчас невозможна, актуализировать вручную при изменении настроек в кабинете.

Результат — CSV-снапшот в `Клиенты/<клиент>/Статистика/`, exit code 1 при
любом несовпадении (для встраивания в дальнейший мониторинг/расписание).

- **text** — обычный текстовый узел с номером, подходит стандартная
  full-replace маска Ringostat;
- **icon-only** — ссылка без текста, номер только в `href` (иконка-кнопка
  звонка, частый паттерн для мобильной вёрстки) — full-replace маской впишет
  цифры текстом рядом с иконкой и испортит вид, см. `База_знаний/Инструменты/
  Ringostat-механизм-подмены-номера.md`.

Кандидат XPath строится по классам предков (не по числовым индексам div —
те слетают при любой правке вёрстки), с проверкой количества совпадений
через сам браузер — берётся только вариант с 1-3 совпадениями, иначе честно
помечается `[ПРОВЕРИТЬ: матчит N элементов]` вместо того, чтобы молча выдать
бесполезный XPath. Автосгенерированные числовые id-классы Tilda
(`tn-elem__6514636821...`) используются только как последний резерв и
помечаются `[хрупкий id]` — подтверждено на практике ProfiMet, что такой id
слетает при пересборке блока в редакторе Tilda.

**Важный нюанс XPath 1.0**, всплывший при разработке: инлайн `<svg>` живёт в
XML-namespace, и голый шаг `svg` в XPath (`a[svg]`) никогда не совпадёт с
реальным `<svg>`-элементом, хотя `querySelector('svg')` в JS находит его без
проблем. Обход — `*[local-name()="svg"]` вместо голого `svg`. Это
ограничение XPath 1.0, а не Playwright — значит правило с голым `svg` не
заработает и в кабинете Ringostat, если у клиента иконка — инлайн-SVG, а не
`<img>`.

Только консольный вывод (не пишет в `Статистика/`) — это инструмент разовой
разведки перед настройкой, не регулярный мониторинг.

**ИЗВЕСТНОЕ ОГРАНИЧЕНИЕ (на 2026-09-01, не устранено):** скрипт не
различает "класс/элемент присутствует уже при загрузке страницы" от
"появляется только динамически после скролла" — а Ringostat сканирует DOM
именно в момент загрузки, не после скролла. На ProfiMet это привело к
тому, что скрипт (и ручная разведка до него) предложили XPath на класс
`t396__artboard-fixed-active`, который выглядел правильным в Playwright
ПОСЛЕ скролла, но был полностью нерабочим в реальном кабинете Ringostat,
потому что в момент загрузки страницы этого класса ещё не существовало
(см. `База_знаний/Инструменты/Ringostat-механизм-подмены-номера.md`,
раздел "и класс должен существовать ДО скролла" — там же и то, как искать
классы правильно, вручную, до исправления самого скрипта). Также не
сканирует скрытые блоки (бургер-меню, попапы) — только то, что видно на
странице без клика по триггерам, и не отличает узлы, скрытые от глаза
через CSS, от видимых (desktop/mobile часто physically один и тот же
HTML — см. ту же страницу базы знаний, раздел "один HTML-код"). Полный
список доработок — `Задачи.md` (корень), пункт про `phone_xpath_discovery.py`.

Общий инструмент (не завязан на EkspertAgro) для регулярного контроля
Shopping-кампаний в Поиске: сколько расхода уходит на запросы, где указан
размер товара (теплицы/тоннели у EkspertAgro, но логика такая же для
любого товара с размером в `title`), которого НЕТ в текущем фиде. Родился
из разбора [[../Клиенты/EkspertAgro/Мерчант/Решения|EkspertAgro]]
(2026-09-24): `search_term_view` считает метрики по тексту запроса, а не
по показанному товару — если точного размера нет в каталоге, Google
Shopping может показать товар-заменитель, и конверсия засчитается под
текстом исходного запроса. Разница между "деньги слились впустую" и
"устойчивый спрос закрывается заменителем" видна только по наличию
конверсий у конкретного размера-сироты — обе ситуации даёт один отчёт.

Список размеров, которые реально есть в фиде, берётся не из отдельного
XML-файла, а из `shopping_performance_view` (title товаров, показанных в
этой же кампании за тот же период) — не может устареть относительно
последнего экспорта фида. Подробности метода разбора размера из текста
(варианты написания: слитно/раздельно, кириллица "х", запятая/точка,
пробел вместо точки в дробной части, суффикс m/м для отличия от профиля
трубы) и известный потолок API (нет джойна `search_term_view` ↔
`product_item_id`, оценка идёт по совпадению текста, не по факту показа
конкретной карточки) — см. `Инфраструктура.md`, запись 2026-09-24.

По умолчанию сводка показывает ВСЕ размеры-сироты, включая 0 кликов — 0
кликов не значит 0 показов/сигнала (см. `Инфраструктура.md`, запись
2026-09-28: размер с 1 показом и 0 кликами один раз оказался реальным
случаем "спрос есть, конкретный товар просто не существует", а не шумом).
`--hide-zero-impressions` — скрыть строки без единого показа (это уже
почти наверняка мусор — цифры не из реального запроса о размере, а из
посторонних слов вроде толщины поликарбоната в мм). `--min-cost N` —
дополнительный фильтр по минимальному расходу. Результат — CSV со всеми
search terms кампании (с разметкой размера и признаком "есть/нет в фиде")
в `Статистика/` клиента, плюс сводка в консоль с топом размеров-сирот по
показам.

Для клиентов, у которых Shopping-кампания разбита на отдельные Ad Group по

находит поисковые запросы на размеры, которых нет в фиде вообще (не
относительно ожидаемого размера самой группы, а относительно полного

(`fetch_feed_sizes`) из `gads_shopping_size_gap_monitor.py` — не отдельная
копия логики.

решению пользователя — Google Ads минус-слова регистронезависимы, а
кириллица в самом запросе нужна только для распознавания размера, не для
итоговой фразы). Для дробных размеров генерируются три варианта дробной
части: точка/запятая/пробел ("2.5x4"/"2,5x4"/"2 5x4").

Дата последнего запроса хранится в
`<client-folder>/Статистика/shopping_size_negatives_state_<кампания>.json`
— обычный запуск без `--date-from`/`--date-to` сам берёт период с
следующего дня после сохранённой даты, не нужно каждый раз помнить и
передавать период вручную. Если новых завершённых дней ещё нет — скрипт
сообщает об этом и не делает запрос к API.

По умолчанию показывает и генерирует минус-фразы для ВСЕХ найденных новых
размеров, включая 0 кликов (изначально скрывались — оказалось, что размер
с реальным показом, но 0 кликами, может быть полезным сигналом, не только
шумом, см. `Инфраструктура.md`, запись 2026-09-28). `--hide-zero-impressions`
— скрыть только то, что не получило вообще ни одного показа (это уже
почти наверняка мусор из посторонних слов запроса). `--exclude-ad-group`
(можно указывать несколько раз) — исключить группу из разбора, обычно
общую "all products", где по определению могут быть любые размеры и
понятие "новый размер" не применимо так же строго.

Один запуск = одна проверка; либо в цикле самим скриптом: `--loop-min 30` (проверка каждые 30 минут, пока открыто окно терминала; остановка Ctrl+C; завершается сам, когда по всем кампаниям работа закончена; предохранитель `--loop-hours`, по умолчанию 12). Планировщик Windows не использовали: создание фонового задания было заблокировано системой разрешений. Поднимает только вверх, только у ENABLED со стратегией `TARGET_SPEND`, только внутри расписания показов кампании (читает из API, часовой пояс `--tz`, по умолчанию Europe/Warsaw), не выше `--cap`, не чаще раза в `--cooldown-min`. Как только показов с момента первого запуска стало ≥ `--min-impressions` — останавливается; если потолок дошёл до `--cap`, а показов нет — пишет вердикт «дело не в ставке». Без `--execute` только `validate_only` и строки «поднял бы» в логе. Лог — `Статистика/gads_display_bid_ramp_log.csv`, состояние — `gads_display_bid_ramp_state.json` (чтобы начать заново — удалить запись кампании из файла состояния). Сначала запускать вручную без `--execute`.

## Кампанийные минус-слова: `gads_add_campaign_negatives.py` и `gads_remove_campaign_negatives.py` (ЗАПИСЬ, по умолчанию validate_only)

Add пропускает уже существующие; remove пишет снимок «до» всех минусов кампании в `Статистика/`. Оба читают обратно. `gads_set_conversion_values.py --customer-id … --client-folder … [--execute]` — обнуляет ценность у всех включённых лид-конверсий (значение 0, «всегда по умолчанию»), кроме содержащих «Отгружено» (реальная сумма продаж); снимок «до» в Статистика/, чтение обратно. `gads_set_conversion_attribution.py --customer-id … --client-folder … [--execute]` — переводит включённые конверсионные действия с атрибуцией «управляемая данными» на «последний клик»; GA4-действия пропускает (их модель задаёт GA4), старые UA Google менять не даёт. Снимок «до», чтение обратно.
