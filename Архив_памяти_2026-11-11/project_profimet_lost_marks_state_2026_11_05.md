**Готово:** черновик GTM версия **94** (база 93 + поле `mark_source`: url/rb_utm/tildautm, колонка создана пользователем 05.11; публиковать 94, не 93). Версия 93: (скрипт `Скрипты/gtm_marks_without_consent.py`): тег 117 берёт метки адрес → `rb_utm` → `TILDAUTM` (только utm_*), пишет fbclid/gbraid/wbraid; тег 147 сохраняет их в rb_utm; новый тег 270 дописывает метки во внутренние ссылки, пока нет ad_storage. Тест A/B/C пройден (Хроника_2026-11 05.11). ОПУБЛИКОВАНА 05.11 (живая 94, проверено живым аудитом), откат — `gtm_publish_version.py --account 6003760261 --container 44158621 --version 92 --execute`. Затем замер через 3–5 дней: доля реальных заявок с меткой против числа форм Tilda.

**Находки:** (1) живая версия GTM была 92 (тег Ringostat Phone call, опубликована не нами), не 91. (2) `TILDAUTM` хранит значения в нижнем регистре — `gclid` из неё не брать. (3) CRM читает метку из адреса страницы отправки (84 из 84), механизм не доказан — вопрос клиенту про CRM (задача 06.11) открыт. (4) В `profimet_leads` с 01.10 746 строк, 659 в пустых пачках (284 — тестовые прогоны GTM, `page_url` gtm-msr.appspot.com; ~375 пачек по 5 неизвестного источника), с телефоном 46; считать только после фильтра. (5) Колонки fbclid/gbraid/wbraid есть; `mark_source` создана 05.11.

**Why:** CRM клиента не берёт `utm_*` из заявки Tilda; интеграцию с CRM в Tilda не нашли.

**How to apply:** следующий шаг — замер через 3–5 дней (см. И-099 в Журнале). Слой «метки в адрес для CRM» (replaceState) не делали, нужно решение.
