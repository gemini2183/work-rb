# Инфраструктура

Это не база знаний по контекстной рекламе (для этого — `База_знаний/`) и не лог
решений по конкретному клиенту (для этого — `Клиенты/<клиент>/Решения.md`).
Здесь — история решений о том, как устроена сама система: вики, скрипты,
автоматизация. Формат — как везде: `## [ГГГГ-ММ-ДД] тема | решение | почему`.

Если тут наберётся много разноплановых страниц (не просто хронология, а
несколько независимых тем) — превратить в папку `Система/` со своим index.md.
Пока хватает одного файла.

## [2026-07-16] Скрипты сбора статистики (Директ / Метрика)

Расположение: `Скрипты/direct_stats.py`, `Скрипты/metrika_stats.py`, общий модуль
`Скрипты/_config.py`. Подробности запуска — `Скрипты/README.md`.

**Решение:** один скрипт на источник данных (не по скрипту на клиента) —
различие между клиентами только в логине/токене/номерах целей, структура
запроса одинаковая.

**Почему:** логин/токен/счётчик Метрики не дублируются в этой вики — читаются
напрямую из общей Google-таблицы (`1ymDNHkj32mYIb_ymf7t8O6H6WY1s5F1FN43-56fwiQM`,
вкладки "Директ"/"Metrika"), той же самой, что питает продовый BigQuery-пайплайн
в `E:/PythonProjects/RedBird/google-cloud-jobs`. Единый источник правды — если
токен обновится там, здесь ничего менять не нужно. Доступ — через service
account `Скрипты/secrets/rb_cloud_service.json` (скопирован оттуда же, не в git,
read-only к таблице).

Логика запроса адаптирована из `google-cloud-jobs/redbird/func/direct_stats_job_src`
и `metrika-stats-job_src`, но без BigQuery/Google Sheets записи — работает на
одного клиента за раз, кладёт TSV/CSV снапшот прямо в
`Клиенты/<клиент>/Статистика/`.

**Проверено:** 2026-07-16 — успешный запуск на клиенте [[ЕГЭ Merlin]] (реальные
данные по кампаниям и визитам получены).

**Открытый вопрос:** пока запуск ручной. Если станет неудобно — обсудить
автоматизацию (cron/Task Scheduler) с фиксированной периодичностью снапшотов.

## [2026-07-16] Разделение База_знаний/Инструменты vs Инфраструктура

**Решение:** `База_знаний/Инструменты/` — строго только отраслевое знание
(фичи/инструменты Директа и Ads), извлечённое из статей и мануалов, которые
приносит пользователь, со статусом протестировано/не протестировано на наших
кампаниях. Документация про наши собственные скрипты и устройство вики туда не
попадает — для этого этот файл (`Инфраструктура.md`) и `Скрипты/README.md`.

**Почему:** изначально страница про скрипты сбора статистики была ошибочно
положена в `База_знаний/Инструменты/` — смешала внешнее отраслевое знание с
внутренней документацией инструментов. Это две разные вещи с разной судьбой:
знания из статей растут от источников и не меняются, когда меняется наш код;
факты про нашу инфраструктуру меняются, когда меняется наш код, и не зависят от
новых статей.

## [2026-07-16] Схема целей дашборда: Директ (расход/клики) + Метрика (цели) + колл-трекинг (звонки) напрямую

**Решение:** так же, как в проде — расход и клики берём из Директа, конверсии
(заявки через сайт) — из целей Метрики, а звонки, если у клиента подключён
колл-трекинг — из API колл-трекинг-сервиса напрямую, а не из целей Метрики.

**Почему:** источник трафика "Яндекс.Директ: не определено" в Метрике иногда не
долетает до правильной атрибуции — часть звонков просто не попадёт в отчёт,
если брать их только из целей Метрики. Это видно в таблице (вкладка "Metrika")
по колонкам `goal_id` (обычная цель Метрики) / `ct_goal_id` (цель
колл-трекинга) / `ct_goal_source` — если `ct_goal_source` заполнено (например,
`api`), звонки нужно брать из API этого сервиса, а не из Метрики.

**Открытая задача:** у нас пока нет скрипта, который тянет звонки из API
колл-трекинга (для ЕГЭ Merlin это Callibri, см. [[Клиенты/ЕГЭ Merlin/Цели/goals|Цели ЕГЭ Merlin]]).
Из-за этого текущий анализ по заявкам неполный — метрика-конверсии видим, звонки
нет. Нужно писать `callibri_stats.py` по аналогии с `direct_stats.py` /
`metrika_stats.py`, когда будем разбираться со звонками для реального KPI.

## [2026-07-24] Второе агентство в этой же вики: Adwhite (Google Ads)

**Решение:** помимо Redbird (Директ), в вики теперь ведётся второе агентство —
Adwhite (Google Ads/Merchant Center). У него отдельная общая Google-таблица
клиентов (`SHEET_URLS["adwhite"]` в `Скрипты/_config.py`, отдельно от
`SHEET_URLS["redbird"]`), с похожей, но не идентичной структурой вкладок
(`Google_Ads_API` вместо `Директ`/`Metrika`). `get_client_row(...,
agency="redbird"|"adwhite")` — параметр таблицы, по умолчанию `"redbird"`.

Доступ к Google Ads API (в отличие от Директа/Метрики, где REST+токен) требует
библиотеки `google-ads` (добавлена в `requirements.txt`) и OAuth-кредов
`Скрипты/secrets/google-ads.yaml` (developer_token/client_id/client_secret/
refresh_token/login_customer_id — MCC), скопированных из
`E:/PythonProjects/RedBird/google-cloud-jobs/adwhite/func/<любой gads-job>/google-ads.yaml`.
Не в git (папка `secrets/` целиком в `.gitignore`).

Написан общий `Скрипты/gads_stats.py` (трафик + конверсии одним GAQL-запросом
к ресурсу `campaign`, конверсии разбиваются по `segments.conversion_action_name`,
не суммируются — чтобы не терять смену основной цели конверсии во времени) и
первый клиент-специфичный `Скрипты/gads_stats_korogva.py` (клиент [[Клиенты/Корогва/index|Корогва]]:
один аккаунт Google Ads, разбитый на два подпроекта "Google Ads"/"Merchant
Center" по маркеру в названии кампании — `Sales`/`Merchant_` — не по
отдельному customer_id; 1:1 логика прод-job'ов `gads_korogva_gads`/
`gads_korogva_merchant`).

**Почему:** у клиента Корогва раньше трафик и конверсии собирались из разных
источников (Google Ads API + отдельно GA4) — сейчас переводим на единый
источник, GA4 больше не подключаем на этом этапе.

**Проверено:** 2026-07-24 — `gads_stats_korogva.py` прогнан на реальных данных
(11–17 июля), оба подпроекта собрались корректно.

**Открытый вопрос:** алгоритм анализа кампании для Google Ads/Корогвы —

## [2026-07-29] Третье направление: ВКонтакте — агентная генерация объявлений (в разработке)

**Контекст:** по мотивам кейса Anthropic Growth Marketing team (slash-команда
`/rsa` + два саб-агента по RSA-полям + experiment memory log, см.
`База_знаний/Источники/Кейс-Anthropic-Growth-Marketing-Claude-Code.md` и вывод

напрямую, а как slash-команда/агент внутри Claude Code.

**Решение (архитектура саб-агентов):** в отличие от оригинала (деление по
формальному лимиту headline/description), для VK делим саб-агентов по
смысловой роли — агент **"Заголовок"** (короткий вовлекающий элемент, до 40
симв.) и агент **"Текст"** (весь текст объявления целиком, включая собственный
хук в первой строке — в ленте ВК заголовок и текст показываются вместе, но
хук физически должен быть в тексте, т.к. отдельного поля "хук" в интерфейсе
нет). Подробности и открытые вопросы по этому делению —
`База_знаний/Паттерны/Структура-объявления-ВКонтакте-заголовок-хук-текст.md`.

**Решение (мультинишевость):** предыдущие попытки сделать один универсальный
инструмент под все ниши проваливались — по всей видимости, потому что нишевая
специфика зашивалась прямо в промпт агента и размывалась. Вместо этого —
четырёхслойная модель контекста, подмешиваемого в вызов саб-агентов (подробнее
и с обоснованием четвёртого слоя —
`База_знаний/Паттерны/Агентная-генерация-объявлений-архитектура.md`):
1. **Площадка** (VK) — общие правила/лимиты/механики ленты, не зависит от ниши.
2. **Ниша** — примеры хуков/болей/тона конкретно под нишу, растёт из практики.
3. **Клиент** — бренд-тон и специфика конкретного проекта (уже покрывается
   `Клиенты/<Имя>/_project.md`).
4. **Цель кампании** (подписаться / написать сообщение / далее по мере
   появления новых целей VK) — влияет только на то, к какому действию должен
   логически подводить финал текста саб-агента "Текст"; сама структура
   объявления (заголовок+текст) от цели не зависит, меняется только CTA-кнопка

Агент (роль "Заголовок"/"Текст") остаётся один и тот же для всех ниш и целей —
меняются только данные слоёв 2/3/4, которые ему подмешивают на входе, а не сам
промпт/код.

## [2026-08-18] Семейство скриптов Google Ads Editor bulksheet (гео-расширение и генерация семантики с нуля)

**Решение:** четыре новых скрипта в `Скрипты/`, читающих Google Ads API
только на чтение и собирающих CSV в формате Google Ads Editor bulk upload —
ничего не пишут в аккаунт напрямую, заливка всегда вручную через Editor:

- `gads_geo_ad_group_builder.py` — расширяет СУЩЕСТВУЮЩУЮ кампанию: берёт
  вручную отобранные группы кампании-источника, строит из них гео-варианты
  (дублирует каждый ключ под несколько geo-суффиксов внутри одной новой
  группы, адаптирует текст объявления заменой "CA"/"California" на короткий
  geo-текст).
- `gads_semantics_generator.py` — генерирует широкие/фразовые ключи из
  словаря тем клиента (`Клиенты/<клиент>/Семантика/Словарь-тем.yaml`):
  перемножение тема × модификатор происшествия × юридический суффикс. Только
  печатает список для одобрения, ничего не группирует и не заливает.
- `gads_ad_adapter.py` — штампует RSA-объявление по зафиксированному эталону
  (`Клиенты/<клиент>/Кампании/Search/Эталонное-объявление-и-sitelinks.yaml`,
  headlines/descriptions размечены role themed/universal) под каждую тему +
  готовит sitelinks на уровень кампании.
- `gads_campaign_builder.py` — комбинирует предыдущие два (генератор
  семантики + адаптер объявлений) в один CSV для НОВОЙ кампании "с нуля":
  строка `Campaign` (Search, статус Paused, бюджет-заглушка) + группы по
  темам словаря + сгенерированные ключи + объявления + sitelinks.

**Почему такое разделение на 4 скрипта, а не один универсальный:** это два
разных сценария использования (расширить то, что уже есть в аккаунте
гео-вариантами / построить что-то новое искусственно из словаря), которые
делят только форматирующую логику (CSV Google Ads Editor, проверка лимитов
символов, адаптация текста объявления по теме) — вынесена в переиспользуемые
функции, импортируемые между скриптами, а не продублирована.

**Технический баг, исправленный по ходу (актуален для любого нового скрипта,
работающего с текстом RSA-объявлений):** лимит символов Google Ads (30 симв.
Headline, 90 Description) для динамических вставок `{KeyWord:...}` и
`{LOCATION(...):...}` считается по видимому тексту ПОСЛЕ последнего `:`
внутри скобок, не по всей синтаксической записи со скобками — и вставка
может быть частью более длинной строки (не только всей строкой целиком).
Обе ошибки давали ложные "превышения лимита" при первой версии проверки.

**Рабочий цикл — диалоговый, не автоматизированный сквозняком:** пользователь
явно называет, какие группы/темы брать на каждом шаге; скрипты выводят
превью и предупреждения о превышении лимитов символов для ручного review
перед запуском следующего скрипта или импортом в Editor. Обсуждалась
альтернатива (Streamlit-приложение с чекбоксами) — отклонена пользователем
в пользу диалогового цикла в чате, см. `Клиенты/Andverpersonalinjury/Решения.md`.

**Открытый вопрос:** сверка сгенерированной семантики с уже загруженными в
аккаунте ключами (чтобы не предлагать дубли) сознательно не реализована —
решено полагаться на подсветку дублей самим Google Ads Editor при импорте.
Если это станет узким местом при регулярном использовании — реализовать
отдельным шагом (GAQL-запрос по всему аккаунту + diff со сгенерированным
списком).

## [2026-08-19] Аудит сетей показа Google Ads (Search vs Search Partners) — новый скрипт + подтверждён доступ без строки в таблице

под одного клиента, не по общему паттерну "один скрипт на источник для всех
клиентов"). Использует отдельный OAuth-токен с правом `promopages:api` —
НЕ тот же токен/механизм, что у Директа/Метрики (`Скрипты/_config.py` сюда не
относится, там только Google Sheets service account).

**API:** `GET /campaigns` (список кампаний, `title` совпадает 1:1 с UTM Campaign
в Метрике — можно сводить датасеты по названию без доп. маппинга) и отчёт
`campaigns-daily-stats` (POST создать отчёт → GET по `reportId`, до готовности
код 202) с полем `budget` (расход в руб.) по кампании/дню.

**Важное ограничение, подтверждённое эмпирически:** в API Promo Pages НЕТ
гео-разреза вообще — ни в `campaigns-daily-stats`, ни в
`campaigns-publications-daily-stats` (второй report type в скрипте). Расход
считается и таргетируется только на уровне кампании/публикации, не региона.
Гипотезу "какой-то конкретный город/регион съедает непропорционально много
бюджета" по этому источнику проверить нельзя в принципе — не ограничение
скрипта, ограничение самого API.

**Результат первого запуска:** сохранено в

**Открытый вопрос:** если у других клиентов тоже используются Promo Pages,
стоит перенести `promopages.py` в `Скрипты/` и обобщить по паттерну README

захардкоженным в файле, а либо в `secrets/`, либо в общей таблице — сейчас

клиента, не общий паттерн.

**КРИТИЧЕСКОЕ ОГРАНИЧЕНИЕ, найденное 2026-08-25:** `GET /campaigns` НЕ
отдаёт статус кампании (Активна/Остановлена/Архив) — только булево поле
`isArchived` (и то отсутствует в ответе для неархивных кампаний вместо
`false`, т.е. "нет поля" нужно трактовать как "не в архиве"). Различие
"Активна" vs "Остановлена" в интерфейсе кабинета в API вообще никак не
отражено — ни отдельным полем, ни косвенно. Проверено на конкретном кейсе:
кампания `6a5dfc0b4d523600932b216c` в кабинете помечена "Остановлена", в
API `isArchived` отсутствует (как у активных) — стороннему потребителю
API кажется такой же "живой", как реально активная. Единственный косвенный
способ через API — смотреть факт расхода/показов в `campaigns-daily-stats`
за последние N дней (0 = скорее всего остановлена или архив), но это
ненадёжно: активная кампания с низким CTR/высокой ставкой тоже может дать
0 показов за случайный короткий период, и наоборот. Для точного статуса
кампаний **нет замены ручной сверке со скриншотом раздела "Текущие" в
кабинете** — при любом анализе активных/неактивных кампаний клиента
запрашивать этот скриншот у пользователя, не полагаться на `isArchived`
или на факт расхода как на прокси статуса.

## [2026-09-24] Новый скрипт: мониторинг Shopping-запросов на размеры вне фида

Написан `Скрипты/gads_shopping_size_gap_monitor.py` — общий инструмент (не
завязан на EkspertAgro, параметры `--client`/`--customer-id` + `--campaign`
+ `--client-folder` по паттерну остальных `gads_*.py`) для регулярного
мониторинга Shopping-кампаний в Поиске: сколько расхода уходит на поисковые
запросы, где указан размер товара, которого нет в текущем товарном фиде.

**Зачем понадобился:** при разборе Shopping-кампаний
[[Клиенты/EkspertAgro/Мерчант/Решения|EkspertAgro]] обнаружилась ловушка
метода — `search_term_view` считает метрики по ТЕКСТУ запроса, а не по
показанному товару. Если в запросе указан размер, которого нет в каталоге
(напр. "szklarnia 3x5" при отсутствии товара 3x5 в фиде), Google Shopping
может показать ближайший товар-заменитель — клик/конверсия при этом
засчитываются под текстом исходного запроса. Разовый анализ принял это за
"теплица 3x5 продаётся", хотя такого товара физически нет. Скрипт делает
это разделение на каждый запуск, чтобы не полагаться на разовую ручную
проверку.

**Источник списка размеров фида — не отдельный XML-файл**, а
`shopping_performance_view` (title показанных товаров за тот же период) —
так список размеров всегда соответствует текущему состоянию Merchant
Center в аккаунте, не зависит от того, свежий ли лежит XML-снапшот в
`Статистика/`.

**Разбор размера из текста** учитывает варианты написания, реально
встреченные в данных (не гипотетические): слитно/раздельно ("3x6"/"3 x 6"),
кириллическая "х", запятая/точка как разделитель дробной части
("2,5x4"/"2.5x4"), пробел ВМЕСТО точки ("3 5x6" = "3.5x6" — Google иногда
режет запрос на токены по пробелу; распознаётся только по паттерну "N 5"
сразу перед "x", т.к. в ассортименте реально есть ширины 2.5/3.5м, а "5"
как целая ширина не встречается — более общее правило "цифра пробел
цифра" сломало бы обычное "2 x 3"), суффикс "m"/"м" в title, который нужен
только там, чтобы отличить реальный размер теплицы от паразитного второго
числового паттерна профиля трубы в том же title ("...2,5x4m profil
40x20mm..." — второе число всегда с "mm", не "m").

**Известный технический потолок**, не устранённый и неустранимый на
стороне скрипта: Google Ads API не даёт джойна `search_term_view` ↔
`product_item_id` — это разные ресурсы (см. также `Скрипты/README.md`,
секция про `gads_semantics.py`, для PMax то же ограничение). Сопоставление
"размер в фиде да/нет" — оценка по совпадению текста, не точная связка
клика с конкретной показанной карточкой.

Провалидирован на исторических данных `shop1 /search` (нашёл известные из
ручного разбора конверсии по 2x3/3x5 через товары-заменители) и на
активной `shop_search` (числа расхода по 2x3/3x5 совпали с ручным
подсчётом день в день). По умолчанию скрывает размеры-сироты с 0 кликов
(`--show-zero-clicks` — включить обратно) — это в основном случайный
текстовый шум (толщина поликарбоната в мм и т.п.), не реальные запросы.

**Два бага найдены и исправлены при проверке юнит-тестами до сдачи
(2026-09-24, после вопроса пользователя "учитываешь ли написание с 'm'"):**
1. Негативный лукахед на профиль/толщину проверял только латинское "mm",
   пропуская кириллическое "мм" — реальный запрос из данных клиента
   "теплица своими руками из бруска 50х50 мм" (сечение бруска в мм, не
   размер теплицы) ложно распознавался бы как размер "50x50". Добавлена
   кириллица в лукахед.
2. После этого фикса лукахед внутри жадной группы `\d+` спровоцировал
   backtracking: на "50х50 мм" регэксп сам укорачивал второе число до "5",
   чтобы обойти запрет, и всё равно матчил "50x5" — валидная часть строки
   для лукахеда, невалидная по смыслу. Решение — зафиксировать границу
   числа через `\b` ДО лукахеда на суффикс, а не полагаться на "не mm/мм
   сразу здесь" внутри той же группы. Это привело к третьему следствию:
   слитное "3x6m" (без пробела) перестало ловиться универсальным `\b`-
   паттерном (нет границы слова между цифрой и слитной буквой) — решено
   тем, что `extract_size_from_term` теперь сначала пробует паттерн С
   явным суффиксом (`_SIZE_WITH_UNIT_RE`, тот же, что для title фида), и
   только затем общий паттерн без суффикса как fallback.

Урок для будущих правок этого файла: любой regex с негативным лукахедом
на суффикс внутри жадной числовой группы стоит сразу тестировать на
"число+пробел+суффикс" (не только слитно) — backtracking там неочевиден
и не ловится на глаз при чтении паттерна.

После этого случая в сам скрипт добавлен встроенный `--self-test` (33
регрессионных случая на `extract_size_from_term`/`extract_size_from_title`,
без обращения к API) — прогонять после любой правки `_SIZE_WITH_UNIT_RE`/
`_SIZE_ANY_RE`/`_SPACED_DECIMAL_RE`, не проверять новые regex-фиксы
разовыми bash-командами, которые пропадают вместе с сессией.

## [2026-09-28] Новый скрипт: регулярный генератор минус-фраз по размерным Ad Group

Написан `Скрипты/gads_shopping_size_negatives_by_group.py` — переиспользует

`gads_shopping_size_gap_monitor.py` (2026-09-24), не дублирует парсер
размера. Появился, когда пользователь для `shop_search` вручную разбил
кампанию на отдельные Ad Group по размеру (`3x4`, `3x6`, `2x4`, `4x6`,

`Клиенты/EkspertAgro/Мерчант/Решения.md`, запись 2026-09-28) и попросил
регулярный инструмент: по каждой такой группе смотреть её поисковые
запросы, находить размеры, которых нет в фиде вообще, и сразу готовить
список минус-фраз для занесения в аккаунт.

**Отличие от `gads_shopping_size_gap_monitor.py`:** тот даёт общую картину
по кампании целиком (сколько денег уходит на запросы вне фида), этот —
разбивает по `ad_group.name` (Google Ads API отдаёт его прямо в
`search_term_view`, без доп. join) и сразу генерирует готовые минус-фразы,
а не только отчёт для последующего ручного составления списка (это было
ключевой болью — пользователь несколько раз вручную просил "составь минус
фразы для этого размера" после того, как находил его в отчёте, каждый раз
отдельным запросом; теперь это один шаг).

**"Новый размер" определяется относительно ПОЛНОГО фида, не относительно
ожидаемого размера конкретной группы** — это осознанный выбор: трафик по
"3x6" в группе "3x4" (размер, который есть в фиде, просто должен был уйти
в другую группу) это проблема таргетинга/группировки, не тема этого
скрипта; трафик по "2x3" (которого нет нигде в каталоге) — то, что нужно
минусовать.

**Генератор минус-фраз** (`generate_negative_phrases`) — тот же принцип,
что вручную делался для пользователя в чате несколько раз подряд до этого
скрипта: слитно/раздельно вокруг "x", суффикс "m"/" m", и для дробных
размеров — три варианта записи дробной части (точка/запятая/пробел, напр.
"2.5x4"/"2,5x4"/"2 5x4"). По явному решению пользователя (2026-09-27) —
только нижний регистр без кириллической "х" в самих фразах (Google Ads
минус-слова регистронезависимы, кириллица нужна была только для детекции
размера в тексте запроса, не для итоговых фраз для загрузки). Тип
соответствия — фразовое (в круглых кавычках при загрузке), не точное: по
запросу пользователя, фразовое отсечёт "3x6" в любом контексте ("szklarnia
3x6", "3x6 producent" и т.п.), не задевая соседние размеры вроде "2x3".

**Хранение состояния между регулярными запусками** — маленький JSON
`<client-folder>/Статистика/shopping_size_negatives_state_<кампания>.json`
с полем `last_date_to`. Каждый следующий запуск без явных `--date-from`/
`--date-to` сам продолжает с дня после сохранённой даты — без этого
регулярная задача требовала бы каждый раз помнить и подставлять период
вручную. Если ещё не прошло ни одного нового полного дня — скрипт явно

## [2026-09-28] Баг парсера размера: терялась вторая дробная часть при "N 5xM 5"

После вопроса пользователя "почему в отчёте нет размера 5x2,5 — его нет в
фиде или анализ плохой" нашёлся третий баг в `_join_spaced_decimals`
(`gads_shopping_size_gap_monitor.py`, см. записи 2026-09-24 про первые два
бага того же семейства). Правило "N 5, сразу за которым x" (введено для
случая "3 5x6" = "3.5x6") требовало "x" СРАЗУ ПОСЛЕ дробной части — но не
покрывало симметричный случай, когда дробная ВТОРАЯ половина размера тоже
написана через пробел и стоит в конце запроса, без "x" после себя: реальный
запрос "szklarnia 2 5x2 5" (должен быть "2.5x2.5") молча терял вторую
половину и распознавался как "2.5x2" — который, в отличие от "2.5x2.5",
реально существует в фиде. Из-за этого запрос ложно засчитывался как
"размер есть в каталоге" и пропадал из отчёта о размерах-сиротах.

**Исправление:** добавлено симметричное правило `_SPACED_DECIMAL_AFTER_RE`
(`(?<=[xх])\s*(\d)\s+5\b`) — схлопывает "N 5" в "N.5", когда оно идёт
СРАЗУ ПОСЛЕ "x"/"х" (а не только когда идёт перед ним, как раньше).
Обновлён `--self-test` (добавлены случаи "2 5x2 5" -> "2.5x2.5" и
"2x2 5" -> "2x2.5") — все прошли, включая ранее существовавшие 33 случая.

Практическое следствие при пересчёте `shop_search` (2026-08-29 —
2026-09-27): размер "2.5x2.5" теперь корректно виден как отсутствующий в
фиде (запрос "szklarnia 2 5x2 5" в группе `2x4`), но с 0 кликов за этот
период — на момент этого пересчёта скрывался фильтром `--show-zero-clicks`
по умолчанию (см. следующую запись — этот фильтр сразу после пересмотрен и
заменён), не из-за самого бага парсера. Основной список 7 размеров с
реальными кликами не изменился — баг задевал только этот один конкретный
кейс с нулевым трафиком на момент проверки, не исказил уже принятые
выводы.

## [2026-09-28] Пересмотр дефолта: "0 кликов" скрывалось, хотя это не значит "0 показов"

Пользователь спросил прямо: "какого хера ты скрываешь с показами, но без
кликов?" — по делу. Оба скрипта (`gads_shopping_size_gap_monitor.py` и
`gads_shopping_size_negatives_by_group.py`) по умолчанию скрывали
размеры-сироты с 0 кликов через `--show-zero-clicks` (нужно было явно
включать, чтобы увидеть). Это было решение автора скриптов, принятое без
подтверждения пользователем, и оно спрятало реальный кейс: "2.5x2.5" (см.
запись выше) получил 1 показ и 0 кликов — данные были, просто скрыты по
умолчанию, а не "не существовали".

**Исправлено:** порог фильтрации сдвинут с "клики" на "показы" — по
умолчанию видно ВСЁ, включая 0 кликов (только не 0 показов сразу же — это
и есть минимальный порог "запрос вообще был"). Новый флаг
`--hide-zero-impressions` в обоих скриптах — на замену `--show-zero-clicks`
(инвертированная логика: раньше по умолчанию скрыто, теперь по умолчанию
показано, флаг явно СКРЫВАЕТ, а не показывает). Строка с 0 показов — это
уже почти наверняка текстовый мусор (число из постороннего слова в
запросе, не размер), поэтому именно эту границу оставили как единственный
дефолтный фильтр. Агрегации в обоих скриптах дополнены колонкой
`impressions`, которой раньше не было (сортировка тоже переключена на неё
вместо cost/clicks) — без неё нельзя было отличить "0 кликов, но был
показ" от "вообще ничего не было".

**Урок:** не молчаливо занижать полноту отчёта ради "чистоты" вывода —
если добавляется фильтр по умолчанию, который прячет часть сырых данных,
явно проговаривать это пользователю в момент внедрения фильтра, а не
только документировать постфактум в README. Молчаливая фильтрация — это
решение за пользователя, которое он не одобрял.

## [2026-10-08] Подход «запись макроса» для агентов: каталог операций вместо дословного повтора

## [2026-10-09] Офлайн-выгрузка конверсий по gclid: старый сервис Google закрыт, нужен Data Manager API

Проверка Google (`validate_only`) на `ConversionUploadService.UploadClickConversions` вернула `CUSTOMER_NOT_ALLOWLISTED_FOR_THIS_FEATURE`: для новых интеграций Google требует Data Manager API (аккаунту 7552781705 доступ к старому сервису не разрешён, несмотря на то что конверсии типа UPLOAD_CLICKS в нём уже есть). Общее правило для всех клиентов: перед написанием офлайн-загрузчика по gclid сначала проверить `validate_only` на старом сервисе, не писать весь код под него. Data Manager API: область `https://www.googleapis.com/auth/datamanager`, developer token не нужен, API включается в проекте Cloud, адрес назначения — `operatingAccount` + числовой `productDestinationId` (id конверсии), лимит 10 000 событий на запрос (по пересказу поиска; структуру запроса сверять с документацией). Для Ringostat: gclid извлекается из `utm_content` регулярным выражением `gclid[_=]…`; у 81% уникальных звонков Google CPC за 90 дней он есть.

**Дополнение 2026-10-09 (решено):** выгрузка переписана на Data Manager API и работает: `datamanager_auth.py` (одноразовая авторизация браузером, область `https://www.googleapis.com/auth/datamanager`, токен в `Скрипты/secrets/` — вне git), `POST https://datamanager.googleapis.com/v1/events:ingest`, `eventSource` PHONE для звонков (значение CALL из документации-пересказа не принимается), `validateOnly` в теле запроса, пачка отвергается целиком при ошибке формата — поэтому скрипт выбрасывает плохие события и повторяет; успех обработки видно не в ответе (там только `requestId`), а позже в отчётах Google Ads. Регулярный запуск — цикл `--loop-min`, потому что Планировщик Windows заблокирован. Для других клиентов с Ringostat/gclid в `utm_content` — тот же шаблон; по оговорке: признак согласия пользователя в запросе пока не передаётся.

## [2026-10-09] Гео OpenAI Ads по списку городов клиента: `openai_ads_geo.py`
Что: `Скрипты/openai_ads_geo.py` — перевод списка городов клиента (как в Google Ads) в почтовые индексы для кампании OpenAI Ads; `resolve` только читает, `apply` по умолчанию печатает «было → станет», запись с `--execute`, затем чтение обратно. Почему так: в OpenAI Ads городов нет (проверено на аккаунте: поиск локаций отдаёт штат, рынок DMA и индекс; на официальной странице таргетинга городов нет, каталог локаций отдал 403), а ручной подбор сотен индексов повторять на каждого клиента нельзя. Индексы берутся из публичной таблицы GeoNames, затем каждый проверяется поиском OpenAI; выдача поиска ограничена 20 записями, поэтому «поиск по названию города» не работает для крупных городов. Приближение: индекс не равен городу. Побочно: в `openai_ads.py` ключ кэшируется (раньше PowerShell вызывался на каждый запрос) и добавлен повтор при 429. Операция каталога агентов: «гео кампании OpenAI по списку городов клиента» (чтение → таблица плана → «да» → запись → чтение обратно). Ручным остаётся решение, оставлять ли рынки DMA рядом с индексами (рынки намного шире списка клиента).
