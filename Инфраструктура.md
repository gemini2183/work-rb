# Инфраструктура

Это не база знаний по контекстной рекламе (для этого — `База_знаний/`) и не лог
решений по конкретному клиенту (для этого — `Клиенты/<клиент>/Решения.md`).
Здесь — история решений о том, как устроена сама система: вики, скрипты,
автоматизация. Формат — как везде: `## [ГГГГ-ММ-ДД] тема | решение | почему`.

Если тут наберётся много разноплановых страниц (не просто хронология, а
несколько независимых тем) — превратить в папку `Система/` со своим index.md.
Пока хватает одного файла.

## [2026-07-16] Скрипты сбора статистики (Директ / Метрика)

Расположение: `Скрипты/direct_stats.py`, `Скрипты/metrika_stats.py`, общий модуль
`Скрипты/_config.py`. Подробности запуска — `Скрипты/README.md`.

**Решение:** один скрипт на источник данных (не по скрипту на клиента) —
различие между клиентами только в логине/токене/номерах целей, структура
запроса одинаковая.

**Почему:** логин/токен/счётчик Метрики не дублируются в этой вики — читаются
напрямую из общей Google-таблицы (`1ymDNHkj32mYIb_ymf7t8O6H6WY1s5F1FN43-56fwiQM`,
вкладки "Директ"/"Metrika"), той же самой, что питает продовый BigQuery-пайплайн
в `E:/PythonProjects/RedBird/google-cloud-jobs`. Единый источник правды — если
токен обновится там, здесь ничего менять не нужно. Доступ — через service
account `Скрипты/secrets/rb_cloud_service.json` (скопирован оттуда же, не в git,
read-only к таблице).

Логика запроса адаптирована из `google-cloud-jobs/redbird/func/direct_stats_job_src`
и `metrika-stats-job_src`, но без BigQuery/Google Sheets записи — работает на
одного клиента за раз, кладёт TSV/CSV снапшот прямо в
`Клиенты/<клиент>/Статистика/`.

**Проверено:** 2026-07-16 — успешный запуск на клиенте [[ЕГЭ Merlin]] (реальные
данные по кампаниям и визитам получены).

**Открытый вопрос:** пока запуск ручной. Если станет неудобно — обсудить
автоматизацию (cron/Task Scheduler) с фиксированной периодичностью снапшотов.

## [2026-07-16] Разделение База_знаний/Инструменты vs Инфраструктура

**Решение:** `База_знаний/Инструменты/` — строго только отраслевое знание
(фичи/инструменты Директа и Ads), извлечённое из статей и мануалов, которые
приносит пользователь, со статусом протестировано/не протестировано на наших
кампаниях. Документация про наши собственные скрипты и устройство вики туда не
попадает — для этого этот файл (`Инфраструктура.md`) и `Скрипты/README.md`.

**Почему:** изначально страница про скрипты сбора статистики была ошибочно
положена в `База_знаний/Инструменты/` — смешала внешнее отраслевое знание с
внутренней документацией инструментов. Это две разные вещи с разной судьбой:
знания из статей растут от источников и не меняются, когда меняется наш код;
факты про нашу инфраструктуру меняются, когда меняется наш код, и не зависят от
новых статей.

## [2026-07-16] Схема целей дашборда: Директ (расход/клики) + Метрика (цели) + колл-трекинг (звонки) напрямую

**Решение:** так же, как в проде — расход и клики берём из Директа, конверсии
(заявки через сайт) — из целей Метрики, а звонки, если у клиента подключён
колл-трекинг — из API колл-трекинг-сервиса напрямую, а не из целей Метрики.

**Почему:** источник трафика "Яндекс.Директ: не определено" в Метрике иногда не
долетает до правильной атрибуции — часть звонков просто не попадёт в отчёт,
если брать их только из целей Метрики. Это видно в таблице (вкладка "Metrika")
по колонкам `goal_id` (обычная цель Метрики) / `ct_goal_id` (цель
колл-трекинга) / `ct_goal_source` — если `ct_goal_source` заполнено (например,
`api`), звонки нужно брать из API этого сервиса, а не из Метрики.

**Открытая задача:** у нас пока нет скрипта, который тянет звонки из API
колл-трекинга (для ЕГЭ Merlin это Callibri, см. [[Клиенты/ЕГЭ Merlin/Цели/goals|Цели ЕГЭ Merlin]]).
Из-за этого текущий анализ по заявкам неполный — метрика-конверсии видим, звонки
нет. Нужно писать `callibri_stats.py` по аналогии с `direct_stats.py` /
`metrika_stats.py`, когда будем разбираться со звонками для реального KPI.

## [2026-07-24] Второе агентство в этой же вики: Adwhite (Google Ads)

**Решение:** помимо Redbird (Директ), в вики теперь ведётся второе агентство —
Adwhite (Google Ads/Merchant Center). У него отдельная общая Google-таблица
клиентов (`SHEET_URLS["adwhite"]` в `Скрипты/_config.py`, отдельно от
`SHEET_URLS["redbird"]`), с похожей, но не идентичной структурой вкладок
(`Google_Ads_API` вместо `Директ`/`Metrika`). `get_client_row(...,
agency="redbird"|"adwhite")` — параметр таблицы, по умолчанию `"redbird"`.

Доступ к Google Ads API (в отличие от Директа/Метрики, где REST+токен) требует
библиотеки `google-ads` (добавлена в `requirements.txt`) и OAuth-кредов
`Скрипты/secrets/google-ads.yaml` (developer_token/client_id/client_secret/
refresh_token/login_customer_id — MCC), скопированных из
`E:/PythonProjects/RedBird/google-cloud-jobs/adwhite/func/<любой gads-job>/google-ads.yaml`.
Не в git (папка `secrets/` целиком в `.gitignore`).

Написан общий `Скрипты/gads_stats.py` (трафик + конверсии одним GAQL-запросом
к ресурсу `campaign`, конверсии разбиваются по `segments.conversion_action_name`,
не суммируются — чтобы не терять смену основной цели конверсии во времени) и
первый клиент-специфичный `Скрипты/gads_stats_korogva.py` (клиент [[Клиенты/Корогва/index|Корогва]]:
один аккаунт Google Ads, разбитый на два подпроекта "Google Ads"/"Merchant
Center" по маркеру в названии кампании — `Sales`/`Merchant_` — не по
отдельному customer_id; 1:1 логика прод-job'ов `gads_korogva_gads`/
`gads_korogva_merchant`).

**Почему:** у клиента Корогва раньше трафик и конверсии собирались из разных
источников (Google Ads API + отдельно GA4) — сейчас переводим на единый
источник, GA4 больше не подключаем на этом этапе.

**Проверено:** 2026-07-24 — `gads_stats_korogva.py` прогнан на реальных данных
(11–17 июля), оба подпроекта собрались корректно.

**Открытый вопрос:** алгоритм анализа кампании для Google Ads/Корогвы —
разработка отложена на следующую сессию, начинается с чистого листа сразу по

## [2026-07-29] Третье направление: ВКонтакте — агентная генерация объявлений (в разработке)

**Контекст:** по мотивам кейса Anthropic Growth Marketing team (slash-команда
`/rsa` + два саб-агента по RSA-полям + experiment memory log, см.
`База_знаний/Источники/Кейс-Anthropic-Growth-Marketing-Claude-Code.md` и вывод

строить аналог для ВКонтакте — не как Python-скрипт, вызывающий Claude API
напрямую, а как slash-команда/агент внутри Claude Code.

**Решение (архитектура саб-агентов):** в отличие от оригинала (деление по
формальному лимиту headline/description), для VK делим саб-агентов по
смысловой роли — агент **"Заголовок"** (короткий вовлекающий элемент, до 40
симв.) и агент **"Текст"** (весь текст объявления целиком, включая собственный
хук в первой строке — в ленте ВК заголовок и текст показываются вместе, но
хук физически должен быть в тексте, т.к. отдельного поля "хук" в интерфейсе
нет). Подробности и открытые вопросы по этому делению —
`База_знаний/Паттерны/Структура-объявления-ВКонтакте-заголовок-хук-текст.md`.

**Решение (мультинишевость):** предыдущие попытки сделать один универсальный
инструмент под все ниши проваливались — по всей видимости, потому что нишевая
специфика зашивалась прямо в промпт агента и размывалась. Вместо этого —
четырёхслойная модель контекста, подмешиваемого в вызов саб-агентов (подробнее
и с обоснованием четвёртого слоя —
`База_знаний/Паттерны/Агентная-генерация-объявлений-архитектура.md`):
1. **Площадка** (VK) — общие правила/лимиты/механики ленты, не зависит от ниши.
2. **Ниша** — примеры хуков/болей/тона конкретно под нишу, растёт из практики.
3. **Клиент** — бренд-тон и специфика конкретного проекта (уже покрывается
   `Клиенты/<Имя>/_project.md`).
4. **Цель кампании** (подписаться / написать сообщение / далее по мере
   появления новых целей VK) — влияет только на то, к какому действию должен
   логически подводить финал текста саб-агента "Текст"; сама структура
   объявления (заголовок+текст) от цели не зависит, меняется только CTA-кнопка
   (выбирается из готового списка VK, не генерируется).

Агент (роль "Заголовок"/"Текст") остаётся один и тот же для всех ниш и целей —
меняются только данные слоёв 2/3/4, которые ему подмешивают на входе, а не сам
промпт/код.

## [2026-08-18] Семейство скриптов Google Ads Editor bulksheet (гео-расширение и генерация семантики с нуля)

**Решение:** четыре новых скрипта в `Скрипты/`, читающих Google Ads API
только на чтение и собирающих CSV в формате Google Ads Editor bulk upload —
ничего не пишут в аккаунт напрямую, заливка всегда вручную через Editor:

- `gads_geo_ad_group_builder.py` — расширяет СУЩЕСТВУЮЩУЮ кампанию: берёт
  вручную отобранные группы кампании-источника, строит из них гео-варианты
  (дублирует каждый ключ под несколько geo-суффиксов внутри одной новой
  группы, адаптирует текст объявления заменой "CA"/"California" на короткий
  geo-текст).
- `gads_semantics_generator.py` — генерирует широкие/фразовые ключи из
  словаря тем клиента (`Клиенты/<клиент>/Семантика/Словарь-тем.yaml`):
  перемножение тема × модификатор происшествия × юридический суффикс. Только
  печатает список для одобрения, ничего не группирует и не заливает.
- `gads_ad_adapter.py` — штампует RSA-объявление по зафиксированному эталону
  (`Клиенты/<клиент>/Кампании/Search/Эталонное-объявление-и-sitelinks.yaml`,
  headlines/descriptions размечены role themed/universal) под каждую тему +
  готовит sitelinks на уровень кампании.
- `gads_campaign_builder.py` — комбинирует предыдущие два (генератор
  семантики + адаптер объявлений) в один CSV для НОВОЙ кампании "с нуля":
  строка `Campaign` (Search, статус Paused, бюджет-заглушка) + группы по
  темам словаря + сгенерированные ключи + объявления + sitelinks.

**Почему такое разделение на 4 скрипта, а не один универсальный:** это два
разных сценария использования (расширить то, что уже есть в аккаунте
гео-вариантами / построить что-то новое искусственно из словаря), которые
делят только форматирующую логику (CSV Google Ads Editor, проверка лимитов
символов, адаптация текста объявления по теме) — вынесена в переиспользуемые
функции, импортируемые между скриптами, а не продублирована.

**Технический баг, исправленный по ходу (актуален для любого нового скрипта,
работающего с текстом RSA-объявлений):** лимит символов Google Ads (30 симв.
Headline, 90 Description) для динамических вставок `{KeyWord:...}` и
`{LOCATION(...):...}` считается по видимому тексту ПОСЛЕ последнего `:`
внутри скобок, не по всей синтаксической записи со скобками — и вставка
может быть частью более длинной строки (не только всей строкой целиком).
Обе ошибки давали ложные "превышения лимита" при первой версии проверки.

**Рабочий цикл — диалоговый, не автоматизированный сквозняком:** пользователь
явно называет, какие группы/темы брать на каждом шаге; скрипты выводят
превью и предупреждения о превышении лимитов символов для ручного review
перед запуском следующего скрипта или импортом в Editor. Обсуждалась
альтернатива (Streamlit-приложение с чекбоксами) — отклонена пользователем
в пользу диалогового цикла в чате, см. `Клиенты/Andverpersonalinjury/Решения.md`.

**Открытый вопрос:** сверка сгенерированной семантики с уже загруженными в
аккаунте ключами (чтобы не предлагать дубли) сознательно не реализована —
решено полагаться на подсветку дублей самим Google Ads Editor при импорте.
Если это станет узким местом при регулярном использовании — реализовать
отдельным шагом (GAQL-запрос по всему аккаунту + diff со сгенерированным
списком).

## [2026-08-19] Аудит сетей показа Google Ads (Search vs Search Partners) — новый скрипт + подтверждён доступ без строки в таблице

Расположение: `Скрипты/gads_search_partners_audit.py`. Написан по запросу
пользователя (Клиенты/Andverpersonalinjury — подозрение на бот/фрод-трафик с Search

клики/расход/конверсии раздельно по SEARCH/SEARCH_PARTNERS/CONTENT/и т.д.;
(2) детальный список площадок внутри Search Partners через
`detail_content_suitability_placement_view` — новый ресурс API, которым
Google в августе 2025 впервые дал видимость по доменам Search Partner
Network (до этого такой отчёт не существовал вообще, ни в UI, ни в API).

**Найденные ограничения API (не решаются на нашей стороне, задокументированы
в docstring скрипта):**
- `detail_content_suitability_placement_view` отдаёт ТОЛЬКО
  `metrics.impressions` — API отклоняет запрос с clicks/cost_micros/
  conversions в том же SELECT ("metric is incompatible with the resource").
  По каждой площадке видно только количество показов, не деньги/клики/
  конверсии по ней отдельно.
- Этот же ресурс несовместим с `segments.ad_network_type` в SELECT/WHERE —
  видимо, ресурс уже по своей природе относится только к Search Partner
  Network, отдельный фильтр по сети не нужен и не принимается API.
- Оба GAQL-запроса в этом ресурсе и в campaign resource требуют явно
  включать в SELECT любое поле, использованное в WHERE (`campaign.status`,
  `segments.ad_network_type`) — иначе `EXPECTED_REFERENCED_FIELD_IN_SELECT_CLAUSE`.
  Общее свойство GAQL, не специфика этого скрипта, но стоило времени на
  дебаг при первом запуске — фиксируется, чтобы не наступать повторно.

**Побочная находка — доступ к клиенту без строки в общей таблице:**
Andverpersonalinjury (Юристы США) не заведён строкой на вкладке
Google_Ads_API общей таблицы Adwhite (см. Клиенты/Andverpersonalinjury/_project.md) —
`get_client_row()` в этом случае бросает исключение. Скрипт расширен опцией
`--customer-id` (по образцу уже существующего паттерна в
`gads_geo_ad_group_builder.py`) — принимает customer_id напрямую, в обход
таблицы, доступ к самому Google Ads API при этом уже настроен и рабочий
(`Скрипты/secrets/google-ads.yaml`, тот же для всех Adwhite-клиентов). Это
не отсутствие доступа, а отсутствие записи в таблице-реестре — сам API
доступен с самого начала. Для Andverpersonalinjury customer_id
`213-621-6123` зафиксирован в `Клиенты/Andverpersonalinjury/_project.md` — использовать
`--customer-id 213-621-6123`, не искать заново и не спрашивать доступ.

## [2026-08-25] Третий источник данных: API Яндекс ПромоСтраниц (расход)

**Решение:** для клиента [[Клиенты/Франшиза Мокрый Нос Дзен/index|Франшиза Мокрый Нос Дзен]]
подключён API Яндекс ПромоСтраниц через уже существующий рабочий скрипт
`E:/PythonProjects/RedBird/dev/Promopages/promopages.py` (вне этого репозитория,
в `RedBird/dev` — не копировался в `Скрипты/`, т.к. пока разовый запуск
под одного клиента, не по общему паттерну "один скрипт на источник для всех
клиентов"). Использует отдельный OAuth-токен с правом `promopages:api` —
НЕ тот же токен/механизм, что у Директа/Метрики (`Скрипты/_config.py` сюда не
относится, там только Google Sheets service account).

**API:** `GET /campaigns` (список кампаний, `title` совпадает 1:1 с UTM Campaign
в Метрике — можно сводить датасеты по названию без доп. маппинга) и отчёт
`campaigns-daily-stats` (POST создать отчёт → GET по `reportId`, до готовности
код 202) с полем `budget` (расход в руб.) по кампании/дню.

**Важное ограничение, подтверждённое эмпирически:** в API Promo Pages НЕТ
гео-разреза вообще — ни в `campaigns-daily-stats`, ни в
`campaigns-publications-daily-stats` (второй report type в скрипте). Расход
считается и таргетируется только на уровне кампании/публикации, не региона.
Гипотезу "какой-то конкретный город/регион съедает непропорционально много
бюджета" по этому источнику проверить нельзя в принципе — не ограничение
скрипта, ограничение самого API.

**Результат первого запуска:** сохранено в
`Клиенты/Франшиза Мокрый Нос Дзен/Статистика/promopages_budget_2023-01-01_to_2026-08-24.json`
(сырой JSON — campaigns + statistics, не CSV, т.к. campaigns и statistics две
разные таблицы, сведённые по campaignId только на этапе анализа, не на этапе
выгрузки). См. `Клиенты/Франшиза Мокрый Нос Дзен/Решения.md`, запись 2026-08-25
"бюджет и CPL" — сведение с Метрикой и посчитанный CPL по статьям.

**Открытый вопрос:** если у других клиентов тоже используются Promo Pages,
стоит перенести `promopages.py` в `Скрипты/` и обобщить по паттерну README
(один скрипт на источник + client-specific при необходимости), с токеном не
