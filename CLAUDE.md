# Схема хранилища: управление проектами по контекстной рекламе

Это Obsidian-вики по паттерну "LLM Wiki". Ты — единственный, кто пишет и поддерживает
структуру. Пользователь курирует источники, задаёт вопросы и принимает решения; вся
рутина (кросс-ссылки, обновление статусов, ведение логов) — твоя ответственность.

## Структура

- `Клиенты/<Имя>/` — рабочая папка по каждому проекту (клиенту). Шаблон — в
  `Клиенты/_шаблон_клиента/`, копируй его при заведении нового клиента.
  - `_project.md` — бриф: ниша, ЛПР, история отношений, договорённости.
  - `Цели/goals.md` — цели аналитики (Метрика/GA): ID, название, макро/микро, что считается конверсией.
  - `Семантика/` — мастер-список ключей: статус (в проработке / использован / в архиве / отклонён), в какой кампании.
  - `Аудитории/` — сегменты ретаргетинга: где заведены, на каком этапе воронки, статус проработки по типам кампаний.
  - `Кампании/Search/`, `Кампании/РСЯ_КМС/` — по файлу на кампанию. Внутри — append-only лог действий и эффектов.
  - `Статистика/` — снапшоты, которые кладут скрипты из `Скрипты/`. Ты их читаешь и анализируешь тренды, сам туда не пишешь руками.
  - `Решения.md` — append-only стратегический лог клиента (формат ниже).
  - `Журнал_изменений.md` — append-only список фактических изменений в кабинетах/трекинге
    (было → стало, снимок «до», откат, когда мерить). Заводится у клиента при первой записи
    в кабинет; пример — `Клиенты/ProfiMet/Журнал_изменений.md`.
  - `Задачи.md` — to-do список по клиенту (чекбоксы `- [ ]`, теги `#задача` и
    `#клиент/<Имя>` на каждой строке, дедлайн `📅 ГГГГ-ММ-ДД`). Не путать с
    `Решения.md` — задачи это конкретные действия к исполнению, решения — это
    зафиксированный факт/вывод. Когда в разговоре всплывает конкретное действие
    "надо сделать X" — заносить сюда, а не только проговаривать в чате.
  - `index.md` — точка входа по клиенту: ссылки на всё выше + текущий статус одной строкой.
- `База_знаний/` — общие, кросс-клиентские знания (не привязаны к одному проекту).
  - `Источники/` — сырые материалы (статьи, доки по инструментам). Неизменяемые, только читаешь.
  - `Инструменты/` — вики-страницы по фичам/сервисам Директа и Ads. Frontmatter `status: протестировано|не протестировано|отклонено`.
  - `Паттерны/` — обобщённые выводы ("что работает / не работает"), со ссылками на конкретные записи в `Решения.md` клиентов как на доказательство.
  - `index.md`, `log.md` — как в паттерне Karpathy.
- `Бэклог_идей.md` — append-only список идей и гипотез, всплывших в разговоре, которые не относятся к текущей задаче, но жалко терять. См. правило ниже.
- `Инфраструктура.md` — append-only лог инженерных решений про саму систему (вики, скрипты, автоматизация): что построено и почему так, а не иначе. НЕ отраслевое знание про рекламу (для этого — `База_знаний/`) и НЕ решения по клиенту (для этого — `Клиенты/<клиент>/Решения.md`). Если содержимое разрастётся до нескольких независимых тем — превратить в папку `Система/` с index.md; пока хватает одного файла.
- `Скрипты/` — Python-инструменты, тянущие статистику из API Директа/Ads в `Статистика/` клиента. Скрипты только собирают данные, не делают выводов. Как устроены — см. `Скрипты/README.md` и `Инфраструктура.md`.
- `Инбокс.md` — сырые мысли/заметки пользователя на лету, без структуры. Разбирается
  ТОЛЬКО по явному запросу пользователя ("разбери инбокс") — не разбирать
  автоматически без запроса. При разборе: каждую запись отнести к нужному месту
  (`Решения.md` клиента, `Задачи.md` клиента или корневой, `База_знаний/Паттерны|Инструменты/`,
  `Бэклог_идей.md`), а разобранные записи удалить из `Инбокс.md` — он должен
  оставаться пустым между разборами.
- `Задачи.md` (корень) — to-do для НЕ-клиентских задач (инфраструктура, скрипты,
  база знаний, орг-вопросы). Клиентские задачи — только в `Клиенты/<Имя>/Задачи.md`,
  не здесь.
- `Обзор-задач.md` — сводный вид всех задач (клиентских и общих) через запросы
  community-плагина Obsidian "Tasks". Ничего не дублирует, только агрегирует
  живым запросом по тегу `#задача`. Когда заводишь новую задачу в любом
  `Задачи.md` — обязательно ставить тег `#задача` (и `#клиент/<Имя>` для
  клиентских), иначе она не попадёт в сводный обзор.

## Формат записей в логах (Решения.md, лог кампании)

Единый парсибл-префикс:

```
## [ГГГГ-ММ-ДД] Кампания/тема | действие | гипотеза | результат
```

Это позволяет `grep "^## \["` по всем клиентам разом для еженедельного обзора.

## Протокол в начале сессии по клиенту

1. Прочитать `Клиенты/<Имя>/index.md` и `_project.md`.
2. Прочитать последние ~10 записей `Решения.md`.
3. Если вопрос касается конкретной кампании/семантики/аудитории — открыть соответствующий файл.
4. Проверить `База_знаний/Паттерны/` на релевантные обобщения, прежде чем предлагать стратегию с нуля.

## Протокол на вопрос по практике/инструментам

1. Сначала искать в `База_знаний/Инструменты/` и `Паттерны/`.
2. Если там нет ответа — явно сказать пользователю "в базе знаний этого нет, ищу внешне",
   пойти в WebSearch/память модели, ответить.
3. При внешнем поиске по вопросу, привязанному к конкретному типу
   кампании/объекту/конфигурации (например "стратегии ставок для Shopping",
   а не "стратегии ставок вообще") — не останавливаться на первой найденной
   общей статье. Целенаправленно искать специализированную страницу именно
   под этот тип/объект (официальная документация Google/Яндекса обычно
   такие держит отдельно от общих обзорных статей — общая описывает
   механику стратегии вообще и может не уточнять, для каких типов кампаний
   она физически недоступна). Сделать минимум два поисковых запроса:
   один по официальной документации, один по независимым профильным
   источникам (агентские блоги, практики) — если они расходятся, явно
   проговорить расхождение и вероятную причину, не выбирать один ответ молча.
   Если специализированной страницы нет — сказать это прямо, не подменять
   её общей формулировкой.
4. Не подавать список фактов из документации уверенным тоном без оговорок —
   если факт не сверен со скриншотом/поведением реального кабинета,
   пометка "не проверено на практике" должна стоять в начале ответа или
   рядом с самим фактом, а не единственной строкой в конце.
5. После ответа — обязательно оформить результат новой или обновлённой страницей в
   `База_знаний/Инструменты/` (или `Паттерны/`, если это вывод, а не факт про инструмент),
   со статусом "не протестировано" по умолчанию, пока пользователь не подтвердит проверку на практике.
6. Не путать "нашёл во внешнем источнике" и "проверено на наших кампаниях" — это разные статусы.

## Правило бэклога идей

Во время любого обсуждения (по клиенту или по общим концепциям) — если всплывает идея,
гипотеза или направление для будущего мозгового штурма, которое не является прямым
предметом текущего вопроса: не терять её в чате, а сразу дописать в `Бэклог_идей.md`
короткой записью с датой, контекстом (какой клиент/тема породили) и почему это может
быть ценно. Не спрашивать разрешения на каждую такую запись — просто делать по ходу и
кратко упоминать пользователю, что записал. Когда пользователь спрашивает "что у нас есть
интересного на подумать" — читать этот файл целиком и предлагать выжимку.

## Что фиксировать как "решение" vs "лог"

- `Решения.md` — стратегический уровень: почему выбрали направление, что поменяли в
  стратегии и зачем, реакция на результаты по крупным срезам.
- Логи кампаний — операционный уровень: конкретные правки (ставки, объявления, минус-слова)
  и их непосредственный эффект.
- Не дублировать одно и то же в обоих местах — операционное действие попадает в
  `Решения.md` только если оно стратегически значимо (смена подхода, а не рутинная правка).

## Куда класть факт: База_знаний vs Инфраструктура

- `База_знаний/Инструменты/` — только отраслевое знание: фичи/инструменты Директа
  и Ads, извлечённые из статей/мануалов, которые приносит пользователь. Растёт от
  внешних источников, не зависит от нашего кода.
- `Инфраструктура.md` — факты про то, как устроена наша собственная система
  (скрипты, вики, автоматизация). Меняется, когда меняется наш код, не зависит
  от новых статей. Не смешивать эти два потока.

## Обязательная сверка конверсий перед выводами по кампании

Перед любым стратегическим выводом по конкретной кампании ("эта РК не работает,
надо выключить/урезать" и т.п.) — сначала свериться с методологией
`База_знаний/Паттерны/Сверка-конверсий-Директ-Метрика-Коллтрекинг.md`: конверсии
по Директу (через `Goals`) могут быть занижены (звонки/конверсии без чистой
привязки к кампании). Не делать вывод "кампания слабая" по одним лишь данным
Директа, не проверив, не выросла бы картина при учёте Метрики+колл-трекинга —
и если сверка невозможна/ненадёжна, явно проговорить это ограничение, а не
опустить его молча.

## Протокол записи в рекламные кабинеты (Google Ads API)

Запись в кабинет через API разрешена (договорённость 2026-10-06), но только по схеме
«предложил → согласовали → записал»:

1. **Сначала план в таблице, ничего не пишу.** Перед любой записью показываю
   пользователю таблицу: `Объект | Действие | Было → Станет | Откуда факт`.
   Для текстов объявлений отдельная таблица: `Поле | Текст | Знаков/лимит | Откуда факт`.
2. **Допущения — отдельным блоком "Допущения (проверить)":** всё, что я выбрал сам
   по умолчанию (расписание, URL, гео, галочки), чтобы пользователь видел их до записи.
3. **Факты в текстах (подарки, цены, сроки, условия акций) — только из свежих
   источников клиента** (присланное в сессии), не из старых кампаний аккаунта.
4. **Явное «да» от пользователя — тогда пишу.** До этого максимум режим
   `validate_only` (Google проверяет, ничего не создаёт).
5. **Новые кампании — всегда на паузе.** Включение — отдельное согласование.
6. **Запись считается:** создание/изменение/удаление кампаний, групп, объявлений,
   ключей, минус-слов, аудиторий; смена бюджета, ставок, стратегии, статуса.
7. **После записи — прочитать обратно из аккаунта** и показать фактическое состояние
   (а не пересказ того, что отправлял), затем записать в `Решения.md`/лог кампании
   и при необходимости `Инфраструктура.md`, **а также блоком в `Клиенты/<Имя>/Журнал_изменений.md`**
   (что было → что стало, снимок «до», проверка, откат, когда мерить эффект) — оттуда
   берёт данные ежемесячный отчёт.

Скрипты записи лежат в `Скрипты/` (пример — `gads_display_rtg_builder.py`:
по умолчанию `validate_only`, запись только с `--execute`).

## Периодический lint (по запросу пользователя)

Проверять: противоречия между `Решения.md` и текущими настройками кампаний; семантику/
аудитории без статуса; orphan-страницы в `База_знаний/`; устаревшие практики, которые
новые источники опровергли; кампании без записей дольше N недель (возможно, заброшены);
Google Ads: цель «привлечение новых клиентов» у кампаний (`campaign_lifecycle_goal`) и метки «Purchasers»
у списков (`user_list_customer_type`) — метка должна стоять только на списке реальных покупателей, на
широких списках (посетители, вовлечённые, корзина) её нужно снимать.

## Стиль

Обновлять, а не переписывать заново — вики растёт инкрементально. Ссылки между файлами —
через `[[Имя_страницы]]`. Все новые страницы — с YAML frontmatter минимум `status` и
`updated`, где это применимо.
